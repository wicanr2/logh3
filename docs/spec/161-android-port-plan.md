## 移植阻礙（已確認）

0. **實作時的結構（第175輪）**：`cmd/gin3` 原地不動，被 105 份文件與多支工具以路徑引用，整個搬移屬大型重構。
   行動版另起 `internal/mobileshell`（殼）與 `mobile`（只露出給 Java 的 `Start`、`Back`），不會編到
   `cmd/gin3`，所以下面第 1 項的 ALSA 問題實際不會發生；第 2、3 項由新殼直接處理。
   只編 64 位元：`internal/ai/tactical.go` 等處以 `1<<62` 當哨兵值，32 位元版會溢位或算出不同結果。
1. **音效裝置偵測會讓 Android 編不過。** `cmd/gin3/audio_device_linux.go` 標 `//go:build linux`，
   用 cgo 連 ALSA。`GOOS=android` 也符合 `linux` 標籤，會去找 `alsa.pc`。要改成 `linux && !android`，
   Android 走 `audio_device_other.go`。
2. **入口是 `package main` 加命令列旗標。** 載入流程是 `main()` 裡的一個閉包，路徑都來自旗標與
   `os.Executable()` 推出的發行目錄（`resourcepaths.go`）。行動版需要一個可被 `ebitenmobile bind`
   匯出的套件，接收 Java 傳進來的目錄，回傳 `ebiten.Game`。做法是把載入流程抽成共用函式，
   桌面 `main` 與行動版都呼叫它。
3. **存檔目錄。** `defaultSaveDir` 用 `os.UserConfigDir()`。Go 在 Android 走 Unix 分支，
   需要 `XDG_CONFIG_HOME` 或 `HOME`（`$GOROOT/src/os/file.go`），App 程序不保證有。
   改由 Java 傳入 App 私有目錄（`Context.getFilesDir()`）。
4. **素材是一般檔案路徑。** 全部用 `os.ReadFile`／`os.Open` 讀目錄。APK 裡的 assets 不是檔案系統，
   要選一種：首次啟動解到 App 私有目錄、改走 `fs.FS` 抽象由 Java 的 AssetManager 供檔，或用商店的
   大型資源分送機制。發行包目前約 356 MB（v1.6.5 AppImage），主要是 HD 圖 101 MB、配樂 127 MB、
   音色庫 142 MB。商店對 APK／AAB 的大小限制**待查證**，查到再定。
5. **沒有觸控輸入。** `cmd/gin3` 有 11 處讀滑鼠（`CursorPosition`、`IsMouseButtonJustPressed`），
   讀觸控的地方是 0。介面也依賴滑鼠特性：左下角摘要跟著游標停的星域走（hover），右鍵逐層關窗，
   左鍵按住連捲。
6. **原版遊戲檔不能隨包。** 專案規則是發行包不內嵌原版遊戲檔與素材（`AGENTS.md` 素材邊界）。
   Android 版要讓玩家匯入自己的原版檔，例如用系統的檔案選取器選資料夾，再複製到 App 私有目錄。

### 架構

- 輸入層抽一個虛擬指標：桌面由滑鼠寫入，Android 由觸控手勢寫入，遊戲端照舊讀「游標位置與按鍵」。
- 觸控以 TouchID 在按下時綁定區域（海報區按鈕、遊戲區），一手按鈕一手滑動不互相干擾。
- 輕觸在抬起時合成「移位 → 按下至少一格 → 放開」，避免同一格按下又放開被 `JustPressed` 漏掉。
- 移動超過門檻（約 8–12 dp）就判定為拖曳，抬起不送左鍵。
- 返回手勢：Java `OnBackPressedCallback` 寫入執行緒安全佇列，下一次 `Update` 消費成一次右鍵。遊戲中一律攔截，不直接關 App。
- `onPause` 清空所有觸控與按鍵狀態，避免切回來卡在按住。
- 觸控控制一律放在 4:3 遊戲區之外的左右兩條，避開系統返回手勢熱區與挖孔安全區；中央原版畫面不疊任何虛擬按鍵。

## 行動版版面設計（第三輪討論後）

2026-11-19 與 Gemini 第三輪討論（原文 `workplace/android174/gemini3.md`）。

### 繪製分層

原本設想只從 640×480 畫面裁切重組，但原版計劃視窗（480×340 置中）會蓋住左半的銀河地圖，
從單一畫面裁出地圖會帶到視窗殘片，顯示層也無法只看像素判斷開了幾層視窗。改成：

- **世界層**：只畫銀河地圖或戰場視野。
- **面板與視窗層**：照原版座標畫右半面板、小地圖、各種原版視窗。
- 遊戲端每格另外回報目前開著的視窗矩形、種類、疊放順序、是否強制（modal）。
- 桌面與對拍：兩層照原座標合成，就是原版 640×480，既有收據不受影響。這一點要用既有逐像素測試證明。
- Android：兩層分開排版；觸控座標反算回原版座標再交給遊戲。直接觸控模式隱藏原版游標。

### 戰略畫面（20:9）

| 區塊 | 位置與規則 |
|---|---|
| 銀河地圖 | 滿高、**靠左**，約佔寬度 48%。置中會讓兩側各剩不到 173 單位，放不下 320 寬的卡片 |
| 側欄 | 地圖左側：戰略命令、一覽表、系統指令、返回、模式切換 |
| 卡片槽 | 地圖右側，約佔寬度 43%。最上方常駐日期與軍事費；下方停靠星域摘要卡，不遮地圖 |
| 星域摘要卡 | 只裁「選中星域摘要＋四分頁清單」那一段，不裁整條右半面板，換取較大的放大倍率；卡片上加「詳細情報」鈕，與原版「再點同格開星系情報」並存 |
| 原版強制視窗 | 計劃、清單、星系情報、提督資料等一律置中等比放大，底下加半透明遮罩；子視窗依原版順序層層疊，只有最上層可操作 |
| 窄螢幕（16:9、18:9）| 剩餘寬度不足時，卡片改成浮動並避開點到的星域那一側 |

地圖下方原版的「游標停留星域摘要」在直接觸控模式下由摘要卡取代，不另做長按預覽；觸控板模式照原版。

### 戰場畫面

- 視野寬度抽成一個參數：桌面與對拍 28 格，Android 40 格。要一起改的有鏡頭右邊界（128−寬度）、置中公式、
  戰場點擊範圍、小地圖上的視野框與點小地圖跳轉。
- **待查證**：是否有「物件在畫面內才觸發」的邏輯（自動切鏡頭、播動畫、暫停），若會改變計時或亂數消耗，
  Android 與桌面會分歧。驗收時同一份戰場輸入在 28 與 40 格下跑完，比每回合結束的規則狀態與亂數種子必須相同。
- 點分隊開作戰選單時，分隊面板一起跳出，放在被選分隊的對側；小地圖改為側欄開關的浮窗。

### 可讀性

- 6.5 吋 20:9 手機上，清單視窗放到 90% 高時原版 16×16 字約 2.65 mm，可讀；但每列只有 2.7–3.3 mm，
  遠小於建議的觸控目標，清單要加上下滑動翻頁，觸控板模式保留為精準點選工具。
- 非整數倍放大會讓 1 像素筆畫粗細不一，縮放用「先整數倍再線性濾波」的方式。HD 模式的高解析字改善清晰度，
  但不改變實際毫米大小；手機上 HD 3 倍 CPU 繪製的發熱與幀率要實測。

## 驗證方式

- 桌面回歸：A1 之後跑標準 21 套件與既有正常玩家 GUI 路徑。
- Android：本機 Docker 內的 KVM 模擬器可用（`tools/android_emulator_check.sh`，API 35、1280×576）。主機負載高時系統程序可能被判無回應殺掉，連帶 App 結束，屬環境問題。實機驗收需要使用者的裝置。
- 整場玩家路徑：`TestMobileNewGameFullBattle`（`LOGH3_MOBILE_E2E=1`）在桌面驅動行動版殼，每一下都換成手機上的觸控位置。
- 觸控路徑的完成定義比照畫面對拍：每條路徑的截圖、輸入序列、裝置型號與 Android 版本都要記錄。
