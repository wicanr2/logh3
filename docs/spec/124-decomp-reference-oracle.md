# 124：反編譯參考實作作為規則 oracle

狀態：READY（2026-10-09，使用者核准契約修訂）。第一支函式已有收據，契約已寫入專案 `AGENTS.md` §3c。

## 要解決的問題

規則層的對拍目前每一案都要起 dosgolem、載入保存狀態、送輸入。純函式的驗證可以改成：
先把原版函式用 C 寫成參考實作，一次性對原版做差異測試，之後 remake 與 C 版在原生環境窮舉比對。

## 驗證等級

| 等級 | 條件 | 可以宣稱 | 不可以宣稱 |
|---|---|---|---|
| `byte-matching` | 同版編譯器與旗標編出的 bytes 與原版相同，relocation 另記 | C 版與原版機器碼一致 | 作者當年的原始碼 |
| `diff-tested` | 同一份記憶體輸入下，原版函式（dosgolem 直接呼叫）與 C 版輸出逐筆相同，並有負向對照 | 在聲明的輸入域內功能等價 | 域外行為、呼叫時機 |
| `reasoned` | 只由反組譯推導，沒有差異測試 | 研究線索 | 等價 |

`GIN3PS.EXE` 的 C runtime 是 Datalight C 3.10 Large（`docs/re/442`）。已取得的後代編譯器產生不同的 long 運算呼叫慣例，
目前只能到 `diff-tested`。取得同版編譯器後，函式可以升到 `byte-matching`，等級不倒退。

## diff-tested 的最低條件

1. 原版函式以 `Call` 直接呼叫，函式位元組的 SHA-256 與保存狀態的 SHA-256 記入收據。
2. 呼叫期間清除 IF、設定 DS，並驗證函式只動到堆疊（純函式）。有副作用的函式要明列寫入範圍。
3. 輸入包含邊界與溢位案，隨機欄位涵蓋函式不讀的位元組，確認沒有隱藏依賴。
4. 兩次產生的向量檔逐位元組相同。
5. 至少三個負向對照（故意改壞 C 版）全部被抓到。
6. 輸入域在文件寫明。域外（例如槽數超過記錄長度）的原版行為不由 C 版涵蓋。

## 各類驗證的歸屬

| 類別 | 做法 | 狀態 |
|---|---|---|
| 純規則運算（輸入為記憶體資料，輸出為回傳值或資料變更） | 原版函式一次性對 C 版差異測試；remake 對 C 版原生窮舉 | 試點 `203A:0424` 完成 |
| 含亂數的規則 | C 版帶原版 LCG 與呼叫順序，受控亂數下比對；亂數序列等價要先證 | 未開始 |
| 呼叫時機與流程（回合推進、觸發順序） | 仍用 dosgolem 同狀態對拍。`oracle.Call` 只驗常式實作，不驗呼叫時機 | 保留 |
| 畫面、調色盤、文字、動畫 | 仍用 dosgolem framebuffer 對拍 | 保留 |
| 計時、輸入、DOS 與硬體服務 | 仍用 dosgolem | 保留 |
| 戰略 AI 決策 | 先判斷各函式是否純函式，再歸入上面某類 | 待評估 |

C 版不涵蓋的類別不會因為規則層的函式都有 C 版而消失，所以「完成度」仍以 `VERIFICATION-MATRIX.md` 為準。

## 試點結果

`203A:0424`（戰略艦隊攻擊力）：5006 案與原版零不符，三個變異全被抓到，remake 的 Go 實作只在 16 位元溢位區與原版不同。
