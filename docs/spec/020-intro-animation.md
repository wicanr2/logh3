# 020 — 開頭動畫

第97輪續接勘誤：動畫末格的額外等待、TITSPT尾段色盤與自然標題／逾時重播，
以[112](112-title-player.md)及[431](../re/431-title-player.md)為準。
下方「自然播完進主選單」與「標題還沒接上」保存當時狀態，已由112取代。
輸入跳過仍直接進主選單；逐格解碼與其他時程保持。

狀態：**CONFORMED**（照原版播放順序、逐格時程與尾段清除規則實作，
並以 dosgolem 收據抽樣對拍）。
證據：`docs/re/71`、`docs/re/72`、`docs/re/108`、`docs/re/110`、
`docs/re/283`、`docs/internals/19`。

## 素材

| 檔 | 內容 |
|---|---|
| `IBM16.350` | 1,764,911 bytes，374 段壓縮資料首尾相接 |
| `IBMFLS16.350` | 748 bytes ＝ 374 個 uint16，每一個是一格的長度（加起來剛好等於上面）|
| `BU16IBM.RGB` | 48 bytes ＝ 16 組 RGB，值 0–15 |

## 一格怎麼解（confirmed）

一格 ＝ **四個 plane**，每個 plane 後面接一個分隔位元組（實測是 `01`）。
一個 plane 是 80 × 227 ＝ 18,160 個位元組，token 解出來的位元組
**一欄一欄往下 XOR**：

```
di ＝ 0；limit ＝ 0x100
迴圈：
    di == limit → 收工
    讀兩個 byte a、b（只前進 1）
    a != b → buf[di] ^= a；di += 80；（di ≥ 18160 就 −18159）
    a == b → 再吃一個 byte 當計數：
                 有 bit7 → 次數 ＝ 低七位
                 沒有   → 再吃一個，次數 ＝ 大端兩位元組
             重複次數次：a 非 0 才 XOR；di += 80；換欄
             **run 跑完之後 limit ← 0x50**（單一 byte 的路徑不動它）
```

`limit` 的規則照 `041F:024B` 逐條寫（`docs/re/108`）。

驗算三條，全部通過：374 格的長度逐一相符、整份檔案吃光一個位元組不差、
累加的 XOR 在第 97–102 與第 244–251 格整個歸零（場景之間的黑幕）。

**第 0 格逐位元組對過原版**（`TestIntroFirstFrameMatchesOracle`）：
收據 `introseq` 錄到的 12 筆寫入——從 di ＝ 9,406 起每次 +80，
值 `C0 80 20 30 70 10 30 08 14 0C 02 06`——與解碼器產生的完全相同，
而且 plane 0 的其餘 18,148 個位元組都是 0。

## 畫在哪（confirmed）

`OPEN.EXE` 用 mode 10h（640×350×16）。解好的四個 plane 由四趟
`rep movsw`（`CX ＝ 0x2378`）搬進 `A0000 + 0x1310 + 頁`，頁在 `0` 與
`0x6D60` 之間交替（雙緩衝）。

```
0x1310 ＝ 4,880 ＝ 61 列 × 80
```

**640×227 的畫面畫在頁面的第 61 列**——垂直置中。逐一試 y 位移量過，
61 是明確的峰值。remake 照這條：`screen.IntroPage`
（`TestIntroPagePlacesImageAtRow61`）。

## 調色盤（confirmed）

`BU16IBM.RGB` 裡的值只有 0–15，**乘 4 才是 VGA DAC 的 6 位元值**。
與收據 `introvram/pal.bin` 的 48 個位元組逐一相符（`docs/re/110`）。
形狀是十六階亮度梯：G ＝ B ＝ 色號，偶數色號的 R 少一階，略偏青。

remake：`screen.IntroPalette`（`TestIntroPaletteMatchesOracle`）。

## 一格多久（confirmed）

`OPEN.EXE` 進場時把 PIT 除數改成 `0x0800`（離場寫回 0），所以動畫
期間計時器是 1,193,182 / 2,048 ≈ 582.6 Hz。解碼器入口四個一組
（四個 plane ＝ 一格），組與組的間隔是計時器驅動的：`-tick 20000` 下
量到的步數是 **1,500,000 的整數倍**，換 `-tick 10000` 步數跟著減半。

```
75 × 2048 / 1193182 ≈ 128.7 ms ≈ 每秒 7.77 格   （格 0–348）
77 × 2048 / 1193182 ≈ 132.2 ms ≈ 每秒 7.57 格   （格 350–373）
```

remake：`screen.IntroFrameIntervalAt`，由 `Game.Tick(d)` 推進
（`TestIntroAdvancesOneFramePerInterval`）。**不讀牆上時鐘**，
顯示層把每格的長度傳進來，所以同一串 `Tick` 重現同一串畫面。

前段使用 75 刻、尾段使用 77 刻；格 102、247、350、351 與每趟尾段
接縫的停頓也照 `docs/re/283` 的量測表接上。這些停頓的原始儲存位置仍是
`unknown`，程式碼保留量測常數並以收據測試鎖定，不把它們冒稱成已解出的
遊戲資料表。

### 整段的逐格時程（confirmed，`docs/re/283`）

把 421 組解碼呼叫全部量出來（收據 `introfull`，
`-regs-at 041F:024B,041A:0035 -regs-max 2000 -steps 1000000000`）之後，
整段動畫只有四個數字：

```
格 0 → 348      一格 75 刻（≈128.7 ms，約 7.8 fps）
  └ 格 102 前停 336 刻（≈577 ms）      ← 落在 97–102 那段全黑
  └ 格 247 前停 2,236 刻（≈3.84 秒）   ← 落在 244–251 那段全黑
格 349          原版從來沒有解過（見最後一節）
（四個 plane 緩衝區清成 0）
格 350 → 373    一格 77 刻（≈132.2 ms）；格 350 前停 2,850 刻、
                格 351 前停 1,798 刻（只有第一趟有）
（每趟之前再清一次緩衝區）格 350 → 373 再跑兩趟，接縫停 1,240 刻
```

第一趟 0 → 373 是 **34,864 刻 ≈ 59.8 秒**；含尾段三趟共 **40,886 刻
≈ 70.2 秒**。那兩處停頓的長度存在哪裡、尾段為什麼跑三趟，都還沒查。

`screen.IntroFrameIntervalAt` 依播放格索引重現前段、尾段與五個量到的停頓。

## 接進玩家路徑（remake 決定）

- `bootstrap.Load` **不接**動畫；要動畫的入口自己呼叫
  `bootstrap.LoadIntro`。動畫排在主選單前面，接上去整條輸入序列就
  往後位移一格畫面，而對拍收據與 README 的截圖腳本都是照沒有動畫的
  路徑寫的。
- `cmd/gin3` 預設開（`-intro=false` 關），走 `-script` 時自動不開。
- 三個素材缺任何一個就整段跳過，不是錯——玩家自備的原版目錄不保證完整。
- 左鍵、右鍵、任何按鍵都跳過；421 個玩家可見格播完自己進主選單。
- **畫面尺寸**：原版這一段是 mode 10h（640×350），remake 的畫布固定
  640×480（mode 12h），兩者對不起來。remake 把整頁垂直置中
  （`IntroScreenTop ＝ 65`），加上頁面內的第 61 列剛好是第 126 列，
  與「227 列的畫面在 480 列裡置中」相同。這是 remake 自己的決定，
  沒有可以對拍的原版狀態。

## 原版的播放順序（confirmed，`docs/re/283`）

原版前段照檔案順序播第 0、1、2…348 格；第 349 格不顯示，之後
350–373 播三趟。先前記的「第 1–116 格從來沒被解過」是執行器造成的：那份收據錄在 `4732181` 之前的 dosgolem 上，
而那一版子行程結束時不釋放 MCB、把 DOS 的空間表寫壞（`docs/re/270`），
兩個 64 KB 讀取緩衝因此疊在一起。修好之後量到的是 `175C:001E` 與
`275D:0016`，相差 65,544 bytes，互不相干。

remake 以 `asset.IntroPlaybackDecoder` 重現這個玩家可見序列；每趟尾段
開始前清除四個 plane。`docs/re/283` 在 48 個時點各倒一份 640×350 的
色號陣列，格 0–348 與尾段抽樣**每一個都是 224,000 個位元組全部相同**。

實作前的差異有兩處，現在都已接上：

1. **第 349 格原版不播。** 第 23 塊裝得下 11 格（339–349），但載入器的
   每塊格數表第 23 筆寫的是 10，解碼器照表遞減就換手，於是第 349 格永遠
   不會被解。（`docs/internals/19` 記的「回算 11、表上 10」就是這一筆。）
   那一格相對第 348 格改 **748 個像素**，播出來看得到。
2. **進尾段之前，四個 plane 緩衝區被清成 0。** 清的是載入器自己
   （`0349:056B`），而且尾段每跑一趟就清一次——XOR 累加沒有反向操作，
   不清的話上一趟的內容會疊進去。**實作前的 remake** 不清，所以第 348 格那艘
   戰艦會從標題圖底下露出來，尾段每一格差 **5,657 個像素**，全部落在
   `(246,113)–(416,235)`。

把這兩條加上去之後，尾段 7 個時點也全部逐位元組相同；
`TestIntroPlaybackMatchesDosgolemReceipts` 會在本機收據存在時逐位元組核對。
**其中只有「清緩衝」是必要的**：清了之後尾段從零累加，第 349 格有沒有 XOR
進去都被清掉了——只加清緩衝、不跳第 349 格，尾段那 7 個時點一樣全中
（`docs/re/283`）。跳不跳第 349 格影響的是**它自己那一格會不會被播出來**。

## 整段對拍（CONFORMED）

採用原版方案：前段顯示 0–348、略過 349，尾段 350–373 重播三趟，
每趟開始前清除四個 XOR plane，並套用 `docs/re/283` 量到的逐格時程。
`asset.IntroPlaybackDecoder` 與 `screen.IntroFrameIntervalAt` 已接入正常
玩家入口；可重生的收據存在時，`TestIntroPlaybackMatchesDosgolemReceipts`
會核對前段與尾段抽樣的 640×350 色號陣列。

尾段趟數與五個長停頓的原始資料來源仍是 `unknown`。這不阻擋目前的
玩家可見 parity：它們是 dosgolem `2e9dd3b` 收據量出的明確行為常數，
而非未經證據的猜測；若日後執行器或原版證據改變，必須重新產生收據並
重驗本規格。
