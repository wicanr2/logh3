# 046：戰場小地圖下方的格表殘留

狀態：**READY**（2026-09-14 證據審查完成）

## 玩家可見契約

戰場小地圖仍是 `(480,75)`、`128×128`，最後一列是 `y=202`。原版在其正下方
的 `y=203` 另留下一列固定的色號 1／3 圖樣；remake 要重現這列，但不得把它
算進小地圖尺寸、地形取樣或命中區域。

以色號 1 為 1、色號 3 為 0，由左至右每八像素一個位元組，固定遮罩是：

```text
CE CE C5 CE C5 CE C5 CE E5 CE E5 CE E5 CE C5 CE
```

遮罩為 1 的像素寫色號 1；為 0 的像素保留面板既有的色號 3。

## 原版來源與裁決

- **已證實**：dosgolem `e0b6a03` 收據 `s3strip-write-calls` 在該列的
  `x=480` 看到 `2376:10EA`、`110B`、`1132` 各寫入七次；同一畫面重畫七次。
- **已證實**：呼叫鏈是格表重畫 `341B:00EE → 2376:0E0D → 10B7`；輸入是
  空白內容格 `DX=0x0020`、顏色 `CX=0x0097`，不是小地圖地形資料。
- **已證實**：`10B7` 的三趟合成列數是 19／20／20；原版的 20 列寫入越過
  小地圖下緣後，只有 `y=203` 沒被後續的 128×128 小地圖覆蓋。
- **已證實**：`s3ai6` 與 `s3fight` 的 128 像素完全相同；它不是 RNG 或局面資料。

因此 production path 採獨立的固定殘留繪製函式。這是刻意保存原版繪圖瑕疵，
不擴張小地圖資料格式，也不讓規則層依賴它。

## 驗證

`TestBattleMatchesOracle` 不再排除 `y=203`；唯一允許排除的是 dosgolem 所畫的
滑鼠游標。整個戰場畫面其餘像素必須與 `s3ai6` 收據相同。
