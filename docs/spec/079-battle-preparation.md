## READY：共用行星補充

原版 `1AAB:0D9F`：給出的艘數 `n` 是滿編缺額與該種類行星庫存的較小值。
現有艘數／庫存公式保留，補足遺漏的修理上限回寫：

1. `n == 0` 時所有欄位不變。
2. 現有艘數增加 `n`，32位行星庫存減少 `n`。
3. 修理上限 = `min(uint16(原修理上限 + n), 滿編艘數)`。

**已證實**：寫入鏈 `0E10／0E1B／0E33／0E3F／0E4A` 保存於分級索引，
雙跑滿補、部分補、無庫存、已滿與種類5的欄位相同。
主要樣本 `Ships=50, FullShips=100, RepairCap=75`，庫存100／20／0；
16位回繞依原指令，不把非法合成狀態外推成正常玩法。
兩側比較條件事前固定種子 `0x12345678`，此規則不消費亂數。

垂直鏈：原始78bytes的 `+08／+0A／+0C` → `BattleUnit` → `PlanetReplenish` →
行星選單「補充」正式點選 → `Slot.ApplyBattleResult` → SHIP存讀；
行星82bytes的 `+20+4kind` → `PlanetStock` → `ApplyBattlePlanets` → PLANET存讀。
不新增欄位或格式；空指標／非法艦種沿用既有安全返回。

戰後回寫必須保存既有 `BattleUnit` 的修理上限 `+0C`、飛彈32位 `+0E`、
戰機32位 `+12`，即使艘數沒變也要寫。原版受控補給／補充直接改同一筆艦艇記錄，
原版存檔保存整份池（內部事實30／64）；不得只將 `+08` 寫回後遺失資源。
現有 `ApplyBattleResult` 回傳的艘數變更筆數維持原義，不新增正式中途戰場保存聲明。

驗收：直接核對原版保存的輸出欄位，測試不另算預期公式；正式Click檢查修理上限，
補池回寫／正式存讀抽樣、標準產品套件與正常GUI入口。
常式收據、合成UI局面及正常GUI分別標範圍，不以任何一項宣稱完整第一階段same-state完成。

## READY：自動候選排序，完整階段尚未接線

證據：[研究368](../re/368-battle-preparation-sort.md)、
[固定75案](../internals/data/battle-preparation-sort.json)與分級指令索引。
原版身份／工具／切段雜湊與位址空間均在研究368；正式八步的入口閘門維持規格062。

輸入為保留原始列序的候選池索引、各艦艇的艦隊byte／分隊byte、有效來源遠指標。
原版`1930:0510`／`1AAB:04BD`比較：同艦隊依分隊序；不同艦隊優先來源艦隊，
其他艦隊回0。`3C6A:000D`以梳狀排序處理，不能改成穩定排序或艦隊槽號序：

1. `n <= 1`原樣返回，不讀比較器；`gap=n`。
2. 每輪`gap=floor(gap*10/13)`；零改1，9／10改11。
3. 沿清單首筆起比較相隔gap的元素，只在回傳正數時交換。
4. 直到gap為1且本輪沒有交換才返回。

輸出只重排索引，不改艦艇欄位或消費亂數。驗收必須核對原版完整候選輸出序列，
包括平手換位、大小0／1、9／10轉11與55筆案例；不能只檢查來源艦隊排在前面。
此子範圍不自行接`AdvanceBattleTurn`，也不以孤立排序測試宣稱垂直鏈完成。

行星沿用來源狀態的已證實部分：自動補給逐筆更新A42E，故取最後一筆艦艇；
自動修理只在種類6更新A440，沒有種類6時保留先前指標。
必須保留池身份並讀其當前艦隊；不能只快取來源艦隊號。
首次主選單零指標、三個寫入端及池槽活指標已由研究369補證；
**換戰場／重新開始／讀檔重設仍DRAFT**，不得在正式程式猜補生命週期。

## READY：已量測來源、結果面板與士氣續接契約

證據：[研究369](../re/369-battle-preparation-lifecycle.md)、
[六案及六組原版雙跑](../internals/data/battle-preparation-lifecycle.json)、
[十五項分級索引](../internals/data/battle-preparation-lifecycle-semantics.json)。
這是完整第一階段的已解子範圍；不授權尚未知的重設或直接宣稱整步完成。

- 正常開機主選單的兩個來源都是`0000:0000`。原版零指標仍解參照實體位址1，
  固定dosgolem版本該byte為0；只確認此執行器狀態，不外推所有真實DOS。
  typed表示必須區分「未指向池」與「池槽0」，不能用索引0假冒零遠指標。
- 手動運補`1930:05EC`及修理`1AAB:0583`在找候選之前寫來源；
  沒有候選仍不豁免來源更新。電腦前置修理`1AAB:0190(faction)`，
  只在種類6且陣營吻合時寫修理來源。
- 保留的有效來源以池身份解參照目前艦隊byte，不快取艦隊號；
  已有來源且本次無種類6，修理不重設。兩次常式診斷與明示池槽重用證實此條。
- 人類實際獲得補給時`1930:0AA2`刷新右側結果面板，實際獲得修理時`1AAB:08FB`同理。
  source／target、艘數、來源剩餘庫存、目標容量缺額依原始欄位顯示；
  已量測補給畫面顯示負缺額及紅字，修理畫面顯示艘數70／損壞艘數5。
  這兩個函式沒有本身的按鍵確認等待，不能改接需要玩家確認的報告佇列。
- 修理結束才執行`1261:000B(1)`。士氣報告沿既有規格059的戰場臨時視窗，
  等待定時或按鍵；報告關閉前不得回復防衛力或進入移動。
  續接只做防衛力與後續階段，不重新補給／修理／亂數初始化。

驗收須保存面板完成幀及第一階段結束幀；首尾seed相同，六組原版完整記憶體／畫面／色盤雙跑相同。
正式垂直鏈仍須原始池身份→typed來源→回合／手動規則→右側UI／士氣續接→戰後回寫→存讀。
現有原版收據只證明契約，不能代替尚未實作的remake驗收。
