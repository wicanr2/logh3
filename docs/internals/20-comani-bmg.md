# `COMANI.BMG` — 戰鬥動畫封存檔

資料：`docs/internals/data/comani-bmg.json`
產生：`tools/py.sh tools/scripts/bmg_export.py`
證據等級：目錄結構 **confirmed**（位移可用累加逐筆驗證）；每一段的編碼 **未解**
——**不是開頭動畫那套 XOR-RLE**，253 段一段都吃不光
（[`docs/re/46`](../re/46-comani-not-intro-codec.md)）。

## 目錄

```
+0      u16      第一段資料的位移（2540）
+2 起   每筆 10 bytes：
          +0  char[4]  名稱
          +4  u16      長度
          +6  u32      位移
```

**253 筆**，目錄在 2532 結束，之後 8 bytes 補到 2540。驗證方式是把每一筆
的「位移 ＋ 長度」拿去比下一筆的位移——253 筆一路接得起來，中間沒有洞。
檔尾還有 1,732 bytes 不在目錄裡，內容看起來與其他段同型（第 254 段）。

## 名稱的結構

四個位元組拆成三段：

| 位置 | 值 | 猜測 |
|---|---|---|
| `[0]` | `E`／`F`／`P` | 陣營或艦種大類 |
| `[1]` | `A`–`Z` 的一部分，以及 `0xB1`–`0xC0`、`0xDD` | 單位代碼（不全是 ASCII）|
| `[2..3]` | `AB`／`AF`／`AM`／`D0`／`D1`／`D2` | 同一個單位的六個畫格 |

六個畫格 × 42 個單位 ≈ 253 筆，數量對得上。

## 段頭的欄位邊界（量出來的，語意未解）

「開頭幾個位元組每段都不一樣」是錯的觀察——**逐位元組統計 253 段**之後，
邊界很清楚：`byte[3]`、`byte[5]`、`byte[11]` 在 253 段裡**全部是 0**，
那是三個 u16 的高位元組。

| 位移 | 型別 | 值域（253 段）| 樣子 |
|---|---|---|---|
| `+0` | byte | 0（247 段）；其餘 15／24／20／128 各一 | 旗標？ |
| `+1` | byte | 0–255 散開 | ？ |
| `+2` | u16 | **4–14**，5 佔 167 段、6 佔 58 段 | 計數／尺寸 |
| `+4` | u16 | **只有 0（53 段）與 1（200 段）** | 旗標 |
| `+6` | u16 | 多數 < 256（`byte[7]` 有 196 段是 0）| ？ |
| `+8` | u16 | 散開到 0x1200 以上 | ？ |
| `+10` | u16 | **1–12** | 計數 |

「只有 0 與 1」與「高位元組全是 0」這兩件事各自都不可能是巧合，
所以 `+2`／`+4`／`+10` 是真的欄位，不是壓縮資料的頭幾個位元組。

熵不足以分辨有沒有壓縮：三段抽樣是 5.19／6.28／5.33，
而已知**壓縮過**的 `FACE.AMG` 是 5.54、已知**沒壓縮**的 `GRAPH.IMG` 是 6.03。

## 每一段的編碼未解

拿上面量出來的欄位當寬高、再套 `.AMG` 的狀態機（四個 plane 共用、
「兩個 byte 相同」是重複組）試過七種組合
（`w@2 h@10`、`w@10 h@2`、`w@2 h@6`、`w@6 h@10`、`w@8 h@10`，
資料起點 12／14／16）——**剛好吃完整段的數量是 0/253**（`w@2 h@6` 一段）。
`.AMG` 那套不是它。

遊戲在開機時
就把整個檔案打開（`docs/re/03` 的開檔清單有它），但目前走得到的畫面
都沒有用到它——要先能進到戰鬥畫面，才有原版畫出來的東西可以對。
