# FACE.AMG — 人物頭像（.AMG 圖庫格式）

證據等級：**confirmed**（反組譯原版解碼常式 ＋ 與原版畫面逐像素相同）
資料：`docs/internals/data/face-amg.json`
實作：`internal/asset/amg.go`、測試 `internal/asset/amg_test.go`
素材：`workplace/assets/face/face-NN.png`（83 張，一次性產物，不進 Git；
以 `tools/py.sh tools/scripts/amg_export.py` 從自備原版重建）

`FACE.AMG` 本身 263,568 bytes，SHA-256
`514c1ea9b2c63b85f4ecf1b9d473f46691dc70140272027d8e62fd16d768e0d4`。

## 檔案結構

```
0x0000  索引表：N 筆 × 6 bytes     N ＝ 第一筆的位移 ÷ 6
        +0 u16  該張的位元組長度
        +2 u32  檔案內位移
0x01F2  影像資料（第一筆的位移剛好等於索引表長度，兩者前後相接）
```

`FACE.AMG` 有 83 筆，每張影像 80 × 100 像素、4 位元色號。

## 每張影像

```
+0   u32  固定 1
+4   u32  size − 6
+8   u16  直行數 w（每直行 8 像素）      FACE.AMG 全部是 10 → 80 像素寬
+10  u16  每直行的 word 數 h（每 word 2 列） 全部是 50 → 100 列
+12  …    壓縮的 planar 資料
```

**標頭只有 12 bytes，`+12` 就是資料的第一個位元組**，不是旗標。判準是
「從哪裡開始解才會剛好用完索引表寫的長度」：從 `+12` 起 83 / 83 全中，
從 `+13` 起 0 / 83（[`../re/271`](../re/271-face-amg-index-is-the-admiral-index.md)）。
用同一套狀態機的 `ANI_PNL?.A98`（[`37-ani-pnl-a98.md`](37-ani-pnl-a98.md)）
一直寫的就是 `+12`。

## 壓縮：直行掃描 ＋ 相等即重複

原版的解碼常式在 `GIN3PS.EXE` `348A:02F9`（定位方法見 §「怎麼找到的」）。
進到它之前先過 `348A:01DC`：那一支設好目的位址（`3A8D:003A` 換算，見
§「落點怎麼算」）、跳過緩衝區前 8 個 bytes 的標頭、再讀 `+8`／`+10` 的
w／h 進 `dh`／`dl`，然後才落到這個迴圈。

```
02F9  AD           lodsw              ; 取兩個 byte
02FA  38 E0        cmp al,ah
02FC  74 13        je  0311           ; 相等 ⇒ 重複組
02FE  26 88 05     mov es:[di],al     ; 同一個 x 的第一列
0301  03 FB        add di,bx          ; bx ＝ 80（mode 12h 每列位元組數）
0303  26 88 25     mov es:[di],ah     ; 相鄰的第二列
0306  03 FB        add di,bx
0308  FE CA        dec dl             ; 這一直行還剩幾個 word
030A  75 ED        jnz 02F9
030C  E8 1F 00     call 032E          ; 走完一直行 → x+1
030F  EB E8        jmp 02F9
0311  8A 24        mov ah,[si]        ; 重複組：值對 ＝（al, 下一個 byte）
0314  8A 0C        mov cl,[si]        ; 次數
0319  26 88 05     mov es:[di],al     ; 同樣兩列一組，重複 cx 次
```

換直行與換 plane（`032E`）：

```
032E  mov di,cs:[02B7] / inc di       ; 下一個直行
0339  mov dl,cs:[02B4]                ; 重設每直行的 word 數
033E  dec dh / jnz ret                ; 還有直行 → 繼續
0343  mov di,cs:[02B5]                ; 直行用完 → di 回到最初起點
034D  mov dh,cs:[02B3]                ; 重設直行數
0354  mov al,cs:[02B9] / shl al,1     ; map mask 左移 ＝ 下一個 plane
0361  out dx,al                       ; 03C5h
0362  test al,10h / jz ret            ; 還沒到第 4 個 plane → 繼續
0368  inc sp / inc sp / ret           ; 四個 plane 做完 → 丟掉返回位址收工
```

**四個 plane 共用同一個狀態機**：重複組的次數可以跨過 plane 邊界，
原版在那裡只是換 map mask 再回到同一個迴圈。把每個 plane 當成獨立一段解，
跨界的那幾個 word 會落在錯的位置——症狀是人臉看得出來、輪廓也對，
但有 1355 個像素的 **bit0** 不同（其他三個位元全對），
看起來很像色盤或執行器的 planar 寫入有問題。

## 83 格裡有 82 個人

| 編號 | 內容 |
|---|---|
| 0 – 81 | 提督 0 – 81 的人像，一人一張（83 張的像素兩兩相異，沒有共用圖）|
| 82 | 沒有人物：整張單色 9（外框那個深青），44 bytes ＝ 12 標頭 ＋ 8 組重複組 |

`KEIREKI.DAT` 的形狀相同——83 筆位移、最後一段長度為 0
（[`15-keireki-dat.md`](15-keireki-dat.md)）。兩個檔都是 83 格、最後一格空著。

八張（18、31、33、34、35、37、38、39）的**外框比其他 74 張往下挪一列**：
第 0 列是色 9、第 1 列才是色 6，一般張的第 0 列就是色 6。除了外框的第 1 列
與第 96 列，遮罩完全相同。挪一列讓 `+12` 剛好是 `0xFF`，先前因此被當成
「空白旗標」——那八張是完整的人像。

### 二、制服的分界落在 39／40（一次覆蓋 82 格）

同盟制服用色號 4（`#306100`），帝國制服不用。整張數色 4 的像素：
編號 0–39 是 0（只有第 10、18、34、36 張各有 6–10 點雜訊），
40–79 是 208–1304，80–81 是 0。

`ADMIRAL.DTX` 的 `+1`（陣營）切在同一個地方。**兩個例外自己解釋自己**：
第 80、81 段人物傳寫的是梅爾卡茲與舒奈德——帝國軍名將與他的副官，
利普休達特戰役後逃亡到同盟、以客座提督身分任職，所以在同盟的名冊上
穿帝國制服。同一組例外在提督記錄裡也看得到：82 筆的 `+0` 全是 `0xFF`，
只有第 80、81 筆是 `0xFE`。

### 三、人物傳寫的長相對得上像素

`0` 金髮、`1` 火紅髮、`2` 蜂蜜色髮、`3` **右眼黑左眼藍**（畫面內唯一的
藍色像素在他的左眼）、`34` 鬍鬚、`49` 淺黑膚色、`74` 兩眼虹膜是色 4 的綠
——都與同編號的人物傳字面相符。第 3 張的左右不對稱最有力；第 34 張是
先前被誤標成「空白」的八張之一。

### 四、頭像編號不是提督記錄裡的欄位

`ADMIRAL.DTX`／`DT8` 的 28 個位移，沒有任何一欄的值等於記錄索引，也沒有
一欄等於陣營內序號。繪圖端拿到的編號只能是索引本身。

### 五、繪圖端的程式碼直說（`docs/re/272`）

畫頭像的入口是 `3958:0215`（簽章
`55 89 E5 80 7E 06 FF 75 04 C6 46 06 52 8A 46 06 3C FE 74 10`）。三個參數都是
byte：`(編號, 行, 列)`。它對編號只做兩件事，其餘原樣往下傳：

```
0218  80 7e 06 ff     cmp  byte [bp+6],0FFh
021E  c6 46 06 52     mov  byte [bp+6],52h     ; 0FFh → 82（那一格空白）
0225  3c fe           cmp  al,0FEh
0227  74 10           jz   0239                ; 0FEh → 不重載，畫緩衝區裡現有的
0232  9a 01 04 2e 33  call far 332E:0401       ; 其餘：讀 FACE.AMG 第 n 筆
024D  9a dc 01 8a 34  call far 348A:01DC       ; 再畫出來
```

`332E:0401` 只是把檔名 `ds:6AAF` ＝ `face.amg` 補上，真正讀檔的是通用常式
`332E:0B8E`（函式內簽章 `8A 46 5C 30 E4 B9 06 00 F7 E1 89 C3`）：

```
0BE3  8a 46 5c        mov al,[bp+5Ch]      ; 編號（byte）
0BE8  b9 06 00        mov cx,6
0BEB  f7 e1           mul cx               ; n × 6
…     lseek(n×6) → read 6 bytes → lseek(該筆位移) → read(該筆長度)
```

**`n × 6` 直接當索引表的位移，中間沒有轉換表。** 提督詳細資料那個呼叫端
（線性 `0x0D98B`）更短：同一個區域變數先 `× 28` 加上提督表 `ds:B77C`
去印欄位，再原樣推給 `3958:0215` 當頭像編號——**「第 n 張」與「第 n 筆」
在同一個基本區塊裡是同一個值。**

`0xFF` 那條特例與資料對得上：提督索引的「沒有這個人」在資料裡寫 `0xFF`
（`ADMIRAL.DT*` 的 `+0x07` 副官欄、艦隊記錄的 `+0x04`），碰到就畫第 82 張。
所以 83 格裡那一格空白是**設計上的空位**，不是多出來的一格。

### 落點怎麼算

`3958:0215` 的參數 2／3 是「行」與「列」，經 `3A8D:003A`（入口簽章
`8A E1 32 C0 8B D8 D1 EB D1 EB 03 D8 8A CD 32 ED 03 D9 81 C3 80 0C CB`）
換成 mode 12h 的位元組位移 `列 × 320 ＋ 行 ＋ 3200`，也就是

```
x ＝ 行 × 8
y ＝ 列 × 4 ＋ 40
```

兩個量過的落點對得上：易主報告 `(0x44, 0x23)` → `(544, 180)`
（[`../spec/034`](../spec/034-region-flip-report.md)）、提督詳細資料
`(0x38, 0x0F)` → `(448, 100)`（[`../spec/012`](../spec/012-admiral-detail.md)）。

## 雜湊怎麼引用

`face-amg.json` 每格有兩個雜湊：

- `sha256_pixels` — 解碼後 80 × 100 個色號位元組的 SHA-256。**引用以它為準**，
  它只看解碼結果，換一個 PNG 編碼器或 zlib 版本都不會變。
- `sha256_png` — `workplace/assets/face/face-NN.png` 的 SHA-256，只在同一個
  zlib 版本下重現。

人物傳每篇底下掛的是 `sha256_pixels`。**要查手上的 `FACE.AMG` 對不對，
不必逐格算**：跑一次 `tools/py.sh tools/scripts/amg_export.py`，再看
`git diff docs/internals/data/face-amg.json` 有沒有東西——沒有就是 83 格
的像素全部相同。這也是這兩支產生器唯一的驗收方式（同一份輸入重跑，
輸出逐位元組相同）。

## 怎麼找到的

在 dosgolem 開 `-vram-sites`（統計「誰在寫視訊記憶體」），跑兩次不同步數
再相減：頭像畫出來那一段新增的寫入者只有 `348A:02FE/0303/0319/031E`
四處，合計 4000 次寫入 ＝ 4 plane × 10 × 100。接著 `-peek` 取出那一段
位元組直接讀。

先前在壓縮位元組上猜格式（PackBits、三種位元組 RLE、96 組 LZSS／LZ77 參數、
nibble RLE）全部落空——**判準都用「83 張要解出同一個長度」，沒有一組通過**。
差別在於：猜格式是在搜尋空間裡亂走，找繪圖常式是直接問「誰畫的」。

編號與人物的對應怎麼查出來的，記在
[`../re/271`](../re/271-face-amg-index-is-the-admiral-index.md)；繪圖端那三支
常式怎麼切段反組譯出來的，記在
[`../re/272`](../re/272-face-index-is-the-caller-argument.md)。
