# 中文字型：`GRAPH.IMG`

機器可讀版本在 [`data/font-graph-img.json`](data/font-graph-img.json)；
點陣圖集在 `workplace/assets/font/`（本機，gitignore）。

## 結論（confirmed）

`GRAPH.IMG`（419,850 bytes）是完整的中文點陣字型，**內容是倚天中文系統的
字型，逐位元組相同**：

| 區段 | 位移 | 字形數 | 內容 |
|---|---|---:|---|
| 半形 | `0x0000`–`0x0F00` | 256 | 8×15，等同倚天 `ascfont.15`（3,840 bytes 全同）|
| 全形符號 | `0x0F00`–`0x4632` | 471 | 16×15，Big5 `0xA1`–`0xA3` 三個前導位元組 |
| 假名／西里爾／框線 | `0x4632`–`0x6996` | 302 | 16×15，字碼對應**未確認** |
| 漢字 | `0x6996`–結尾 | 13,094 | 16×15，等同倚天 `stdfont.15`（392,820 bytes 全同）；`0xA440`–`0xC67E` 與 `0xC940`–`0xF9FE` 連續存放，中間 408 個碼位沒有存 |

全形字形一律 **16 寬 × 15 列、每列 2 bytes、高位在前、bit15 在最左**，
一個字 30 bytes。

## 索引公式（confirmed）

```
big5_index(code) = (lead - 0xA1) * 157
                 + (trail <= 0x7E ? trail - 0x40 : trail - 0xA1 + 63)

i = big5_index(code)
if i >= 6280: i -= 408          ← 次常用字要補這一步，見下

半形     offset = code * 15
全形符號 offset = 3840  + i * 30              （0xA140–0xA3FE）
漢字     offset = 27030 + (i - 471) * 30      （0xA440 起）
```

`471` 是 `big5_index(0xA440)`，也就是漢字區的起點序號。

### 次常用字的斷層（confirmed）

Big5 的常用字止於 `0xC67E`，次常用字從 `0xC940` 開始，中間
`0xC6A1`–`0xC8FE` 那 408 個碼位（前導 `C6` 的 94 個 ＋ `C7`、`C8` 各 157 個）
是造字區與符號區，**字型檔沒有存**。檔案裡 `0xC67E` 的下一個字形直接就是
`0xC940`，所以 `big5_index` 算出來的序號要扣掉這 408。

`6280` ＝ `big5_index(0xC940)`。不扣的話整個次常用字區偏
408 × 30 ＝ 12,240 bytes，而且**畫得出來**——畫出來的是別的字，
不是空白也不是亂碼。這種錯只有拿原版畫面對拍才看得出來。

> 怎麼確認的：從 `settings1e` 收據裡把「璐」（`0xED69`）的點陣抽出來
> （x304–319、y122–136，前景色 7），打包成 30 bytes 拿去 grep
> `GRAPH.IMG`，命中位移 **359,850**；未修正的公式算出 372,090，
> 差 12,240 ＝ 408 × 30。

## 怎麼驗的

三條互相獨立的證據都指向同一個答案：

1. **點陣對得上**：主選單九個字（帝國同盟對戰取進度）從 dosgolem 的
   framebuffer 抽出來，與公式算出的位移取出的 30 bytes **逐位元吻合**。
2. **機制對得上**：probe 的檔案存取記錄顯示遊戲每畫一個字就
   `seek` 到那個位移再讀 30 bytes，九次的偏移與公式算出來的**完全相同**：

   ```
   #25777538 seek Graph.img → 0xF780   #25777542 read 30 bytes   ← 帝
   #25781661 seek Graph.img → 0x9042   #25781665 read 30 bytes   ← 同
   #25786791 seek Graph.img → 0x2554E  #25786795 read 30 bytes   ← 戰
   ```
3. **外部對照**：漢字區與倚天 `stdfont.15` 的 13,094 個字形逐位元組
   100% 相同；半形區與 `ascfont.15` 3,840 bytes 100% 相同。

## 存取方式（confirmed，而且是個陷阱）

**字型不整份載入。** 開機時只讀開頭 1,920 bytes（前 128 個半形字形），
之後每要畫一個中文字才 seek 過去讀 30 bytes。

所以**在記憶體或 EMS 裡搜字形點陣一定是空的**——實測跑到主選單之後，
1 MB 位址空間與全部 EMS 頁都找不到任何一個字的點陣。那不代表字型不在，
代表它從來沒有以整塊形式存在過。要追這類「按需取用」的資料，看檔案存取
記錄，不要去搜記憶體。

## 還沒解出來的

`0x4632`–`0x6996` 這 302 個字形（平假名 → 片假名 → 西里爾大小寫 → 框線 →
圈號 → `㊣No.正`）的字碼對應**未確認**。

已排除的假說：「以 Big5 `0xC6A1` 為起點連續存放」——依該假說算出的
`ジ`(`0xC7B4`) 位置實際上是西里爾大寫。

可行的測法：`ENDING.EXE` 的版權行會顯示 `德間ジャパン．キティフィルム`，
把遊戲跑到結局畫面，用 probe 的檔案存取記錄看它 seek 到哪個偏移，
一個字就能定出基準。

## 對 remake 的意義

- 字型是**倚天的**，不是這款遊戲自製的。重製時要嘛自備字型，要嘛沿用
  系統字型，不能假設 `GRAPH.IMG` 的內容可以隨產品散布。
- 半形 8×15、全形 16×15 是版面的硬約束：欄距 16、列距 20（主選單實測）。
- 文字一律 Big5；日文假名走 ETen 擴充區（見
  [`04-text-windows-and-big5.md`](04-text-windows-and-big5.md)）。
