# `IBM16.350` ＋ `IBMFLS16.350` — 開頭動畫

證據等級：影格切分、壓縮語法與**位元圖的走法**都 confirmed
（[`docs/re/36`](../re/36-ibm16-token-grammar.md)、
[`docs/re/72`](../re/72-intro-decoder-solved.md)）。
解碼器：`tools/scripts/intro_decode.py`、`tools/scripts/intro_frames.py`。

## 影格長度表（confirmed）

`IBMFLS16.350` 是 748 bytes ＝ **374 個 uint16**，每一個是一格的壓縮長度。
把它們加起來剛好 **1,764,911**，一個位元組不差，等於 `IBM16.350` 的大小。

```
前幾格：78, 79, 78, 77, 104, 126, 149, 199, 243, 289 …
最大 23,657，最小 20
```

所以開頭動畫是 **374 格**，`IBM16.350` 是把 374 段壓縮資料首尾相接。

`OPEN.EXE` 分段讀進來：每次填一個 64 KB 的緩衝區，**塞得下幾個完整影格
就塞幾個**，分界一律落在影格邊界上（`docs/re/71`）。緩衝區前 40 bytes
固定是檔案的前 40 bytes。

## 位元圖與走法（confirmed）

一格 ＝ 四個 plane，每個 plane 後面接一個分隔位元組。一個 plane 是
**80 × 227 ＝ 18,160 bytes**，token 解出來的位元組**一欄一欄往下** XOR
進去：

```
di += 80
if di >= 18160: di -= 18159      ← 換到下一欄
停止：di == limit（limit 一開始 0x100，第一次換欄後改成 0x50 ＝ 80 欄）
```

終止是**相等**不是大於等於——讀成 `>=` 的話一格只吃 21 個位元組
（`docs/re/72`）。

驗算：374 格每一格吃掉的位元組數與長度表逐一相符；累加的 XOR 在第
97–102 格與第 244–251 格整個歸零（場景之間的黑幕），四個 plane
共 72,640 個位元組全部是 0。

## 播放環境（confirmed）

`OPEN.EXE` 切到 **mode 10h（640×350×16）**，調色盤先讀 `BU16IBM.RGB`
（48 bytes ＝ 16 色 × 3），播到一半換 `TITSPT.RGB`（同樣 48 bytes），
配樂是 `OPEN_M.MDS`。

## 每一格的編碼（已解，以下保留當初排除的路）

不是 `.VO5`／`.AMG` 那套「相等即重複」——照那套解，各格產生的位元組數
差了兩個數量級（第 373 格會吐出 3,258,462 bytes，而一個 plane 只有 28,000）。

`OPEN.EXE` 與 `GIN3PS.EXE` 都被 GLUE 打包過，靜態搜不到解碼常式；
執行期在整個 1 MB 記憶體裡搜 `ENDING.EXE` 那段解碼碼的位元組
（`AC 26 88 05`、`8A F8 4A`、`26 88 05 03`）也全部沒有命中——
**是另一套編碼**，不是同一份程式碼搬過去。

## 繪圖端已經看清楚（confirmed）

`-vram-sites` 指出五個寫視訊記憶體的位置：

| 位置 | 次數 | 是什麼 |
|---|---|---|
| `0110:09E6` | 56,000 | 清畫面（`mov byte es:[bx+si],0`，四個 plane 一起開，跑滿 0xDAC0 ＝ 56,000）|
| `01E6:0206`／`0218`／`022A`／`0241` | 各 54,480 | 四個 plane 的 `rep movsw` |

搬運端的程式碼：

```
mov dx,3C4 / mov al,02 / mov ah,01 / out dx,ax    ; map mask ＝ plane 0
lds si, cs:[0012]                                 ; 來源 2527:0016
mov cx,2378h / cld / rep movsw                    ; 9,080 words ＝ 18,160 bytes
…plane 1／2／4 各重複一次，來源分別是 cs:[001A]、cs:[0016]
```

所以**解碼器寫的是 RAM 緩衝區**（`2527:0016` 與 `3277:0016`），
搬到 VRAM 只是最後一步。

## 記憶體佈局（confirmed）

| 緩衝區 | 位址 | 大小 | 內容 |
|---|---|---|---|
| A | `2527:0016` | 54,480 bytes | plane 0／1／2，三段各 18,160，連續擺 |
| B | `3277:0016` | 18,160 bytes | plane 3 |

一個 plane 是 18,160 bytes ＝ 80 × 227，搬到 VRAM 的目的地是
`A131:6D60`（線性 `A8070`，相對 VRAM 起點位移 32,880）——不是第 0 頁，
所以 `-dump-ega` 從位移 0 讀會看不到動畫（程式有寫 CRTC 的 3D4／3D5，
在換顯示起始位址）。

跑到第 95,000,000 道指令時，緩衝區裡是**稀疏的星空**：三個 plane 合計
8,952 個非零位元組，而且大多是 `0x01`／`0x80` 這種只有一個位元的值。

## 每一格的編碼：三種 RLE 都不對

把 374 格分別用三種「相等即重複」的變體解一遍，看解出來的長度會不會
收斂到定值（一個 plane 是 18,160、三個是 54,480）：

| 變體 | 前幾名的長度 |
|---|---|
| 次數 1 byte、為 0 時改讀 word | 288 ×12，其餘每格各不相同（9,061／589／461／34,434…）|
| 次數固定 1 byte | 288 ×12，其餘散在 4,400–4,700 |
| 次數固定 1 word | 246,044 ×12，其餘 19 萬–38 萬 |

**沒有一個收斂**。所以每一格不是整幀的點陣壓縮。

配合「緩衝區裡是稀疏的星空」與「格長從 78 一路長到 23,657」，
比較像是**向量／多邊形繪圖腳本**（由畫線常式寫進 RAM 緩衝區，
再整塊搬到 VRAM），不是圖片。要解得先把繪圖常式讀出來。
