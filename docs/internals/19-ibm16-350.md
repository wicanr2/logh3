# `IBM16.350` ＋ `IBMFLS16.350` — 開頭動畫

證據等級：影格切分 **confirmed**；每一格的編碼 **未解**。

## 影格長度表（confirmed）

`IBMFLS16.350` 是 748 bytes ＝ **374 個 uint16**，每一個是一格的壓縮長度。
把它們加起來剛好 **1,764,911**，一個位元組不差，等於 `IBM16.350` 的大小。

```
前幾格：78, 79, 78, 77, 104, 126, 149, 199, 243, 289 …
最大 23,657，最小 20
```

所以開頭動畫是 **374 格**，`IBM16.350` 是把 374 段壓縮資料首尾相接。
`OPEN.EXE` 也是分段讀進來的（一次約 65 KB），不是整包載入。

## 播放環境（confirmed）

`OPEN.EXE` 切到 **mode 10h（640×350×16）**，調色盤先讀 `BU16IBM.RGB`
（48 bytes ＝ 16 色 × 3），播到一半換 `TITSPT.RGB`（同樣 48 bytes），
配樂是 `OPEN_M.MDS`。

## 每一格的編碼未解

不是 `.VO5`／`.AMG` 那套「相等即重複」——照那套解，各格產生的位元組數
差了兩個數量級（第 373 格會吐出 3,258,462 bytes，而一個 plane 只有 28,000）。

`OPEN.EXE` 與 `GIN3PS.EXE` 都被 GLUE 打包過，靜態搜不到解碼常式；
執行期在整個 1 MB 記憶體裡搜 `ENDING.EXE` 那段解碼碼的位元組
（`AC 26 88 05`、`8A F8 4A`、`26 88 05 03`）也全部沒有命中——
**是另一套編碼**，不是同一份程式碼搬過去。

## 繪圖端已經看清楚（confirmed）

`-vram-sites` 指出五個寫視訊記憶體的位置：

| 位置 | 次數 | 是什麼 |
|---|---|---|
| `0110:09E6` | 56,000 | 清畫面（`mov byte es:[bx+si],0`，四個 plane 一起開，跑滿 0xDAC0 ＝ 56,000）|
| `01E6:0206`／`0218`／`022A`／`0241` | 各 54,480 | 四個 plane 的 `rep movsw` |

搬運端的程式碼：

```
mov dx,3C4 / mov al,02 / mov ah,01 / out dx,ax    ; map mask ＝ plane 0
lds si, cs:[0012]                                 ; 來源 2527:0016
mov cx,2378h / cld / rep movsw                    ; 9,080 words ＝ 18,160 bytes
…plane 1／2／4 各重複一次，來源分別是 cs:[001A]、cs:[0016]
```

所以**解碼器寫的是 RAM 緩衝區**（`2527:0016` 與 `3277:0016`），
搬到 VRAM 只是最後一步。

## 還沒解開的部分

對緩衝區下 `-watch` 在 3,000 萬道指令內沒有攔到寫入——執行器把
延遲迴圈照跑，動畫推進得很慢（第一格要到約 1,800 萬道指令才讀進來，
到 3,000 萬也才走了兩三格）。要抓到解碼迴圈得先讓它跑得夠遠，
或改用「跳過延遲迴圈」的方式。**這是下一步。**
