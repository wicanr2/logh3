# `IBM16.350` ＋ `IBMFLS16.350` — 開頭動畫

證據等級：影格切分、壓縮語法與**位元圖的走法**都 confirmed
（[`docs/re/36`](../re/36-ibm16-token-grammar.md)、
[`docs/re/72`](../re/72-intro-decoder-solved.md)）。
解碼器：`tools/scripts/intro_decode.py`、`tools/scripts/intro_frames.py`。

## 影格長度表（confirmed）

`IBMFLS16.350` 是 748 bytes ＝ **374 個 uint16**，每一個是一格的壓縮長度。
把它們加起來剛好 **1,764,911**，一個位元組不差，等於 `IBM16.350` 的大小。

```
前幾格：78, 79, 78, 77, 104, 126, 149, 199, 243, 289 …
最大 23,657，最小 20
```

所以開頭動畫是 **374 格**，`IBM16.350` 是把 374 段壓縮資料首尾相接。

## 分塊載入表（confirmed，`docs/re/116`）

`OPEN.EXE` 把 `IBM16.350` 切成 **30 塊**串流進來，每一塊塞得下幾個完整
影格就塞幾個，分界一律落在影格邊界上。載入器的資料段裡有兩張 30 筆的
uint16 表：

| 結構位移 | 內容 |
|---|---|
| `+0x0000` | 每一塊裝幾格 |
| `+0x03C0` | 每一塊幾個位元組 |
| `+0x04F6` | 緩衝區 A 的 far ptr |
| `+0x04FC` | 緩衝區 B 的 far ptr |

長度表 30 筆相加 ＝ **1,764,911**，與檔案大小一個位元組不差；拿
`IBMFLS16.350` 的逐格長度回算，30 塊剛好用完 374 格。兩張表的內容在
[`data/intro-chunks.json`](data/intro-chunks.json)。回算的每塊格數與
表上的值只有第 23 塊不同（回算 11、表上 10）——後果見下面那一段。

第 0 塊最大：**65,365 bytes ＝ 117 格**，其餘每塊 3–34 格。

流程是雙緩衝：解碼器讀哪一塊，載入器就往另一塊讀下一份。`041F` 的
`cs:000E` 是解碼器的來源指標、`cs:001C` 是它在該塊裡的位移，另有一個
「這一塊還剩幾格」的計數由解碼器遞減，歸零才換手。兩個緩衝區是
**`175C:001E` 與 `275D:0016`**，相差 65,544 bytes，互不相干
（`docs/re/283`）。

> 早先記的「兩個緩衝區只差 40 個位元組、第 1–116 格從來不會出現」
> 是執行器造成的，見 `docs/re/283`。遊戲的 `farmalloc(65500)` 確實會
> 算術溢位、把堆積區段結尾寫成 `0x0000`（`docs/re/116`，在
> `2e9dd3b` 上重量仍然如此），但 DOS 的空間表正常時第二段配到 `275D`，
> 不會蓋掉前一塊。`tools/scripts/intro_bufoverlap.py` 讀的是舊執行器的
> `openmem` 傾印，用它之前要先重錄。

**每塊格數表第 23 筆是原版少播一格的原因。** 第 23 塊
`檔案[1,400,255:1,430,100]` 裝得下 11 格（339–349），表上寫 10；
解碼器照表遞減就換手，所以**第 349 格永遠不會被解**。那一格的壓縮長度
1,421 bytes，畫出來相對第 348 格改 748 個像素（`docs/re/283`）。

## 位元圖與走法（confirmed）

一格 ＝ 四個 plane，每個 plane 後面接一個分隔位元組。一個 plane 是
**80 × 227 ＝ 18,160 bytes**，token 解出來的位元組**一欄一欄往下** XOR
進去：

```
di += 80
if di >= 18160: di -= 18159      ← 換到下一欄
停止：di == limit（limit 一開始 0x100，第一次換欄後改成 0x50 ＝ 80 欄）
```

終止是**相等**不是大於等於——讀成 `>=` 的話一格只吃 21 個位元組
（`docs/re/72`）。

驗算：374 格每一格吃掉的位元組數與長度表逐一相符；累加的 XOR 在第
97–102 格與第 244–251 格整個歸零（場景之間的黑幕），四個 plane
共 72,640 個位元組全部是 0。

## 執行期的緩衝區與搬去畫面（confirmed，`docs/re/108`）

四個 plane 各有一個 18,160 位元組的緩衝區，位移 `0x0016`／`0x4706`／
`0x8DF6`／`0xD4E6` 連續排列、沒有填補（間距 `0x46F0` ＝ 18,160）。
段值每次執行都不同，靠 `cs:[…]` 那張表拿；`2e9dd3b` 上前三個在 `375E`、
第四個因為跨過 64 KB 而落在下一個堆積段 `44AE:0016`（`docs/re/283`）。
**解碼器寫的是這四塊 RAM，不是 VRAM。**

解碼器在 `041F:024B`，寫的是 `xor es:[di + dx], al`——`dx` 就是上表的
偏移，四個 plane 共用同一段程式。終止界限存在 `cs:0248`，開頭是 `0x100`，
**在一個 run token 跑完時**改成 `0x50`（單一 byte 的路徑不動它）。

一格解完之後四趟 `rep movsw`（`041F:0206`／`0218`／`022A`／`0241`，
`CX ＝ 0x2378` ＝ 9,080 word ＝ 18,160 位元組）把四個緩衝區搬進 VRAM：
目的地是 `ES:DI`，`ES ＝ A131`、`DI` 在 `0000` 與 `6D60` 之間交替，
也就是 **`A0000 + 0x1310 + DI`**。

`0x1310 ＝ 61 列 × 80`：**640×227 的畫面畫在 640×350 頁面的第 61 列**
（垂直置中）。逐一試 y 位移量過，61 是明確的峰值。

## 播放環境（confirmed）

`OPEN.EXE` 切到 **mode 10h（640×350×16）**，調色盤先讀 `BU16IBM.RGB`
（48 bytes ＝ 16 色 × 3），播到一半換 `TITSPT.RGB`（同樣 48 bytes），
配樂是 `OPEN_M.MDS`。

**配樂寫死是 `_M` 那一份**：`OPEN.EXE` 的音樂模組與本體同一套（偵測音源 →
FM 或 MIDI 兩個外皮 → 同一支載入常式），但兩個外皮送進去的字元都是 `'m'`，
整個執行期映像裡沒有任何一處 `mov al,'f'`。所以不論偵測到什麼音源，
開頭動畫都讀 `OPEN_M.MDS`，而 `OPEN_F.MDS` 在出貨的遊戲裡永遠不會被打開
（`docs/re/274`）。

調色盤檔裡的值只有 0–15，**乘 4 才是 DAC 的 6 位元值**——與收據
`introvram/pal.bin` 的 48 個位元組逐一相符（`docs/re/110`）。形狀是
十六階亮度梯：G ＝ B ＝ 色號，偶數色號的 R 少一階（色號 2 是 `01 02 02`）。

進場時把 PIT 除數改成 `0x0800`（離場寫回 0 ＝ 65536），計時器變成
1,193,182 / 2,048 ≈ 582.6 Hz。

## 播放順序與逐格時程（confirmed，`docs/re/283`）

整段 421 組解碼呼叫的檔案位移**全部落在 `IBMFLS16.350` 算出來的格邊界上**，
順序是 0–348、350–373，再加上 350–373 兩遍：

```
格 0 → 348      一格 75 個計時器中斷（≈128.7 ms，約 7.8 fps）
  └ 格 102 前停 336 個（≈577 ms）      ← 落在 97–102 那段全黑
  └ 格 247 前停 2,236 個（≈3.84 秒）   ← 落在 244–251 那段全黑
格 349          從來沒有被解碼（每塊格數表第 23 筆寫 10，實際裝 11 格）
（載入器 0349:056B 把四個 plane 緩衝區清成 0）
格 350 → 373    一格 77 個（≈132.2 ms）；格 350 前停 2,850 個、
                格 351 前停 1,798 個（只有第一趟有）
（每趟之前再清一次）格 350 → 373 再跑兩趟，接縫停 1,240 個
```

第一趟 0 → 373 是 34,864 個中斷 ≈ 59.8 秒；含尾段三趟共 40,886 個
≈ 70.2 秒。畫面上，0–348 是一艘戰艦由遠而近（中間兩次全黑換場），
350–373 是標題圖淡入的迴圈。尾段跑完三趟之後讀 `SPTIT.350`（標題畫面）。

**尾段每趟都清緩衝區**是它能迴圈的前提——XOR 累加沒有反向操作。
末格後的1150／2000及標題9000等待、左鍵離場與逾時重播已由
[431](../re/431-title-player.md)證實；玩家契約與秒數近似見[112](../spec/112-title-player.md)。
第97輪補上TITSPT尾段色盤，修正Game沿用BU16IBM的漏接。
其他前段停頓來源與尾段為何跑三趟仍未知，不重開與本輪玩家閘門無關的研究。

## 每一格的編碼：不是哪幾套（confirmed 的排除）

- **不是 `.VO5`／`.AMG` 那套「相等即重複」**：照那套解，各格產生的
  位元組數差了兩個數量級（第 373 格會吐出 3,258,462 bytes，
  而一個 plane 只有 18,160）。
- **不是 `ENDING.EXE` 那份解碼常式**：靜態在 `OPEN.EXE` 裡搜不到那份常式
  （只有 `GIN3PS.EXE` 是 GLUE 封裝的，`OPEN.EXE` 與 `ENDING.EXE` 是普通
  MZ，`docs/re/274` §8）；執行期在整個 1 MB 記憶體裡搜那段
  程式碼的位元組（`AC 26 88 05`、`8A F8 4A`、`26 88 05 03`）也全部沒有
  命中。是另一套編碼，不是同一份程式碼搬過去。
- **不是整幀的點陣壓縮**：把 374 格用三種「次數欄位長度」的變體各解一遍，
  解出來的長度沒有一種收斂到 18,160 或 54,480。

現行的解法在上面「位元圖與走法」那一節。

## 繪圖端（confirmed）

`-vram-sites` 指出五個寫視訊記憶體的位置：

| 位置 | 次數 | 是什麼 |
|---|---|---|
| 清畫面 | 56,000 | `mov byte es:[bx+si],0`，四個 plane 一起開，跑滿 0xDAC0 ＝ 56,000 |
| 四趟 `rep movsw` | 各 54,480 | 四個 plane 各搬 18,160 bytes |

搬運端的程式碼：

```
mov dx,3C4 / mov al,02 / mov ah,01 / out dx,ax    ; map mask ＝ plane 0
lds si, cs:[…]                                    ; 來源 ＝ 該 plane 的 RAM 緩衝區
mov cx,2378h / cld / rep movsw                    ; 9,080 words ＝ 18,160 bytes
…四個 plane 各一趟，map mask 依序 01／02／04／08
```

所以**解碼器寫的是 RAM 緩衝區**，搬到 VRAM 只是最後一步。四個緩衝區的
位置見上面「執行期的緩衝區」那一節（段值每次執行都不同，靠 `cs:[…]`
那張表拿）。

目的頁在 `DI ＝ 0` 與 `DI ＝ 0x6D60` 之間交替（雙緩衝），所以
`-dump-ega` 從位移 0 讀只會看到其中一頁；程式同時在寫 CRTC 的
3D4／3D5 換顯示起始位址。
