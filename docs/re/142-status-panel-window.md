# 142 — 右側狀態欄就是一個視窗

`docs/internals/34` 把戰場右側狀態欄的框逐層量了出來：八層、左緣是
`8`／`15` 的 1:1 交錯、四個角靠畫序決定歸屬，還留了一句「換一個視窗尺寸
一定要重驗」。解完視窗系統之後回頭看，那八層根本不存在——**它是一個
普通視窗，框是 `FRAME.BLK` 的圖塊**。

## 找法

`ds:9890`／`ds:9892` 是那個視窗的遠指標，整份程式碼裡被讀了 162 次。
**寫入只有一處**——掃 `A3 90 98`／`89 1E 90 98` 這類儲存碼形，
命中 `0C0A:6B74`／`0C0A:6B77`：

```
0C0A:6B57  push 1        ; 旗標
           push 8        ; 高（內容格）
           push 8        ; 寬
           push 9        ; 格 y
           push 1Dh      ; 格 x ＝ 29
           push 97h      ; 色
           push 0, 0     ; 視窗 ＝ NULL，讓它自己配
0C0A:6B6D  call far 3603:0006
0C0A:6B74  ds:9892 = ax  ; 段
0C0A:6B77  ds:9890 = bx  ; 位移
```

旗標非 0 讓寬高各 ＋2，所以實際佔 **10 × 10 格**，格 (29,9)–(38,18)。

## 對上了

| | 舊的（量出來的）| 新的（機制）|
|---|---|---|
| 位置 | (465, 221) | 格 (29,9) ⇒ 像素 (464, 220)，可見的框從 (465,221) 起 |
| 大小 | 158 × 197 | 10 × 16 − 2 ＝ 158、10 × 20 − 3 …（可見範圍）|
| 框 | 八層 ＋ 交錯左緣 ＋ 26 個角落修正像素 | `FRAME.BLK` 起始碼 1 的八張圖塊 |

拿圖塊直接鋪 10 × 10 格，與三份收據（`s3ai6`、`s3menu`、`s3fight`）
各 **11,520 個像素逐位元組相同**。所謂「1:1 交錯的左緣」與「45° 斜切的
四個角」都只是圖塊裡本來就長那樣的像素。

## 文字也對得起來

內容區是 8 × 8 格，左上角在格 (30,10) ⇒ 像素 (480, 240)。回頭對
`screen-battle.json` 量出來的數字：

- `label_x` ＝ 480 ＝ 內容格第 0 欄 ✓
- `colon_x` ＝ 528 ＝ 第 3 欄 ✓
- `value_right` ＝ 608 ＝ 第 8 欄（內容區右界）✓
- 各列 y ＝ 242、262、282…＝ `240 ＋ 列×20 ＋ 2`——那個 **＋2 就是字在
  格內往下 2 像素**（`docs/re/141`），與訊息框量到的完全一致 ✓

所以狀態欄的九行字也是同一套文字緩衝區印出來的；把 `DrawBattleStatus`
改走 `ui.TextBuffer` 要先讀出原版那串跳脫碼，這裡先不動。

## 進 remake

`DrawBattleStatusFrame` 改用 `ui.TileFrame`，`screen-battle.json` 的
`status.frame` 換成格座標 ＋ 樣式，八層那一堆連同角落修正一起刪掉。
`TestBattleMatchesOracle`（整張戰場畫面的同狀態對拍）照樣通過。

## 可重用的規則

- **「量得出來」不等於「知道為什麼」。** 那八層每一層都量得準，整張畫面
  也對得上，所以它看起來像是完成的；但它的「換個尺寸要重驗」警告正是
  在說「我不知道規則」。**帶著這種警告的斷言要排進工作，不能當成完成。**
- **一個被讀 162 次的全域變數，寫入通常只有一處。** 找建立點時掃「儲存」
  的碼形（`A3 xx xx`／`89 1E xx xx`）比掃所有出現位置有效得多。
