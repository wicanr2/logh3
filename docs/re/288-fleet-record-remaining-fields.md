**星域記錄**的 `+0x13`，不是艦隊的。艦隊的 `+0x13` 從頭到尾是常數 20
（旗艦那一組的隊形槽），84 筆全同。

## 掃描方法與那個會產生假零的洞

沿用 `docs/re/287` 的三段式：`loadbyte.py` 收 Borland 讀 `unsigned char`
的固定形狀、`field_xref.py` 收所有 disp8 存取形式、`struct_window.py`
（本輪新增）把每個命中點附近所有帶段前綴的存取列出來，**用鄰居的位移集合
判「那個基底指向哪一張表」**。四份不同階段的傾印跑同一組位移，命中數逐格相同
——程式影像沒有隨階段換頁。

鄰居這一步不能省。122 bytes 的艦隊、126 bytes 的星域、82 bytes 的行星、
78 bytes 的艦艇共用同一段 disp8 值域，光看「`+0x50` 有 28 處」會全部誤判：

| 位移 | 看起來的消費者 | 實際上屬於誰 |
|---|---|---|
| `+0x50` | 22 處在 `2264`／`303F` 段 | **行星**（要塞砲瞄準方位，`docs/re/145`）|
| `+0x68`／`+0x70` | 七處 `add si,68h` ＋ 一批 `es:[bx+70h]` | **星域**（飛彈／艦載機存量）|
| `+0x45` | `303F:00B0` 寫 3 進去 | **行星**（要塞砲填充倒數）|

`field_xref.py` 原本還有一個**結構上的洞**：它只收 `mod=01`（`es:[bx+64h]`），
而 Borland 要把欄位的**位址**傳出去時會先 `83 C3 64`（`add bx,64h`）再用
`mod=00` 存取。`+0x64`／`+0x66`／`+0x6C` 這種常被取位址的欄位幾乎都走那條路，
只掃 `mod=01` 會得到「沒有消費者」——而那不是結論，是過濾器有洞。
本輪把 `add bx/si/di, imm8` 一併列進去（標 `[add reg,imm]`），
**下「沒有消費者」之前兩份都要是零**。

還有一種假陽性要手動排掉：`FF 74 4B` 被當成 `push [si+4Bh]`，實際上是
前一條指令的尾巴加上 `74 4B`（`jz +4Bh`）。`+0x4B` 那兩處「消費者」就是這樣來的。

## 新解一：`+0x74`／`+0x76`／`+0x78` ＝ 這回合結束時「預計」會在哪

寫入者 `3009:0235`（線性 `0x302C5`），一支艦隊一次：

```
3009:0235(艦隊):
    若 (+0x48 & 0x0F) == 4（待命）:
        +0x74 ← +0x5C ; +0x76 ← +0x5E ; +0x78 ← +0x4A     ; 原地不動
    否則若 (+0x48 & 0x0F) 是 0（移動）或 1（戰鬥）:
        θ = 2BE1:011D(+0x64 − +0x5C, +0x66 − +0x5E)        ; 到目的地的方位
        d = 3310:0006(+0x5C, +0x5E, +0x64, +0x66)          ; 32 位元距離
        若 d < +0x52:+0x54（這回合的行程）:
            +0x74 ← +0x64 ; +0x76 ← +0x66 ; +0x78 ← +0x4C  ; 走得到，就是目的地
        否則:
            (+0x74, +0x76) = 2BE1:026F(+0x5C, +0x5E, θ, 行程)   ; 沿 θ 推一段
            +0x78 ← θ
```

呼叫端 `3009:01E0`（線性 `0x30270`）掃在場艦隊清單（`ds:9898`、筆數 `ds:9894`），
**只對 `+0x01 != ds:8F1D` 的那些算**——也就是只算「不是目前陣營」的艦隊。
所以這三格是**敵方艦隊的落點預測**，不是自己的狀態。

兩個消費者：

- `307D:0921`（線性 `0x310F1`）：先擲一個 40–138 的門檻，拿自己的 `+0x44` 比。
  **它抽六次 `3CD5:000C()`**：第一次 `mod 50 + 40`，接著連抽四次丟掉，
  第六次 `mod 50` 加上去（`門檻 = 40 + r1 mod 50 + r6 mod 50`）——
  抽掉的那四次一樣要照抽，不然亂數序列會歪掉。
  `+0x44 >= 門檻` 才**直接讀另一筆記錄的 `+0x74`／`+0x76`／`+0x78`**；否則改走
  `307D:097E` 估一個。`+0x44` 就是提督與副官逐項取大之後的 `ADMIRAL +20`
  （[`../re/287`](287-admiral-remaining-fields.md)）——**那一項愈高，愈常算準敵人要去哪**。
  比 `+0x44` 的是 `[bp+0Ch]`、被讀預測值的是 `[bp+10h]`，兩筆不同的艦隊記錄；
  「前者是觀測方、後者是被觀測方」是 **strong inference**——沒有讀呼叫端，
  靠的是「預測值只對非目前陣營的艦隊算」這個事實。
- `303F:0230`（線性 `0x30620`）：要塞砲的電腦瞄準，量的是
  `3310:0006(艦隊 +0x74, 艦隊 +0x76, 行星 +0x46, 行星 +0x48)`。
  `docs/re/145` 記過「電腦那條路量的是艦隊的 `+0x74`／`+0x76`」，
  沒說那兩格是什麼——**是預測落點，不是現在位置**，所以要塞砲打的是提前量。

`+0x74`／`+0x76` 是 word（`89 47 74`），`+0x78` 是 byte（`88 47 78`）。
`+0x75`／`+0x77` 是高位元組，不是欄位。

## 新解二：`+0x5B` ＝ 要去打的那一顆行星

`307D:1384`（線性 `0x31B54`）拿它當索引：

```
行星 = ds:CFF8/CFFA 遠指標 + 艦隊[+0x5B] × 82
```

`ds:CFF8` 是「目前星域的行星切片」、一筆 82 bytes（`docs/internals/29`）。
寫入者 `307D:1441`（線性 `0x31C11`）與 `307D:11E2`（線性 `0x319B2`）都是同一組動作：

```
艦隊[+0x5B] ← 行星索引
艦隊[+0x48] ← 0                       ; 行動改成「移動」
艦隊[+0x52]:[+0x54] ← +0x4E << 19     ; 這回合行程 ＝ 巡航速度 × 8
31DB:0024(艦隊, …, 行星[+0x46], 行星[+0x48], &+0x64, &+0x66)   ; 目的地 ← 行星座標
```

所以 `+0x5A` 與 `+0x5B` 是兩件事：**`+0x5A` 是「現在正在打哪一顆」**
（`20B4:0486` 拿它比對行星索引，`docs/re/107`），**`+0x5B` 是「決定要去打哪一顆」**。
戰鬥層的重整（線性 `0x2A088`，`docs/re/230`／`docs/re/235`）把兩格一起設回
`0xFF`，`303F:04CA`／`303F:05F3` 也各清一次。

## 新解三：`+0x6C`–`+0x6F` 是遠指標，`+0x6A`／`+0x6B` 是它的兩個快取

`25DB:00FB`（線性 `0x25EAB`）把一塊記憶體掛上來：

```
艦隊[+0x6E] ← 段 ; 艦隊[+0x6C] ← 位移      ; 遠指標，低位在前
艦隊[+0x6A] ← 9                            ; 9 ＝ 不畫
物件[+1] ← 0FFh ; [+2] ← ds:9B9E ; [+3] ← 0F0h
物件[+0A] ← 10h ; [+0B] ← 10h ; [+0C] ← 9  ; 16 × 16
```

那塊東西是**這一支艦隊在星域戰場上的圖示物件**：`25DB:0670`（線性 `0x26420`）
用 `艦隊[+0x5C] − ds:9BF4` 算它的畫面座標寫進 `物件[+6]`，
`297B:034A`（線性 `0x29AFA`）在艦隊解散時 `35D1:0102` 把它釋放掉。
`docs/internals/33` 原本記的「`+0x6E`／`+0x6F` 進入戰鬥時一律填 1 與 113（假設待驗）」
就是段值 `0x7101` 的兩個位元組——**不是兩個欄位，是一個遠指標的上半**。

`+0x6A` 與 `+0x6B` 是同一個物件兩個欄位的快取，兩支常式的骨架一模一樣
（值沒變就不動，變了才寫回去並把 `物件[+1]` 設成 `0FFh` 標髒）：

| 位移 | 常式 | 推到物件的哪一格 | 來源 |
|---|---|---|---|
| `+0x6A` | `25DB:08A2`（線性 `0x26652`）| `[+0C]` 方向，並用 `3982:0001(方向)` 換一份圖形遠指標寫 `[+0E]`／`[+10]` | `25DB:0670` 拿 `+0x4A` 丟 `3982:0022` 換成 0–7（`docs/re/85`）|
| `+0x6B` | `25DB:0865`（線性 `0x26615`）| `[+3]` | `17A0:0699`（線性 `0x18099`）：寫艦艇 `+0x30` 的時候，**那一筆是旗艦（`艦艇[+0x03] == 0`）就一併寫進所屬艦隊的 `+0x6B`** |

`docs/internals/38` 早就記著艦艇 `+0x30` 是「`17A0:05B2` 從 `0x80` 開始遞減寫進來
的選擇順位……旗艦另外傳進艦隊記錄」——**沒記是哪一格，就是 `+0x6B`**。
四份傾印裡 `+0x6B` 全是 `0xFF`，因為那條路要走到補給／修理排序才會寫；
**值的分布在這裡不能當「沒人寫」的證據**。

## 寫了沒人讀：`+0x4B` 與 `+0x50`

兩格都只有寫入指令，整份影像找不到任何讀取（`mod=01` 與 `add reg,imm` 兩種形式都是零）：

- **`+0x4B`**：`297B:0BAF`（線性 `0x2A35F`）在進戰場時把
  `2BE1:011D(0x3F8 − +0x5C, 0x3F4 − +0x5E)`（指向 (1016, 1012) 的角度）
  **同時寫進 `+0x4A`、`+0x4C`、`+0x4B`**。前兩格之後會各自變（現在朝向／目標朝向），
  `+0x4B` 就停在初始值——是一份沒有人回頭看的備份。
- **`+0x50`**：`297B:106E`（線性 `0x2A81E`）那個「逐分隊取最小值」的迴圈算四個數，
  前三個是 `+0x4D`／`+0x4E`／`+0x4F`（回轉／巡航／戰鬥速度，`docs/re/112`），
  第四個 ＝ `min(艦艇[+0x23])` 寫進 `+0x50`。而 `SHIP.DT[89A]` 的
  **486 筆在用的艦艇記錄 `+0x23` 全部是 `0xFF`**，所以 `+0x50` 恆為 `0xFF`。
  **第四個速度槽在兩份版面上都存在，但從來沒有值、也沒有人讀。**

## 沒有任何存取：`+0x51`、`+0x68`、`+0x69`、`+0x71`、`+0x72`、`+0x73`

三種掃描形式（`loadbyte`、`field_xref` 的 `mod=01`、`add reg,imm`）在
四份傾印上都是零，鄰居檢查也把別張表的命中排掉了：

| 位移 | 命中 | 值 | 說明 |
|---|---|---|---|
| `+0x51` | 0 | 84 筆全 `0xFF` | `+0x50` 是 byte 寫入，所以它連順帶被蓋到都沒有 |
| `+0x68`／`+0x69` | 0（七處 `add si,68h` 全屬星域記錄）| 全 `0xFF` | |
| `+0x71` | 0 | 跟著 `+0x70` 走 | 只被 `20B4:0045` 的 `mov word es:[si+70h],0` 順手清掉 |
| `+0x72`／`+0x73` | 0 | 全 `0xFF` | |

正對照在同一次掃描裡：`+0x5B` 六處、`+0x74` 五處、`+0x4B` 一處（純寫入）、
`+0x6B` 兩處——掃描在已知有人用的位移上都開得了口，才拿它去問未知的。

`+0x49` 是另一種形狀：它有四處存取，但**四處都只動 bit0**
（`1C03:0194`／`1C03:0370` 的 `and …,0FEh`、`1C03:021E` 的 `or …,al`（`al` ＝ 1）、
`1C03:093D` 的 `test …,1`）。其餘七個位元從整筆 `0xFF` 的初始化留下來，
沒有任何讀寫——所以 `+0x49` 是「一格只用一個位元」，不是「一格未解」。

## 高位元組不是欄位

以下幾格看起來像獨立欄位（值域窄、常是 0 或 1），其實是相鄰 word 的上半：

| 位移 | 屬於 | 證據 |
|---|---|---|
| `+0x0B` | `+0x0A` 維持費（word）| 線性 `0x2AA64`：`add si,0Ah` ＋ `mov es:[si],bx` |
| `+0x0D` | `+0x0C` 移動花費（word）| `113A:06E5`：`mov ax,es:[si+0Ch]` |
| `+0x11`／`+0x15`／…／`+0x35` | 每組編制的艦艇池索引（word）| `docs/internals/33` `+0x10`+ 那一列 |
| `+0x39` | `+0x38` 索敵分遣隊索引（word）| `297B:1072`（線性 `0x2A822`）：`mov ax,es:[bx+38h]` |
| `+0x53`／`+0x55`／`+0x57`／`+0x59` | `+0x52`／`+0x56` 兩個 32 位元行程 | `docs/re/129` |
| `+0x5D`／`+0x5F`／`+0x61`／`+0x63`／`+0x65`／`+0x67` | 三對座標 word | |
| `+0x75`／`+0x77` | `+0x74`／`+0x76` 預測落點 word | 上面 |
| `+0x6D`／`+0x6F` | `+0x6C` 遠指標 | 上面 |

`docs/re/40` 當初的形狀猜測「`+0x0A`–`+0x0D` 兩個 word（186／221、212／247）
——像座標」在數字上沒錯（確實是兩個 word），**語意全錯**：那是維持費與移動花費。

## 方法

**「這一格沒有消費者」是一個關於工具的斷言，不只是關於程式的。** 這一輪三次
差點下錯結論，三次都是過濾器的形狀不對：只掃 `mod=01` 會漏掉 `add bx,imm` 那條路；
只看位移不看鄰居會把行星、星域、艦艇的命中全算到艦隊頭上；`FF 74 4B` 這種
跨指令邊界的巧合會生出憑空的消費者。**先讓掃描在已知答案上開口**——
`+0x5B` 六處、`+0x74` 五處都找得到——**再去問未知的**，否則零就只是零。

**值的分布在兩個方向上都不是證據。** `+0x6B` 在四份傾印裡全是 `0xFF`，
但它有寫入者也有讀取者，只是那條路沒被走到；`+0x50` 在四份傾印裡也全是 `0xFF`，
而它真的沒有讀取者。**同一個現象，兩個相反的結論——差別只在有沒有去讀程式。**
