# 225 — 編制排序的比較器：`[2]` 升冪，相同再比 `[3]`

`docs/re/213` 讀到「填完之後第 1 組起會用 `0FF4:0FF2` 排序」就停了，
比較器沒讀。整支只有 0x91 個位元組。

## 呼叫端

`0FF4:11F4` 的最後（線性 `0x11235`）：

```
push cs; push 0FF2h            ; 比較器
push 4                         ; 每個元素 4 bytes
push 艦隊[+0x0F] − 1           ; 筆數（旗艦不算）
push 艦隊段; push 艦隊偏移 + 14h ; 從第 1 組開始
call far 3C6A:000D             ; qsort
```

**第 0 組（旗艦）不參與**——起點是 `+0x14` 不是 `+0x10`。

## 比較器

線性 `0x10F32`：

```
0FF4:0FF2(a, b):                 ; 兩個都是 far ptr，指向 4 bytes 的編制槽
    a[2] > b[2] → 回  1
    a[2] < b[2] → 回 −1
    a[3] > b[3] → 回  1
    a[3] < b[3] → 回 −1
    回 0
```

四次比較都是**無號**（`jbe`／`jae`）。`[2]` 是艦種、`[3]` 是隊形槽索引
（`docs/internals/33`），所以規則是**先按艦種升冪，同艦種再按隊形槽升冪**。

## 與收據對上

`turn260mem` 三支艦隊，樣板順序 → 收據順序：

| 艦隊 | 樣板（第 1 組起）| 收據 |
|---|---|---|
| 提督 52 | (0,10) (0,12) (6,29) | 一樣（本來就升冪）|
| 提督 55 | (1,10) (1,11) (1,12) | 一樣 |
| 提督 47 | (3,5) (3,8) (5,29) (6,34) **(0,10)** | **(0,10)** (3,5) (3,8) (5,29) (6,34) |

提督 47 那一支把最後一組搬到最前面，正是「艦種升冪」。

## remake

`rules.BuildComposition` 收尾加 `sortGroups`。三支的編制現在與收據
**逐組相同**（艦種、艘數、隊形槽、順序），釘在
`TestFirstAITurnMatchesReceipt`。

**remake-owned**：原版走 `qsort`，`[2]` 與 `[3]` 都相同的兩組誰在前面
不保證。樣板裡沒有重複的 `(slot2, slot3)`，但換過艦種之後可能撞上，
所以 remake 用穩定排序把次序定下來。

## 一條方法

**「還沒讀」的東西先量一下有多大再決定要不要跳過。** 這支比較器
0x91 個位元組、四個分支，讀它比為它寫一段「順序不影響加總」的但書
還快。`docs/re/213` 當時跳過它是對的（那一輪在解別的東西），
但它一直掛在那裡，直到編制逐組對拍才變成擋路的東西。
