# 116 — 開頭動畫的 +40：兩個讀取緩衝區疊在一起

`docs/re/108` 量到遊戲看到的資料流是 `檔案[0:40] ＋ 檔案[65365:]`，
`docs/re/115` 找出讀檔常式只是 `read()` 的薄包裝、+40 來自呼叫端，
但呼叫端沒找到。這一輪把整條鏈接完。

## 呼叫端一直都在，只是目標位址算錯一個位元組

讀檔常式的進入點是 **`041A:0024`**（線性 `0x41C4`），不是 `041A:0023`：

```
0x41BC  c5 5e 06 89 07 1f c9 cb     ← 前一支常式的結尾（lds bx,[bp+6] … retf）
0x41C4  55 8b ec 1e c5 56 08 …      ← push bp / mov bp,sp / push ds / lds dx,[bp+8]
0x41D3  cd 21                       ← int 21h（所以 `041A:0035` 是它的下一條指令）
```

`docs/re/115` 搜的是會解到 `0x41C3` 的 far call，差一個位元組，
所以整份 1 MB 掃出零命中。改搜 `9A 24 00 1A 04` 之後，
呼叫端在 `0349:01AB`、`0349:02B4`、`0349:0365`、`0349:047B` 四處。

同一個原因也解釋了「找不到誰寫 `041F` 的 `cs:000E`」：寫入的指令是
`mov es, ds:8624h` ＋ `mov es:0Eh, ax`，段值來自變數，位址裡沒有 `041F`。
`075A:8610` 起是一張模組段表：

```
8610 053E(C 執行庫)  8614 041F  8616 075A  8618 075A  861C 070A  861E 070A
8620 070A  8622 041F  8624 041F  8626 070A  8628 070A  862A 041F  862C 041F
```

載入器本體在 `0349`，資料段 `DS ＝ SS ＝ 075A`，動畫參數在 `070A`。

## 載入器是 30 塊的雙緩衝串流

兩張表都在 `070A`：

| 位址 | 內容 |
|---|---|
| `070A:0000` | 每塊裝幾格，30 個 uint16 |
| `070A:03C0` | 每塊幾個位元組，30 個 uint16 |
| `070A:04F6` | 緩衝區 A 的 far ptr（`175C:001E`）|
| `070A:04FC` | 緩衝區 B 的 far ptr（`175F:0016`）|

長度表 30 筆相加 ＝ **1,764,911**，與 `IBM16.350` 一個位元組不差。
分塊一律切在影格邊界上：拿 `IBMFLS16.350` 的逐格長度回算每一塊裝幾格，
30 塊剛好用完 374 格。回算值與表上的值只有第 23 塊不同（回算 11、表上
10），其餘 29 筆相同——那一筆的差異這一輪沒有解釋。

流程是標準的雙緩衝：解碼器讀哪一塊，就往另一塊讀下一份資料。
`041F` 的 `cs:000E` 是解碼器的來源指標，`cs:001C` 是它在該塊裡的位移，
`075A:010A` 是「這一塊還剩幾格」，由解碼器遞減、載入器等它歸零才換手。

```
0349:0310  cs:001C ← 0；cs:000E ← 緩衝區 A；剩餘格數 ← 表[k−1]；讀第 k 塊進 B
0349:025F  cs:001C ← 0；cs:000E ← 緩衝區 B；剩餘格數 ← 表[k]  ；讀第 k+1 塊進 A
```

第一個迴圈跑 `k ＝ 1,3,…,23`（第 0–24 塊），換過調色盤之後第二段
（`0349:0398` 起）接著把剩下的 5 塊讀完。

## 兩個緩衝區只差 40 個位元組

```
緩衝區 A = 175C:001E → 線性 175DE
緩衝區 B = 175F:0016 → 線性 17606
相差 40
```

所以「讀進 B」會從 A 的第 40 個位元組起把 A 整片蓋掉。
拿收據 `openmem` 的記憶體與原版 `IBM16.350` 逐位元組比對
（`tools/scripts/intro_bufoverlap.py`）：

```
記憶體 175DE 起 40 bytes    ＝ 檔案[0:40]           True
記憶體 17606 起 63656 bytes ＝ 檔案[65365:129021]   True
解碼器看到的資料流 ＝ 檔案[0:40] ＋ 檔案[65365:]     True
```

第 0 塊裝的是 **117 格**，而解碼器只讀得到第 0 格的前 40 個位元組，
**第 1–116 格永遠不會被解**——正是 `docs/re/108` 從另一頭量到的結果。
第一次換手之後每一次讀檔同樣會蓋掉另一塊，逐格的實際後果這一輪沒有
再往下推。

## 為什麼配置器會給出疊在一起的兩塊

兩塊都是向 C 執行庫的遠端堆積要的（`0349:07D2` 與 `0349:07EB`）：

```
mov ax, 0FFDCh          ; 65,500
push ax
call far ptr 53Eh:17CAh
```

`053E:17E9` 的上限檢查是 `cmp cx, 0FFE8h`（65,512），65,500 過關。
但真正擴充區段的常式在 `053E:194C`，算新的區段結尾用的是 16 位元加法：

```
053E:1963  inc cx / inc cx        ; 加上塊頭那個 word
053E:1964  mov si,[bx+4]          ; 目前的區段結尾位移
053E:196B  add cx, si             ; ← 新的結尾
053E:196D  jnb  正常路徑
053E:196F  xor ax,ax / mov dx,0FFF0h
053E:1974  jcxz 擴充              ; 只有剛好進位到 0x10000 才不算失敗
053E:1976  jmp  失敗
```

65,500 ＋ 塊頭 ＋ 既有結尾正好進位到 `0x10000`，於是走 `jcxz` 那條，
**把區段結尾寫成 `0x0000`**。緩衝區 A 的堆積表頭把這件事記在案：

```
175C:0004  0000   ← 區段結尾位移
175C:000A  FFFE   ← 結尾哨兵（結尾 − 2）
175C:000E  175F   ← 下一個堆積區段
```

對照一塊正常的配置（plane 緩衝區，要求 `0xD4D0`）：

```
2760:0004  D4F0   ＝ 0xD4D0 + 0x20
2760:000A  D4EE
2760:000E  34B0   ← 下一段在 0xD500 之後，間距與大小相符
```

結尾記成 0 之後，下一次配置認為這個區段沒有空間，另開一段；而落點是
用那個 0 算出來的，所以只往後三個段 ＝ **48 個位元組**，減掉兩邊表頭
長度的差就是那 40。

也就是說：`farmalloc(65500)` 落在「檢查放行、算術卻已經溢位」的窗口裡
（上限檢查允許到 65,512，實際安全上限比它低），要到的兩塊 64 KB
緩衝區其實是同一片記憶體。

## 對 remake 的影響

沒有影響到目前的實作：remake 照**檔案順序**播 374 格（`docs/spec/020`）。
要不要把這個瑕疵一起重現是忠實度取捨，仍然等使用者裁決——
差別是**看得到的 116 格**，不是細節。
