# 監看漏報：DOS 讀檔與 EMS 換頁對它是隱形的

追「誰把行星的擁有者從無主改成同盟」（`57`）的時候，三個數字互相矛盾：

| 來源 | 行星 59（威爾勃恩）的 `+0x11` |
|---|---|
| `PLADAT.DAT` 檔案原值 | 2（無主）|
| `-watch 543A9` 報的最後一個值（載入期兩次寫入之後）| **0** |
| 200,000,000 步倒出來的表 | 2 |
| 620,000,000 步倒出來的表 | 1（同盟）|

監看說「載入之後停在 0」，倒出來卻是 2。**監看不是報錯，是沒報。**

## 成因

dosgolem 的寫入掛勾只掛在 `Machine.Write8`：

```go
func (m *Machine) Write8(a uint32, v uint8) {
	if m.watchLo <= a && a <= m.watchHi && m.Mem[a] != v { m.onWrite(...) }
	m.Mem[a] = v
	if a >= 0xA0000 && ... { m.planarWrite(...) }
}
```

而 `Write16` 與 `WriteBytes` **直接寫 `m.Mem`**。用到它們的是：

- `internal/dos/files.go` 的 INT 21h `AH=3F`（讀檔）→ 把檔案內容填進緩衝區
- `internal/dos/ems.go` 的 map page → 把一頁 EMS 換進分頁框
- BIOS 資料區、中斷向量

也就是說：**遊戲從檔案讀進來的每一個位元組、每一次 EMS 換頁，
對監看都是隱形的。** 而那正是「這張表是怎麼被填出來的」最常見的兩條路。

那兩次被報出來的寫入（`00 → 01`、`01 → 00`）是 CPU 在同一塊記憶體上
做別的事；真正把 2 填進去的那一下是讀檔，沒有被報。

## 修法

`Write16` ＝ 兩次 `Write8`，`WriteBytes` ＝ 逐位元組 `Write8`
（dosgolem 規格 `018`，單元測試 `TestWatchSeesServiceWrites`）。
planar 影像掛勾也跟著補上——服務層把資料寫進 `A0000`–`AFFFF` 時
本來就該經過 VGA 的寫入邏輯。

## 收穫

> 監看回「這個位址沒有人寫」的時候，先問**它掛在哪一條寫入路徑上**。
> 掛勾只覆蓋一條路的話，另一條路上的寫入不會產生錯誤訊息，
> 只會產生一個看起來很乾淨的錯誤結論。

這與 `49` 的 `-regs-at` 去重是同一類：**工具主動丟掉資料，而丟掉的
那一部分正好是答案**。兩次的判準都一樣——量到的東西與另一種量法
對不起來時，先懷疑量法。
