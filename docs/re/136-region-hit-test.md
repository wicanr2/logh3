# 136 — 點擊落在哪一層（`341B:039D`）

好幾個地方都要先問「這一下點在哪裡」：戰場的選點（`docs/re/121`）、
編隊的選格子（`docs/re/130` 裡那個 `ds:9B9A` 的比較）、行星選單。
那一步走的都是 `341B:039D`。

## 它做什麼

```
341B:039D(畫面x, 畫面y)
    格x = 畫面x >> 4          ; 一格 16 寬
    格y = 畫面y ÷ 20          ; 一格 20 高
    節點 = ds:D804／ds:D806    ; 已註冊區域的串列頭
    while 節點 != 0：
        若 節點[+0] == 2：                       ; 可點的區域
            若 格x >= 節點[+5] 且 格y >= 節點[+6]
            且 格x <  節點[+5] ＋ 節點[+7]
            且 格y <  節點[+6] ＋ 節點[+8]：
                回 這個節點
        節點 = 下一個
    回 0
```

所以**判定是用格不是用像素**（16×20，與選單版面同一組格），
而且是走一條**已註冊區域的串列**——先註冊的先中。

節點的欄位：

| 位移 | 內容 |
|---|---|
| `+0` | 種類；`2` ＝ 可點的矩形 |
| `+5`／`+6` | 左上角的**格**座標 |
| `+7`／`+8` | 寬／高，單位也是格 |

呼叫端拿回傳值去比對某個已知的節點，例如「編隊」選格子時只有
落在 `ds:9B9A`（戰場那一塊）才算數（`docs/re/130`）。

## 對 remake 的影響

remake 目前是直接拿戰場的矩形去比（`battleWorldAt`／`battleFieldPoint`）。
就**戰場這一塊**而言兩者等價——戰場的原點 (16,20) 與大小都是格的整數倍
（`docs/re/135` 量到 `3870:0296` 用的也是同一個原點）。所以不必改。

真正的差別在「同一個點同時落在兩塊區域上」時誰贏：原版看註冊順序，
remake 是寫死的優先序（分隊 → 行星 → 戰術選單）。**目前沒有已知的
重疊案例**，等有反例再處理。

## 還沒解

- 區域是誰註冊的、順序怎麼定（串列 `ds:D804` 的建立點）。
- `+0` 的其他種類（不是 2 的那些）。

## 2026-09-14 勘誤：行星選單的分層不是未解項

GitHub #15 與 `docs/re/133` 後來仍把 `341B:039D` 寫成未讀；那是過期斷言。
本文件已經完整保存它的格座標與視窗串列規則。戰場 viewport 的原點與尺寸
都是 16×20 完整格，所以 remake 的行星整格命中在該視窗內與原版等價。

真正的產品缺陷在更後面的繪製層：`openPlanetMenu` 會建立狀態，但
`drawBattle` 原先只在 `battleCmdUnit >= 0` 時畫命令選單；行星刻意把該欄設成
`-1`，因此選單看不見。修正與同狀態收據見
[`docs/playtest/010`](../playtest/010-planet-command-menu.md)。
