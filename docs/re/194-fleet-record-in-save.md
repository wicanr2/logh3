# 194 — 存檔的艦隊記錄與執行期同版面，`+0x0E` 是「應有組數」

`docs/re/168` 把艦隊 `+0x0E` 標成「形狀像編制槽的應有數（假說）」，
`docs/re/169`／`docs/re/190` 的「類別鍵 `+0x09`」也一直只在執行期看到。
這一輪發現**兩格都在存檔裡**，而且資料直接把假說驗掉了。

## 存檔的艦隊記錄就是執行期那一份

`FLEET.DT[89A]` 是 3904 bytes ＝ **32 × 122**，與 `ds:C074` 的執行期表
同一個版面。`internal/rules` 早就這樣讀了（`+0x04` 用不用、`+0x05` 副官、
`+0x10` 槽、`+0x3C` 士氣、`+0x48` 行動），只是 `+0x09` 與 `+0x0E`
從來沒被取出來。

## `+0x0E` ＝ 應有組數（confirmed）

`FLEET.DT8` 的 26 支在用的艦隊：

| `+0x0E` vs `+0x0F` | 幾支 |
|---|---|
| 相等（編制不缺）| 19 |
| `+0x0E` > `+0x0F`（缺編）| 7 |
| `+0x0E` < `+0x0F` | **0** |

**沒有一支的應有數小於現有數。** 缺編的七支：槽 6（7 vs 3）、
11（7 vs 3）、12（6 vs 3）、14（7 vs 3）、26（7 vs 1）、30（4 vs 1）、
31（4 vs 1）。

這把 `docs/re/168` 的假說坐實了：`2E54:143F` 模式 1／2 的
「`+0x0F == +0x0E`」就是**編制不缺**，`2E54:1574` 的
`× +0x0F ÷ +0x0E` 就是**編制完整度**。

## 順帶抓到一個 bug：`FleetShips` 會多算

`FleetShips` 走完十個槽、只跳過 `0xFF`；原版的戰力（`2E54:1876`）與
候選評分（`2E54:1574`）都**以 `+0x0F` 為界**。

平常兩者一樣，但**縮編過的艦隊後面幾個槽還留著舊的艦艇索引**：

```
FLEET.DT8 槽 26：+0x0F = 1，卻有 7 個槽不是 0xFF
```

三格存檔裡只有這一支不同（`DT9`／`DTA` 各 0 支），所以是**潛在但真實**
的 bug——`FleetStrength(DT8, 26)` 會把六筆舊的艦艇算進去。

修法：新增 `Slot.FleetGroupShips(i)`（以 `+0x0F` 為界），
`FleetStrength` 與 `FleetShipTotals` 改用它；`FleetShips` 本身不動——
艦隊組成那張畫面走的是它，那是另一件事（柵欄原則）。
全套測試在改完之後仍然全過，沒有任何已驗證的數字變動。

## 一條方法

**兩個來源說同一件事的時候，寫一個測試讓它們對撞。** 這個 bug 是
「`+0x0F`」與「編制槽掃到 `0xFF`」兩個來源在一支測試裡被放在一起才浮出來的
——而那支測試原本只是想確認新欄位有載進來。
