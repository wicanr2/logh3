# RE 108 — 開頭動畫：四個 plane 緩衝區的真實位址

`docs/re/104` 的收尾寫著「下一輪改從 `rep movsw` 的來源指標走」。這一輪
照做，兩份**各約三秒**的收據就把位址量準了——但解碼器的輸出仍然對不上。

## 誰在寫 VRAM

收據 `introvram`（`-steps 52000000 -vram-sites`）：

```
041F:0206 ×90800   041F:0218 ×90800   041F:022A ×90800   041F:0241 ×90800
0349:09E6 ×56000
```

前四處就是 `docs/re/73` 說的四趟 `rep movsw`（一趟一個 plane），
`0349:09E6` 是清畫面。90,800 ÷ 9,080 ＝ **10 格**——到第 52,000,000 步
為止搬了十格。

## 來源與參數

收據 `introsrc`（`-regs-at 041F:0206,0218,022A,0241`）：

| 趟 | `DS:SI` | 線性 | `CX` | `DI` |
|---|---|---|---|---|
| 0 | `2760:0016` | `27616` | `2378`（9,080 word ＝ 18,160 bytes）| `0000` 或 `6D60` |
| 1 | `2760:4706` | `2BD06` | 同上 | 同上 |
| 2 | `2760:8DF6` | `303F6` | 同上 | 同上 |
| 3 | `2760:D4E6` | `34AE6` | 同上 | 同上 |

**間距 `0x46F0` ＝ 18,160，正好一個 plane，沒有填補。**

`DI` 在 `0000` 與 `6D60` 之間交替，再次確認雙緩衝（`docs/re/73`）。

> 這推翻兩件事：`docs/re/72` 記的第二個緩衝區 `34B16` 差了 `0x30`
> （正確是 `34AE6`）；`docs/re/104` 猜的「間距 18,176、每個 plane 後面
> 16 個位元組填補」也是錯的——那是拿差了 `0x30` 的位址除出來的。

## 拿正確位址重比：還是不對

四個 plane 的非零位元組數（各 18,160 中）：**3,445／3,881／4,857／5,668**。

| 比法 | 結果 |
|---|---|
| 從第 0 格連續累加，逐格比四個 plane | 沒有一格全對 |
| 24 種 plane 對應（全排列）| 沒有一格全對 |
| 逐 plane 單獨比（374 格 × 4 × 4 組合）| **一組都沒有** |
| 四個 plane 的 XOR 對 XOR | 沒有一格相同（最像第 5 格 7,763／18,160）|

## 一個具體的線索：密度方向相反

執行期四個 plane 的非零數是**遞增**的（3,445 → 5,668），
而解碼器累加到最後一格是**遞減**的（5,738 → 3,182）。

單純把 plane 順序倒過來不成立（全排列都試過了）。所以差別不在「哪個
plane 是哪個」，而在**切分本身**——`docs/internals/19` 記的「一格 ＝
四個 plane，每個 plane 後面接一個分隔位元組」這個切法，很可能不是
執行期真正的切法。長度表逐格對得上只證明**整格吃掉的位元組數**是對的，
不保證中間切在哪裡。

## 解碼器本體在 `041F:024B`

收據 `introwr`（`-watch 27616-27625`，只跑 3,600 萬步）指出寫緩衝區的是
`041F:02D2`（15 次）與 `041F:02A8`（4 次）。反組譯那一段：

```
041F:024B  di ← 0 ; cx ← 0 ; cs:[0248] ← 0x0100      ; 終止界限
      迴圈：
        if di == cs:[0248]: 收工
        ax ← [bx+si] ; bx++                           ; 讀兩個 byte
        if ah != al: xor es:[di+dx], al ; di += 80 ; 換欄 ; continue
        bx++ ; cx ← [bx+si] ; bx++                    ; 讀計數
        if ax == 0: 只前進的迴圈
        if cl & 0x80: cx &= 0x7F      否則 xchg ch,cl ; bx++
        重複 cx 次：xor es:[di+dx], al ; di += 80 ; 換欄
        cs:[0248] ← 0x50                              ; ← **run 跑完才改界限**
```

`dx` 是這個 plane 的緩衝區偏移（`0x0016`／`0x4706`／`0x8DF6`／`0xD4E6`），
所以四個 plane 共用同一段程式、同一個 `di`。

**與 `tools/scripts/intro_decode.py` 的差別只有一處**：那支在**第一次換欄**
時就把界限從 `0x100` 改成 `0x50`，原版是在**一個 run token 跑完**時改，
而且單一 byte 的路徑根本不動它。

照原版改過之後：**374 格的長度依然全部相符**，而且與執行期緩衝區的比對
**結果完全沒變**（最像的仍是第 0 格）。所以那不是差異的來源。

## 影像在頁面裡是垂直置中的

`introsrc` 量到的 `movsw` 目的地是 `ES:DI`，其中 **`ES ＝ A131`**、
`DI ＝ 0` 或 `6D60`。也就是線性 `A0000 + 0x1310 + DI`：

```
0x1310 ＝ 4,880 ＝ 61 列 × 80
(350 − 227) ÷ 2 ＝ 61.5 → 61
```

**640×227 的動畫畫面是畫在 640×350 頁面的第 61 列**——垂直置中，
上下各留 61／62 列。這解釋了 `docs/re/104` 順帶記到的
「`A0000` 兩頁各只有兩、三千個非零位元組」。

量過了，不只是算的：把四個緩衝區組成 640×227 的色號，去比收據
`introvram` 的畫面（`screen.bin`，640×350），逐一試 y 位移——

| y 位移 | 相同 |
|---|---|
| 59 | 62.1% |
| 60 | 62.6% |
| **61** | **74.5%** |
| 62 | 62.5% |
| 63 | 61.8% |

**61 是明確的峰值。** 不是 100% 的原因 `docs/re/73` 已經解釋過：
遊戲正在「顯示這一頁、往另一頁畫」，所以畫面上是**上一格**，
而緩衝區裡是下一格——相鄰兩格本來就有七成多相同。

## 這一輪的結論

**顯示路徑整條通了**：解碼器 XOR 進四個 plane 緩衝區 → 四趟 `rep movsw`
搬進 VRAM 的 `+0x1310`（第 61 列）→ 換頁。remake 要把動畫接上去，
缺的只剩「解碼器的輸出與緩衝區對不上」這一項。

**解碼器仍然對不上**，而且這一輪排除了兩個候選成因：
plane 的位址（量準了）與終止界限的規則（改成原版的寫法，輸出不變）。

### 逐筆對過了：解碼器對第 0 格是**正確的**

收據 `introseq`（`-watch 27616-2BD05`，整個 plane 0 的 18,160 個位元組，
只跑到 3,480 萬步）錄到 980 筆寫入。與 `tools/scripts/intro_decode.py`
產生的寫入序列逐筆比：

```
前 12 筆（di 與寫進去的值）完全相同：
  (9406,192) (9486,128) (9566,32) (9646,48) (9726,112) …
```

**所以 token 文法與逐欄的走法都是對的。** 原始位元組也對得起來：

```
第 0 格開頭  00 00 29 3F | C0 80 20 30 70 10 30 08 14 0C 02 06 | 00 00 1D A5 | 01
             跳 0x293F     十二個單一 byte 寫入                   跳 0x1DA5     分隔
```

`0x293F ＝ 10,559` 次前進正好落到 di ＝ 9,406（欄 46、列 117），
而**段與段之間的那個分隔位元組是 `01`**（兩格的邊界都是）。

### 分歧在一個 340 萬步的空檔之後

第 12 筆與第 13 筆之間隔了 **3,417,298 步**：

| 筆 | 步數 | 位址 |
|---|---|---|
| 12 | #31,302,789 | `29E44`（di 10,286）|
| 13 | #34,720,087 | `27616`（**di 0**）|

而第一次 `rep movsw` 在 #34,706,925——**就在這個空檔裡**。

空檔之後緩衝區 0 的第一筆寫入落在 **di ＝ 0**（值 `0x20`），
接著 di ＝ 80、160，再跳到 8,720。掃過前 40 格 × 4 段，
**沒有任何一段的第一筆寫入在 di ＝ 0**。

所以問題不在文法，在**第一次搬圖之後那一輪的起始狀態**：
`di`、`cs:[0248]`（終止界限）或資料位置，三者之中有一個與第一輪不同。

### 入口的暫存器說出資料是怎麼定位的

收據 `introent`（`-regs-at 041F:024B`）：

| 次 | 步數 | `BX` | `SI` | `DX` |
|---|---|---|---|---|
| 1 | #31,260,075 | `0000` | `001E` | `0016`（plane 0）|
| 2 | #31,333,288 | `0015`（21）| `001E` | `4706`（plane 1）|
| 3 | #31,406,517 | `0027`（39）| `001E` | `8DF6`（plane 2）|
| 5 | #34,720,076 | `0000` | **`986D`** | `0016`（plane 0）|

解碼器讀的是 `[bx+si]`：**`SI` 是這一格在 64 KB 讀取緩衝區裡的起點、
`BX` 是格內的段位移**。第一輪的 `BX ＝ 0／21／39` 正是
`tools/scripts/intro_decode.py` 算出來的四段偏移（0／21／39／60）——
又一個「文法是對的」的證據。

`DX` 就是 plane 的緩衝區偏移，四個 plane 各呼叫一次。

`SI ＝ 0x001E ＝ 30` 對到檔案位移 0（第 0 格），所以緩衝區有 **30 個
位元組的前綴**。第二輪 `SI ＝ 0x986D ＝ 39,021` → 檔案位移 **38,991**
——正是 `docs/re/73` 記到的 `cs:001C` 第一個值。

### 38,991 不是任何一個段的邊界

把整份檔案當成連續的段流解（不假設一格四段）：

```
1,496 段（＝ 374 × 4），總共吃掉 1,764,911 個位元組 ＝ 檔案大小，一個不差
```

段的分解**端到端自洽**。但 38,991、49,213、57,395 這三個 `cs:001C` 的值
**沒有一個是段邊界**，也不是格邊界（38,991 落在第 81 與第 82 格之間）。

所以 `docs/re/73` 那個矛盾在這一輪被從第二個角度確認了：
**檔案不是被順序吃掉的**，第二輪是「跳」過去的。

### 解開了：緩衝區換過，而且**留了 40 個位元組**

收據 `intrord`（`-regs-at 041A:0035`，那是讀檔常式）只有兩次：

| 步數 | 目的地 | 長度 |
|---|---|---|
| #17,897,720 | `175C:001E` ＝ 線性 `175DE` | `0xFF55` ＝ **65,365** |
| #29,800,127 | `175F:0016` ＝ 線性 `17606` | `0xF8A8` ＝ **63,656** |

- 65,365 正是**第 0–116 格**的總長（`docs/re/71` 算過的第一塊）；
- 63,656 正是**第 117–131 格**的總長（第二塊）；
- 兩個目的地相差 **40**——第二塊是寫在第一塊的**後面 40 個位元組處**，
  所以緩衝區開頭那 40 個位元組還是第一塊的（＝檔案的前 40 個位元組）。
  這正是 `docs/re/71` 觀察到的「緩衝區前 40 bytes 固定是檔案的前 40 bytes」。

於是**遊戲實際看到的資料流**是

```
檔案[0 : 40]  ＋  檔案[65365 : 129021]
```

把那個流從位移 0 開始逐段解：

```
38,991 是第 4 段的起點——也就是第 0 格四段吃完之後的下一格。
```

而 38,991 正是 `docs/re/73` 記到的第一個 `cs:001C` 值，
也正是這一輪 `-regs-at` 量到的第二輪 `SI ＝ 0x986D`
（`0x20E2D − 0x175DE ＝ 0x984F ＝ 38,991`）。

**三個獨立來源的數字對上同一個位置。**

### 為什麼先前怎麼比都對不上

因為 remake 這側一直假設「照檔案順序播第 0、1、2… 格」，而原版在
第一次搬圖之前就換過緩衝區，**第 1–116 格根本沒有被解過**——
第 0 格之後直接接到第 117 格那一塊。所以

> 拿「從第 0 格連續累加」去比執行期的緩衝區，**永遠不可能對**。

解碼器從頭到尾都是對的（前 12 筆逐筆相同、1,496 段吃光整個檔案、
入口的 `BX` 與段偏移相符）；錯的是**餵給它的位元組序列**。

### remake 要怎麼做

照原版重現這條播放順序需要連讀檔的緩衝行為一起模擬（包含那 40 個
位元組的殘留）。**那是原版的緩衝副作用，不是動畫的內容**——
要不要照抄是個取捨，得先有規格再決定，不在這一輪的範圍。
可以確定的是：resource 那一側（374 格、四個 plane、逐欄 XOR、
畫在第 61 列）已經全部解完，畫得出來。
