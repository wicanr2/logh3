# RE 18 — 遊戲設定畫面用的不是 `GRAPH.IMG`

日期：2026-09-07
執行器：dosgolem-logh3 `82f430e`
收據：`settings1e`
狀態：**未解**（字型來源）。

## 現象

遊戲設定畫面（系統指令 → 設定）的標籤——「遊戲設定」「音源」「BGM」
「戰鬥BGM」「訊息速度」「動畫效果」「動畫速度」——**一個都掃不出來**。
其餘畫面用同一支 `read_line` 都讀得到。

## 不是位置問題

起點掃過 x 164–240、基線掃過 y 56–67，全部回 0 格。把那一格的點陣
（`ink = 7`，16 × 15）拿去跟整張字型表比，最接近的一個差 **76 個位元**
——不是「差一點」，是完全不同的字。

## 是字形本身不同

畫面上 (176,61) 起 16 × 15、只標色 7 的那一格（`screen.bin` 直接讀出來的）：

```
................
##....##...##...
.##...##..##....
....###########.
#######.........
...############.
..##.##.##..##..
.##..##.##.##...
##...##.#######.
.##.##..##..##..
..##....##..##..
..##..########..
..##...##..##...
.##.............
################
```

筆畫多半是兩個像素寬，最後一列是實心橫線（那是框的邊，不屬於字）。

## 字型檔就是 `GRAPH.IMG`（confirmed）

「另一套字型檔」這個方向已經排除。開設定畫面的那一刻，讀檔紀錄裡
全部都是 `GRAPH.IMG`，一次 30 bytes（＝16 × 15 的全形字）：

```
#210450911 seek Graph.img → 44640   read 30 bytes
#210451495 seek Graph.img → 99240   read 30 bytes
#210452878 seek Graph.img → 100860  read 30 bytes
#210465735 seek Graph.img → 109500  read 30 bytes
```

沒有別的檔被開啟。所以**字形資料是對的，畫的時候做了什麼變換**。

已經試過而且不成立的變換（拿畫面點陣跟整張字型表比，取最小差異）：

| 假說 | 最小差異 |
|---|---|
| 原樣 | 32 位元 |
| 加粗 `v | (v>>1)` | 34 |
| 加粗 `v | (v<<1)` | 32 |
| 半形字橫向放大兩倍 | 87 |
| 把陰影色也算成字身 | 39 |

把遊戲實際讀出來的那一格（位移 44640）跟畫面並排，只有其中一列
完全對得上，其餘都錯開——比較像**兩個字形疊在一起**，
而不是單一字形的變換。**變換是什麼，未解。**

## 影響

`screen-settings` 的規格量得出框與橫條，但標籤文字缺，
差 10,839 / 307,200，**沒有進對拍表**。收據 `settings1e` 留著。

## 寫進畫面的是哪一段（confirmed）

在那個字第一列的 VRAM 位址（`A1376`，＝ x 176、y 62）設監看，
最後一次寫入來自 **`2376:110E`／`2376:1112`**，值 `C3`／`18`——
與畫面上該列的位元 `##....##...##...` 一致。

那一段是**展開的複製迴圈**（線性 `24817` 起）：

```
8B 46 0C    mov ax,[bp+0C]
8B 5E 0A    mov bx,[bp+0A]
26 88 07    mov es:[bx],al
43          inc bx
26 88 07    mov es:[bx],al
...
```

也就是說，要寫的位元組**在呼叫端就算好了**，存在一整排區域變數裡。
變換發生在更前面。

再往前是一段 `rep movsb` 加上 VGA 埠 `3CE` 的設定（線性 `247A0` 起），
看起來是字形先搬到某個緩衝區、再經由圖形控制器寫進 VRAM。

**下一步**：攔 `24817` 這支的呼叫端，看它怎麼把 30 bytes 的字形
變成那一排區域變數。資料來源與寫入點都已經定住，缺的只有中間那一步。
