# RE 18 — 遊戲設定畫面用的不是 `GRAPH.IMG`

日期：2026-09-07
執行器：dosgolem-logh3 `82f430e`
收據：`settings1e`
狀態：**未解**（字型來源）。

## 現象

遊戲設定畫面（系統指令 → 設定）的標籤——「遊戲設定」「音源」「BGM」
「戰鬥BGM」「訊息速度」「動畫效果」「動畫速度」——**一個都掃不出來**。
其餘畫面用同一支 `read_line` 都讀得到。

## 不是位置問題

起點掃過 x 164–240、基線掃過 y 56–67，全部回 0 格。把那一格的點陣
（`ink = 7`，16 × 15）拿去跟整張字型表比，最接近的一個差 **76 個位元**
——不是「差一點」，是完全不同的字。

## 是字形本身不同

畫面上 (176,61) 起 16 × 15、只標色 7 的那一格（`screen.bin` 直接讀出來的）：

```
................
##....##...##...
.##...##..##....
....###########.
#######.........
...############.
..##.##.##..##..
.##..##.##.##...
##...##.#######.
.##.##..##..##..
..##....##..##..
..##..########..
..##...##..##...
.##.............
################
```

筆畫多半是兩個像素寬，最後一列是實心橫線（那是框的邊，不屬於字）。

## 字型檔就是 `GRAPH.IMG`（confirmed）

「另一套字型檔」這個方向已經排除。開設定畫面的那一刻，讀檔紀錄裡
全部都是 `GRAPH.IMG`，一次 30 bytes（＝16 × 15 的全形字）：

```
#210450911 seek Graph.img → 44640   read 30 bytes
#210451495 seek Graph.img → 99240   read 30 bytes
#210452878 seek Graph.img → 100860  read 30 bytes
#210465735 seek Graph.img → 109500  read 30 bytes
```

沒有別的檔被開啟。所以**字形資料是對的，畫的時候做了什麼變換**。

已經試過而且不成立的變換（拿畫面點陣跟整張字型表比，取最小差異）：

| 假說 | 最小差異 |
|---|---|
| 原樣 | 32 位元 |
| 加粗 `v | (v>>1)` | 34 |
| 加粗 `v | (v<<1)` | 32 |
| 半形字橫向放大兩倍 | 87 |
| 把陰影色也算成字身 | 39 |

把遊戲實際讀出來的那一格（位移 44640）跟畫面並排，只有其中一列
完全對得上，其餘都錯開——比較像**兩個字形疊在一起**，
而不是單一字形的變換。**變換是什麼，未解。**

## 影響

`screen-settings` 的規格量得出框與橫條，但標籤文字缺，
差 10,839 / 307,200，**沒有進對拍表**。收據 `settings1e` 留著。

## 寫進畫面的是哪一段（confirmed）

在那個字第一列的 VRAM 位址（`A1376`，＝ x 176、y 62）設監看，
最後一次寫入來自 **`2376:110E`／`2376:1112`**，值 `C3`／`18`——
與畫面上該列的位元 `##....##...##...` 一致。

那一段是**展開的複製迴圈**（線性 `24817` 起）：

```
8B 46 0C    mov ax,[bp+0C]
8B 5E 0A    mov bx,[bp+0A]
26 88 07    mov es:[bx],al
43          inc bx
26 88 07    mov es:[bx],al
...
```

也就是說，要寫的位元組**在呼叫端就算好了**，存在一整排區域變數裡。
變換發生在更前面。

再往前是一段 `rep movsb` 加上 VGA 埠 `3CE` 的設定（線性 `247A0` 起），
看起來是字形先搬到某個緩衝區、再經由圖形控制器寫進 VRAM。

## 那支 VRAM 對拷不是畫標籤的（實測排除）

寫入點往前 `0xB7` bytes（線性 `24760`）確實有一支 VRAM 對 VRAM 的搬運：
設圖形控制器 write mode 1、`ds` 與 `es` 都指到 `A000`、
來源與目的各算一組 `(x, y)` → `y*80 + x/8`。

攔它的執行時參數，前四次都在開場階段（#96,380,115 附近），
參數是「來源 (0, 480) → 目的 (240, 270)」——**來源 y ＝ 480 在螢幕之外**。
VGA mode 12h 只顯示到 y ＝ 479，所以遊戲把素材放在離螢幕那一段
顯示記憶體裡再搬進畫面。這件事本身是 confirmed，值得記著。

但**設定畫面開啟的那段時間它一次都沒被呼叫**（`-regs-from 210260000`
攔到 0 次）。所以標籤不是這樣搬過去的，這條線斷了。

## 真正的線索：寫進去的值不等於畫出來的值

`2376:110E` 寫 `A1376` 的那一刻，`AX = 0909`、`DX = 03CF`——
**`al` 是 `09`，而那個位址最後呈現的是 `C3`**。`03CF` 是圖形控制器的
資料埠，所以那一段是在 write mode ／ bit mask ／ set-reset 的狀態下寫的：
CPU 寫進去的位元組會先被硬體改一次才落到 VRAM。

也就是說**畫面上的位元本來就不該等於字形的位元**，
先前拿字形去比對畫面（差 32 位元、加粗、放大…）全部問對了地方、
用錯了方法。

**下一步**：記下那一段執行時圖形控制器各個 index 的值
（尤其 index 0 Set/Reset、index 3 Function Select、index 8 Bit Mask），
還原硬體那一步做了什麼。dosgolem 已經在記寫過的 I/O 埠，
要的是「這一刻的暫存器狀態」。

## 中間那一段有一支 VRAM 對拷（強證據）

寫入點往前 `0xB7` bytes（線性 `24760`）是這樣開頭的：

```
BA CE 03    mov dx,3CE
B8 05 00    mov ax,0005
EE          out dx,al        ; 圖形控制器 index 5 ＝ Mode
42 EC       inc dx; in al,dx
0C 01       or  al,01        ; write mode 1（latch 對拷）
EE          out dx,al
B8 00 A0    mov ax,A000
8E D8 8E C0 mov ds,ax; mov es,ax
8B 46 08    mov ax,[bp+08]   ; 來源 y
… ax*80 …
8B 76 06    mov si,[bp+06]   ; 來源 x
C1 EE 03    shr si,3
03 F0       add si,ax        ; si ＝ y*80 + x/8
8B 46 0C    mov ax,[bp+0C]   ; 目的 y
… 同樣算 …
8B 7E 0A    mov di,[bp+0A]   ; 目的 x
```

`ds` 與 `es` 都設成 `A000`、write mode 1、來源與目的各一組 `(x, y)`
——這是一支 **VRAM 對 VRAM 的搬運**。

如果標籤是這樣搬過去的，那它在被搬之前就已經是那個樣子了，
「拿 `GRAPH.IMG` 的字形去比對畫面」自然對不上——**該去看的是來源那一塊
VRAM 是怎麼組出來的**，不是字形本身有什麼變換。

⚠ 這一段是靠人工讀反組譯推的，**還沒有實測證實那支就是畫標籤的那一支**
（攔它的執行時參數還沒跑出結果）。在證實之前，這一節是強證據，不是 confirmed。
