# 開頭動畫解出來了：一欄一欄往下走，終止是「相等」不是「大於等於」

`docs/re/36` 把 token 語法解出來、`docs/re/71` 把分段規則解出來，
剩下最後一塊：**一個 token 寫到哪一格**。

## 錯在哪

`docs/re/36` 抄下來的走法是對的：

```
add di,50 / cmp di,46F0 / jnb wrap
wrap: sub di,46EF / mov word cs:[0248],0050
```

錯的是**終止條件**。原版是

```
cmp di,cs:[0248]
jz  ret            ← 相等才停
```

`jz` 是**相等**。`di` 每格 `+80`，一超過 18160 就 `-18159`——換欄之後
`di` 剛好變成欄號 1、2、3…，而 `cs:[0248]` 在第一次換欄時被改寫成
`0x50` ＝ 80。所以停的時機是「走完第 80 欄」。

一開始的 `0x100` 不是「格數上限」，只是一個**在第一次換欄之前不會等於
`di`** 的值（`di` 依序是 0、80、160、240、320…，跳過 256）。

照字面讀成 `di >= limit` 的話，第五格就停了——一格只吃 21 個位元組，
與長度表的 78 差得離譜。

## 驗算：三件互相獨立的事

1. **374 格每一格吃掉的位元組數，與 `IBMFLS16.350` 的長度逐一相符**，
   總和 1,764,911 ＝ 檔案大小，一個位元組不差。
2. **累加的 XOR 在第 97–102 格與第 244–251 格整個歸零**——四個 plane
   共 72,640 個位元組全部是 0。那是兩個場景之間的黑幕。
   走法只要錯一格，這件事的機率是 0。
3. **解出來的畫面就是船艦**（`tools/scripts/intro_frames.py` 輸出的
   PNG）：第 200 格是一艘斜著的巨艦、第 300 格是另一艘加一顆星。

## 為什麼 `docs/re/36` 當時對不上記憶體

兩個原因疊在一起：

- `cs:[001C]` 是**這一塊裡的位移**，不是檔案位移（`docs/re/71`）；
- 拿「從第 0 格累加到第 N 格」去比執行期的緩衝區，但那個緩衝區裝的是
  **當時那個場景**的累加，場景之間會被清掉——不是從第 0 格一路累到現在。

補一個這一輪量到的旁證：第 30,000,000 步倒出來的兩個解碼緩衝區
（`lin:27616` 與 `lin:34B16`）**四個 plane 全部是 0**，
第 40,000,000 步才有內容。所以緩衝區本身不帶底圖，
`docs/re/36` 那句「動畫開始前就有 3,105 個非零位元組」是別的東西
（那份收據的執行器是 `8c8af90`，本來就要重做）。

## 解碼器

- `tools/scripts/intro_decode.py`（解成 plane）與
  `tools/scripts/intro_frames.py`（輸出 PNG）。
- remake 端：`internal/asset.IntroDecoder`，單元測試
  `TestIntroDecoder` 把上面那三個判準都寫進去（374 格全解、
  兩處場景黑幕整個歸零、歸零的格正好是那 14 個）。

收據的 `pal.bin` 是**已經換算成 0–255 的**灰階漸層（0 → 243），
不要再乘 `255/63`——乘了會整片過曝成白／青色。

一格 ＝ 四個 plane，每個 plane 後面接一個分隔位元組；plane 的資料是
`docs/re/36` 那四種 token。位元圖是 80 × 227 ＝ 18,160 bytes，
**一欄一欄往下**：`di += 80`，`di >= 18160` 就 `di -= 18159`。

## 還沒對上執行期的緩衝區

拿「從第 0 格（或場景開頭）累加到第 N 格」去比 `lin:27616`／`lin:34B16`
那兩個解碼緩衝區，**374 格沒有一格逐位元組相同**，比畫面也一樣。
理由很可能只是 dump 的時機落在一格的中間（`-dump-mem` 是跑完才倒，
而一格要解好幾萬個指令），但沒有證據，先當**未對上**記著。

要對上得停在影格邊界：對緩衝區設寫入監看找出兩格之間的指令數，
再用那個數字當 `-steps` 重跑一次。

順帶量到的：第 30,000,000 步時兩個緩衝區四個 plane **全部是 0**，
所以緩衝區本身不帶底圖。

## 還沒做
