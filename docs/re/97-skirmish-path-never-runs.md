# 97：單擊那條路整場沒跑過

`docs/re/86` 讀完 `2350:0023`（單擊的扣除算式）之後下了一個推論：
「戰鬥實際扣艦艇走的是這條，因為量級對得上」。這一輪拿收據直接問，
**那個推論是錯的**——單擊那條整場沒跑過，實際在跑的是艦隊層那條。

## 問法

`2350:0023` 進來第一件事就是 `call far 2264:0FC3` 算分母 K，是無條件的。
所以只要盯 `2264:0FC3` 有沒有被執行，就等於盯 `2350:0023` 有沒有被呼叫。

跑兩次 `s3fight` 的完整序列（14 億步，含九個回合的戰鬥）：

| 收據 | 旗標 | 結果 |
|---|---|---|
| `s3kfire` | `-regs-at 2264:0FC3 -regs-from 1080000000 -regs-max 12` | **前 0 次** |
| `s3kall` | `-regs-at 2264:0FC3 -regs-max 8` | **前 0 次** |

第二份沒有起點限制，涵蓋整條序列。**一次都沒有。**

## 實際扣艦艇的是誰

`s3kinds` 那份 watch（盯艦池第 135 筆的 `+0x08`）早就把寫入者印出來了，
只是當時沒往這個方向看：

```
#1158741688 691DC: B8 → 93  ← 203A:06C0     ; 3000 → 2963（−37）
#1185826490 691DC: 93 → B8  ← 1AAB:08CC     ; 2963 → 3000（補回去）
#1248637773 691DC: B8 → 86  ← 203A:06C0     ; 3000 → 2950（−50）
```

`203A:06C0` 是 `203A:0593` 的善後段（`docs/re/93` 也在那裡加分數）。所以
扣除確實走 `203A:0593`，但**進去的路不是 `2350:0023`**——那條的六個
呼叫點裡，`235EF` 這個已經被排除了。

### `1AAB:08CC` 是一次「搬運」

那支讀下來不是「加回去」，是**從一個 32 位元的來源搬到目的地**：

```
來源 ＝ [bp+1Ah] 的 +0x0E／+0x10（32 位元）
量   ＝ min(來源, [bp+0] 傳進來的上限)
目的地 += 量        ; 0x1B379，就是被 watch 抓到的那一筆
來源   −= 量        ; 32 位元減
```

目的地是艦艇記錄的 `+0x08`（現有艘數），量剛好等於前一次扣掉的 37。
所以**戰鬥中的損失會從某個儲備補回來**——這解釋了為什麼整場打完
艦艇池的總數只掉一點點。來源那筆記錄是誰、什麼時機搬，還沒解。

## 艦隊層那條在跑

同一支函式探兩次，一次回 0、一次命中——差別只在 `段:偏移` 寫對沒有
（見下一節）。用正確的 `20B4:1110`（收據 `s3dist`）：

```
#1158740308 AX=0BB8 ... [bp+] 00:0000 02:0504 04:0FA0 06:0122 08:0000
#1158758261 AX=0BB8 ... [bp+] 00:0001 02:0025 04:0FA0 06:00FD 08:0025
#1158776274 AX=0BB8 ... [bp+] 00:0002 02:0025 04:0FA0 06:00D8 08:004A
#1158794802 AX=0FA0 ... [bp+] 00:0003 02:0025 04:0FA0 06:00B3 08:006F
```

欄位讀得出來：

| `[bp+]` | 是什麼 | 這一輪的值 |
|---|---|---|
| `00` | 分隊序號 | 0、1、2、3… |
| `02` | 這一個分隊分到的量 | 37 |
| `06` | **還沒分完的總量** | 290 → 253 → 216 → 179（每次少 37）|
| `08` | 已經分掉的累計 | 0 → 37 → 74 → 111 |
| `AX` | 這個分隊的艘數 | 3000／4000 |

**一支艦隊一回合算一個總數（這裡是 290），再逐個分隊按比例分攤**——
與 `docs/re/86` 讀出來的算式（`21A0:0004` ＋ 比例分攤）完全一致，
步數也與 `203A:06C0` 的扣除交錯在一起。

所以六個呼叫點裡，**在跑的是 `21CB6`／`21D1B` 這一組**；
`235EF`（單擊那條）確定沒跑。

## ⚠ `-regs-at` 比對的是 CS:IP，不是線性位址

讀 dosgolem 的實作（`cmd/probe/main.go`）：

```go
if m.CPU.Seg[cpu.CS] == w.seg && m.CPU.IP == w.off && m.Steps >= *regsFrom {
```

**`段:偏移` 要與執行時的 CS:IP 完全相同**才算命中。而筆記裡那些
`21A0:0250` 之類的寫法是 IDA 段落命名的產物，不是執行時的 CS——同一個
線性位址可以用很多組 `段:偏移` 表示。

所以要下「這支沒被呼叫」的結論之前，得先確認**它是被哪一種 CS 進去的**：

| 位址 | 怎麼進去 | 筆記的寫法能不能用 |
|---|---|---|
| `2264:0FC3` | 唯一的 far call 編碼就是 `9A C3 0F 64 22` → CS ＝ `2264` | ✓ 能 |
| `1E9B4` | 唯一的 far call 編碼是 `1DD6:0C54` → CS ＝ `1DD6` | ✓ 能（那一條路徑） |
| `21A0:0250` | **沒有任何 far call 指向它**，是同段內的近呼叫 | ✗ 不能 |

`21A0:0250` 那個「前 0 次」因此**不算數**。它所在的區段實際的 CS 是
`20B4`（前兩支函式的 far caller 寫的是 `20B4:1004`／`20B4:103D`），
所以要探的是 `20B4:1110`——換成那個之後就命中了（見上一節）。
**同一支函式，位址寫法不同，一次回 0 一次回 6。**

搜「哪些 far call 指向這個線性位址」的方法很簡單：掃所有 `9A`，
把 `(段 << 4) ＋ 偏移` 算出來比對——同一招在 `docs/re/90` 找 `2350:0023`
的呼叫點時就用過。

## 正對照：`203A:06C0` 探得到

拿一個已知會執行的位址探一次（收據 `s3ctrl`，`-regs-at 203A:06C0`）：

```
#1158741688 AX=0025 BX=2924 ... DS=54B3 ES=668B
    [bp+] 00:00D7 02:0025 04:0000 06:4F24 08:54B3 0A:0BB8 0C:0001 ...
#1158796179 AX=0034 ...
    [bp+] 00:0000 02:0034 ... 0A:0FA0 0C:0002 ...
```

**探針是活的**（前 6 次都印出來了），所以前面兩個「前 0 次」是真的資訊。
而且這一份順帶把幾件事釘住：

- 步數 `1158741688` **與 watch 看到 3000 → 2963 的那一步完全相同**；
- `AX ＝ 0x25 ＝ 37`，正是那一次扣掉的量；
- 第四次 `AX ＝ 0x34 ＝ 52`，那一筆的 `[bp+0Ah] ＝ 0x0FA0 ＝ 4000`
  （滿編 4000 的艦種）、`[bp+0Ch] ＝ 2`（艦種 2）；前三次是
  `0BB8 ＝ 3000` 與艦種 1；
- **第一次的 `[bp+00h] ＝ 0x00D7 ＝ 215`**——那正是 `docs/re/85` 量到的
  同盟第 13 艦隊整場損失（27,000 → 26,785）。

所以扣除是**一支艦隊算一個總數、再逐個分隊分攤**的形狀，與艦隊層那條
（`21A0:0004` ＋ 比例分攤）一致。正在用修正過的 `-regs-at 20B4:1110`
正面確認那支有沒有跑。

## 教訓

**兩條，第二條是這一輪自己踩的。**

一、**量級對得上不等於那條路有在跑。** 當時的推理是「艦隊層算出十幾艘、
實測 37 與 50，所以走的是另一條」——但那只證明「艦隊層那條的某個
輸入被我算小了」，不證明另一條有被呼叫。要下「這條路在跑」的結論，
就要直接問它有沒有被執行。

二、**「前 0 次」要先做正對照才算數。** 三個位址連續回 0 次的時候應該
先停下來問「探針本身有沒有在動」，而不是接著往下推論。正確的做法是
拿一個**已知會執行**的位址（這裡是 `203A:06C0`，watch 印過它寫記憶體）
去探一次；探得到，回 0 次才是資訊。`~/diagnosis-notes` 的
「查詢回空」那條講的就是這件事——規則早就在，這一輪還是先推論後對照。
