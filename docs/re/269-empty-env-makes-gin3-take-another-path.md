# 269 — 環境字串區非空，`GIN3.COM` 就走另一條路（換執行器分支的根因）

日期：2026-09-10
執行器：dosgolem-logh3 `6ab4f95`（分支 `logh3-oracle`）
狀態：**confirmed**（一手證據：分歧點的位元組、兩版的環境區塊傾印、開關的正反對照）

`logh3-com-support` 的四個 commit 併進 main 之後，原版一個畫面都跑不出來
——`GIN3.COM` 在第 60,956,639 道指令跑飛（`CS:IP = B374:0075`）。
這一篇記怎麼從崩潰點追到根因，以及為什麼中間好幾個看起來很像的答案都是錯的。

## 一句話

**loader 從 2026-09-05 起在環境字串區放了一條 `COMSPEC=`**，而 `GIN3.COM`
的載入器看環境的第一個位元組決定要不要掃描它。那一個位元組讓它走上另一條
路，最後某道 `push` 蓋掉堆疊上的返回位址。

## 崩潰機制

軌跡的最後一道是 `0374:023E`（一個 `retf`），下一道就是 `B374:0075`。
`0374` → `B374` 只差最高位元組，所以是**堆疊上的返回 CS 被寫壞**。
對那一格設監看：

```
[watch] #120561079  65E95: 03 → B3  ← 2703:09A1
[watch] #120561079  65E96: 00 → 54
```

寫進去的是 `54B3` ＝ DS 的值，也就是一道 `push ds` 落在不該落的位置。
**舊版完全不執行那一段**（同一段堆疊的 35 筆寫入全是 `0374:xxxx`）。

## 找第一個分歧：比 guest 指令序列，不要比步數

按步數二分會找到「第 30–50 步就分歧」，但那是**假的**：新版的 INT 走一個
guest 端的 stub（段 `0050`），每次多兩道指令——

```
新: 0100:01BA → 0050:0000 → 0050:0002 → 0100:01BC
舊: 0100:01BA → 0100:01BC              （執行器直接處理，不碰 guest 堆疊）
```

所以指令計數本來就會偏移。**把 stub 段濾掉再比**，第一個真正的分歧在
第 151 道 guest 指令：

```
舊: … 053E:04E0  053E:04E6  053E:04EE …
新: … 053E:04E0  053E:04E6  053E:04E8  053E:04EA  053E:04EB  053E:04EC  053E:04EE …
```

倒出那一段的位元組（線性 `0x58C0`）：

```
053E:04E0  26 80 3e 00 00 00   cmp byte ptr es:[0000], 0
053E:04E6  74 06               jz 04EE          ← 舊版 taken、新版沒有
053E:04E8  f2 ae               repne scasb      ← 新版多走的：掃描環境
053E:04EA  46                  inc si
053E:04EB  ae                  scasb
053E:04EC  75 fa               jnz 04E8
```

`ES = 00D0`。倒兩版的環境區塊：

```
舊  PSP+2Ch = 00C0   段 00C0 ＝ 00 01 00 "C:\RICH2\RUN."              ← 空環境
新  PSP+2Ch = 00D0   段 00D0 ＝ "COMSPEC=C:\COMMAND.COM" 00 00 01 00 …
```

第一個位元組 `00` vs `'C'`——**一個位元組決定走哪一條路**。

## 為什麼是繞過不是修好

`-empty-env` 讓環境字串區留空，`GIN3.COM` 就跑得完 2.2 億道指令、整張畫面
都畫出來。但**真 DOS 的環境非空，而這個遊戲在真機上跑得動**，所以掃描那條
路上的東西才是真正壞掉的地方——直接原因是它後來要求把記憶體區塊撐到
`0E00` 段而配置器回「只有 `0040`」（`resize` 只看 arena 裡的下一塊）。
那一段還沒修。

## 錯過的四個候選（都排除了，記下來免得重查）

| 候選 | 為什麼像 | 怎麼排除的 |
|---|---|---|
| CPU 位址遮罩（`c8aa69a`） | 動到位址環繞 | 它的前一個 commit 也崩在同一步數 |
| EMS entry 用 `IRET` 而非 `RETF` | dosgolem 自己有一條 XMS 的測試就寫著這個形狀 | `0100:01BA` 的位元組是 `CD 67`（**int 67h**），IRET 才對；改 RETF 程式立刻退出 |
| INT stub 讓 SP 漂 | 新版多兩道指令、又動 guest 堆疊 | 量 `int 67h` 前後的 SP：`0100:236C` → `0100:236C`，**平衡** |
| 計時器頻率（PIT 分頻正確化） | 新舊的畫面時序差很多 | `-tick` 試 0／5000／50000，三種都崩在同一點 |

## 三條方法

- **指令計數偏移會讓「第一個分歧」假得很有說服力。** 按步數二分一路收斂到
  「第 30 步」，而那只是 INT stub 多兩道指令的累積。**先問「兩邊的計數基準
  一樣嗎」**，不一樣就濾掉不可比的部分再比。
- **從崩潰點往回追會撞牆。** 崩潰在 #120,561,079，根因在第 151 道指令——
  中間隔了一億兩千萬道，而且每一個中間現象（配置失敗、堆疊被寫壞）都
  自成一個可信的故事。**正面比對兩版的執行路徑**才把它夾出來。
- **註解說「這不是某個問題的修法」的東西，正是要先看的。** loader 那條
  `COMSPEC=` 的註解寫著「曾經拿它試…症狀完全沒變…留著純粹是因為它比空環境
  更接近真 DOS，不要以為它修好了什麼」。**沒有修好任何東西、卻改變了行為的
  改動，是換版本時第一個該懷疑的。**
