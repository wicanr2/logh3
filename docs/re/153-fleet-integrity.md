# `艦隊[+0x3C]` 是編制完整度

[`docs/re/151`](151-planet-capture-condition.md) 留下的最後一個問號：
打行星時拿 `艦隊[+0x3C]` 與「防衛力還剩幾成」比大小，而那一格的值在收據
裡是 99–100，語意不明。

## 誰寫它

用 `tools/scripts/field_xref.py` 掃 `+0x3C` 的所有存取，兩處寫入常數
**100**（`C6 45 3C 64` 與 `C6 47 3C 64`），其中一處（線性 `0x2A802`）
就在 `docs/internals/33` 記過的「把各分隊的回轉／巡航／戰鬥速度取最小值
寫進 `+0x4D`／`+0x4E`／`+0x4F`」那支後面——也就是**重算艦隊彙總值**的
地方。另一處在建艦隊的時候。

真正算它的在段 `1261`：

```
di ＝ 0 ; n ＝ 0
對每個編制槽：
    艦艇 = 池[槽]
    if 艦艇[+0x08] == 0: 跳過                  ; 沒艘數的不計
    di += 1261:03FB(艦隊, 艦艇)                ; 這一支的百分比
    n++
if n == 0: 艦隊[+0x00] |= 8 ; 回               ; 全滅
艦隊[+0x00] &= ~8
艦隊[+0x3C] ＝ di ÷ n                          ; ★ 算術平均
```

而每一支的百分比（`1261:03FB`）：

```
提督 ＝ ds:B77C ＋ 艦隊[+0x04] × 28            ; 提督表，一筆 28 bytes
折算 ＝ (艦艇[+0x0A] − 艦艇[+0x08]) × (200 − 提督[+0x0B]) ÷ 100
折算 夾在 艦艇[+0x0A] 以下
回 (艦艇[+0x0A] − 折算) × 100 ÷ 艦艇[+0x0A]
```

所以

> **`艦隊[+0x3C]` ＝ 各分隊「(滿編 − 折算損失) × 100 ÷ 滿編」的算術平均**，
> 只算還有艘數的分隊；折算損失把實際損失乘上 `(200 − 提督[+0x0B]) ÷ 100`。

提督的 `+0x0B` 越大，折算越小、艦隊看起來越完整——是一項「耐打」的能力。
收據裡五位提督的值是 112／89／143／104／106。

順帶：**平均低於 50 會走另一條分支**（`cmp al, 50`），還沒讀。

## 對拍

`aspre` 與 `gunpre` 兩份傾印（都在回合結算的階段邊界拍的，那時原版的值
是最新的）各 18 支在場艦隊，**36 個值逐一相同**
（`rules.TestPlanetAssaultMatchesOracle` 裡順帶驗）。

⚠ 折算的那個乘數在這份樣本上**驗不出來**：五支艦隊的分隊幾乎滿編，
損失是 0 或 1，乘上 `(200 − X) ÷ 100` 之後整數捨去仍是 0。所以
「乘數 ＝ `(200 − 提督[+0x0B]) ÷ 100`」目前是 **strong inference**
（逐行讀出來的），與「直接用 現有 ÷ 滿編」在這份收據上結果相同。

`post` 那兩份傾印對不上——不是公式錯，是**那個值還沒重算**：傾印拍在
扣完艘數之後、重算之前。

## 可重用的規則

- **「哪一份傾印的值是最新的」要當成問題問。** 同一個欄位在階段邊界拍的
  傾印對得上、在動作剛做完拍的對不上；先懷疑時機，再懷疑公式。
- **對不上的樣本要看它能不能分辨兩個候選公式。** 這裡兩個公式在整份
  收據上結果完全相同，所以收據**不是**「乘數正確」的證據——那一項只能
  標 strong inference。
