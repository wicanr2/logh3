# 情報收集畫面的最後三個像素

`info1e` 差 3 個像素，全在 `(368–370, 160)`：原版是色 3，remake 畫成色 7。

那三點是**游標的尾端**。箭頭在畫面上從 `(360,145)` 開始、16 列高，
最後一列只剩三個描邊像素，落在 y ＝ 160；而 y ＝ 160–161 正好是第一個
分頁鈕「治安」的上緣立體邊（色 7，`../internals/31-text-plane.md` 的
樣式旗標 `0x08`）。原版把游標畫在最上面，所以那三點蓋過立體邊。

## 規格裡的表示法

抽規格的工具（`tools/scripts/overlay_spec.py`）沒有把這隻游標當游標處理
——`tools/specs.sh` 給的是 `-2`（「這一層把游標整個蓋掉」），於是箭頭
被當成一個 14×15 的小框量進 `boxes`，而超出那 15 列的最後一列補成一條
純色塊（`rules` 的 `368:160:3:1:3`）。

視窗的繪製順序原本是

```
外框 → boxes → rules → tabs → 內容
```

`rules` 排在 `tabs` 前面，分頁鈕的立體邊就把那三點蓋掉了。改成

```
外框 → boxes → tabs → rules → 內容
```

三點回來，整張 0 / 307,200。

## 試過但更糟的一條路

把游標改成規格的正規欄位（`mouse: {x:360, y:105}`）、拿掉那個小框與純色塊，
看起來比較乾淨，實際上 **744 個像素不對**：抽規格的工具看到游標壓在
`boxes[0]` 上，就自動加了 `after_box_fills`，把三個分頁鈕的內部在游標之後
重填一次，連字一起洗掉。那個機制是給「存進度」那種**原版真的會重刷**的
畫面用的，這張沒有重刷。

`rules` 於是不只是「報告視窗裡的表格分隔線」，它同時是這一層的**最上層補丁**
——一覽表那三張（`lst1e`／`lst2e`／`lst3e`）的
`468:158`、`469:159`、`468:160` 也是同一回事。註解已經補進
`internal/screen/maingame.go`。

## 收穫

> 三個像素的差，成因與三百個像素的差沒有兩樣：**畫的順序**。
> 而順序錯的症狀只有在兩層剛好重疊、而且顏色不同的那幾個點上看得見。

也因為這樣，「差幾個像素」這個數字本身不足以判斷嚴重程度——3 和 744
可以是同一個 bug 的兩個表現。要看的是**差在哪、原版是什麼色**。
