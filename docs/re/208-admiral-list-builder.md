# 208 — `28E0:0103` 的 `0x25` 是一組旗標：同陣營 ＋ 沒有職務 ＋ 沒帶艦隊

AI 收提督清單一律走 `28E0:0103(&清單, 星域, 0x25, 0)`。那個 `0x25`
在 `unsolved` 裡掛了很久，被當成「清單種類（提督）」。**它不是種類，
是一組過濾旗標。**

## 整支

線性 `0x28F03` 起：

```
28E0:0103(&清單, 星域, 旗標, 參4):
    ; 先收全部 82 名
    對 i = 0..81：提督[i][+0x00] != 0FEh → 清單[n++] = i

    星域 != 0FFh → 28E0:0227(清單, n, 星域)      ; 只留 +0x0A == 星域 的
    旗標 bit0    → 28E0:028E(清單, n, ds:8F1D)   ; 只留 +0x01 == 陣營 的
    旗標 bit1    → 28E0:02F5(…)
    旗標 bit2    → 28E0:035C(清單, n)            ; 只留 +0x00 == 0FFh 的
    旗標 bit3    → 28E0:03B6(…)
    旗標 bit4    → 28E0:0410(…)
    旗標 bit5    → 28E0:047E(清單, n)            ; 只留 +0x09 bit7 有設的
    旗標 bit6    → 帶第四個參數的那一支
    回 n
```

每一支都是「原地壓縮」：掃清單、留下合格的、回新的筆數。

`0x25` ＝ `0010 0101` ＝ **bit0 ｜ bit2 ｜ bit5**：

| 位元 | 條件 | 意思 |
|---|---|---|
| 0 | `+0x01 == ds:8F1D` | **同陣營** |
| 2 | `+0x00 == 0xFF` | **沒有職務** |
| 5 | `+0x09` bit7 有設 | **沒有帶艦隊** |

加上底層那道 `+0x00 != 0xFE`，以及星域參數不是 `0xFF` 時的
「只留在那一格的」（`28E0:0227` 比的是 `+0x0A`，順帶證實那一欄是
所在星域）。

## 這個組合我們早就寫過

`docs/re/43` 的不穩事件挑的是「在這個星域、`+0x00 == 0xFF`、
`+0x09` 最高位有設」的提督，`docs/internals/08` 把它總結成
**「在那一格、沒有職務、也沒有帶艦隊的閒置提督」**。

`0x25` 就是同一組條件，只是把星域那一項換成參數：
`2D76:02FA` 傳 `0xFF`（不限星域）、`2E54:0513` 傳首都。

## remake 改了什麼

`internal/game/originalbrain.go` 的 `admiralCandidates` 原本是
remake 自己決定的「同陣營 ＋ 不在 `g.fleets` 裡」。現在照量到的加上
**`+0x00 == 0xFF`（沒有職務）** 與 **`+0x00 != 0xFE`**。

**「沒有帶艦隊」仍然由 `g.fleets` 推**，不是讀 `+0x09` bit7——
`docs/internals/08` 記著一個待驗：載入時 `+0x09` 被夾成 `0x7F`
（最高位一定是 0），若 bit7 真的是「沒帶艦隊」，載入後就不會有人合格。
那個矛盾沒解之前，remake 用自己維護的艦隊表更可靠，這一點標在註解裡。

## 一條方法

**參數的名字是推論，不是證據。** `0x25` 被記成「清單種類（提督）」是因為
兩個呼叫端都傳同一個值、而且回的都是提督——**一個常數只出現一種值的時候，
「它是什麼」完全沒有被觀察到**。展開成位元之後才看得出它是三個獨立條件。
