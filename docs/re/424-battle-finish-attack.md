## 原版非零守軍

原版`17A0:00AC`返回符合條件的池筆數；`203A:04D1`才是守軍艘數消費端。
第89輪42次查詢筆數為零，因此該批守軍也為零；不能由此推廣所有勝方占領。

已證實：

- 查詢讀DS:9896 word筆數、DS:98BA池word清單，依SHIP+00陣營與SHIP+1E bit7篩選。
- 距離讀SHIP+34/+36現在座標；距離大於行星查詢半徑才排除。
- 查詢不讀艦隊士氣bit0，不因敗方失去戰意而排除它。
- 守軍消費端只加艦種0／1，艘數加總飽和65535，最後除100。
- 20B4:0E7E把守軍加防衛力，以word回繞後除一般10／要塞20。

七案從同一8-1完整保存自然到8-5。在入口明示移動敗方分隊，保留失去戰意旗標。
兩次輸出逐byte相同，原版JSON SHA-256
`85fbd698622c307051183167d2315e9977abe5cac8fc8068611b31f4287ee335`。
16次查詢筆數及守軍結果符合獨立幾何／飽和模型。

| 注入 | 查詢筆數 | 守軍 |
|---|---:|---:|
| 近距一個3000艘分隊 | 1 | 30 |
| 同一分隊設Out bit7 | 0 | 0 |
| 同一分隊移遠512 | 0 | 0 |
| 近距兩個3000艘分隊 | 2 | 60 |
| 近距65535與1艘 | 2 | 655 |

另補回合0與反向勝方。65535艘屬格式邊界注入，不能當正常編成。
近距與Out控制案的SHIP終態有20 bytes不同，WORK有2 bytes不同；其餘表相同。
這個差異證明守軍會改變實際戰損，不能以固定0接戰場勝方占領。
