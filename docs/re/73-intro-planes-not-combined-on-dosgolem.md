# 開頭動畫的畫面對不上：執行器忽略顯示起點（已修）——但還有一層沒看到

`docs/re/72` 把解碼器解出來之後，剩一件事沒做到：拿解出來的畫格去比
執行器畫出來的畫面，**一格都對不上**。這一輪找出理由——不是解碼器，
是執行器少了一塊。

## 缺的是顯示起點

搬到 VRAM 那四趟 `rep movsw` 的目的地是 `cs:[001A]`，而那個變數在
**`0000` 與 `6D60` 之間交替**（`docs/re/36` 就記著「畫面在翻頁」）。
`0x6D60` ＝ 28,000 ＝ 350 × 80，正好是 mode 10h 一整頁。所以開頭動畫是
**雙緩衝**：解好的一格搬到背景頁，再把顯示起點切過去。

dosgolem 的 `PlanarPixels` 從 **VRAM 位移 0** 開始組像素，
CRTC 的顯示起點（`3D4` index `0C`／`0D`）根本沒有被記錄——
`grep 0x3D4` 在整個 repo 一個都找不到。所以遊戲顯示第 1 頁的時候，
倒出來的是第 0 頁。

## 這幾件事不是原因（查過了）

- **map mask 有生效。** 畫面的色號分布是
  `8`(11,891)、`4`(6,045)、`2`(2,504)、`6`(2,120)、`12`(1,596)、`1`(1,301)
  ——**四個 plane 拿到的位元組不一樣**，不然只會有 0 與 15 兩種色號。
- **`out dx,ax` 有拆成兩個埠。** 那段程式用的是
  `mov dx,03C4 / mov al,02 / mov ah,0X / out dx,ax`（16 位元 OUT），
  `internal/cpu/ops.go` 的 `0xEF` 寫 `dx` 與 `dx+1`，是對的。
- **`rep movsw` 有走 planar 路徑。** `Write16` 拆成兩個 `Write8`，
  `Write8` 對 `A0000–AFFFF` 會呼叫 `planarWrite`。

## 修好了，但畫面還是對不上

dosgolem 加了 CRTC（`3D4`／`3D5`）的記錄，`PlanarPixels` 從 index
`0C`／`0D` 的起點開始組（dosgolem `20e4583`）。實測：

- 動畫那張的顯示起點是 **28000** ＝ `0x6D60`，正是第二頁——假設成立；
- 一般畫面（`main1eB`，走同一條玩家路徑到戰略地圖）的起點是 **0**，
  而且 `screen.bin` 的 SHA-256 與改之前的 `main1e` **完全相同**。
  所以既有收據不受影響，不必整批重做。

**但畫面仍然對不上解出來的畫格。** 再往下查到的：

- 收據 `intro52` 的 `cs:001A` ＝ 0，而顯示起點是 28000——遊戲正在
  「顯示第 1 頁、往第 0 頁畫」，所以畫面上是**上一格**。這解釋了
  畫面與解碼緩衝區只有七成位元組相同，不是缺陷。
- 拿解碼緩衝區去比「任意一段連續畫格的累加」（用前綴 XOR 的雜湊，
  374 × 374 種區間全掃）——**一個都不是**。
- `cs:001C` 在 `intro40` 是 57,395、在 `intro52` 是 40,216（**變小了**），
  所以它確實是「這一塊裡的位移」、換塊會重來。但兩次換算出來的檔案位置
  （122,720 與 105,581）**都不是影格邊界**，±40 也不是。

最後一條與「374 格逐格對上長度表」直接衝突：我的解碼器每一格吃掉的
位元組數正好是長度表的值，執行期卻停在別的地方。兩邊都有硬證據，
所以中間一定還有一層沒看到——**下一輪從這裡開始**，不要再改解碼器。

可以先做的：對兩個解碼緩衝區設寫入監看，看一格的寫入是怎麼分佈的
（是不是一次解不只一格、或中途換過緩衝區）。

## 順帶：`cs:001C` 一輪只寫三次

同一輪對 `lin:0420C`（`cs:001C`）設寫入監看，45,000,000 步裡只有三次：

```
#34,706,915  0 → 38,991
#35,384,865  38,991 → 49,213
#36,682,236  49,213 → 57,395
```

三個值都**不是影格邊界**（±40 都試過）。`add cs:[001C],bx` 在反組譯裡
看起來是一格一次，那就對不起來——除非那個迴圈一次解的不只一格。
先記著，等畫面能對之後再看。

## 追記：解碼器一次吃掉幾萬個位元組，而且緩衝區不是「檔案前 64 KB」

`-regs-at 041F:01B2,041F:01EB`（外層迴圈入口與 `add cs:[001C],bx`）：

| | 步數 | BX（這一趟吃掉的位元組）| SI（起點） |
|---|---:|---:|---:|
| 第 1 趟 | 34,706,915 | **38,991** | `001E` |
| 第 2 趟 | 35,384,865 | **10,222** | `986D` |
| 第 3 趟 | 36,682,236 | **8,182** | `C05B` |

`SI` 每次前進 `BX`（`0x1E + 38,991 = 0x986D`），所以那三個數是連續吃掉的。
外層迴圈 `041F:01B2` 在 45,000,000 步裡只被踩到 **4 次**，間隔約 1,460,000
步——一趟吃幾萬個位元組，不是一格 78 個。

**緩衝區裝的也不是「檔案的前 64 KB」。** 第 34,700,000 步（第一趟解碼
之前）倒 `lin:175DE` 起 64 KB：

```
緩衝區 [0..39]      ＝ 檔案 [0..39]
緩衝區 [40..63,695] ＝ 檔案 [65,365..129,020]   （63,656 bytes）
緩衝區 [63,696..]   ＝ 別的東西
```

第 40,000,000 步倒出來**一模一樣**——中間沒有換過。所以載入器不是
「從頭讀 64 KB」：它讀了 40 個位元組，然後從 **65,365**（第 117 格的邊界）
讀了 63,656 個位元組。

## 這一條線目前停在哪

已經站得住的：
- token 語法與位元圖走法（`docs/re/72`，三個互相獨立的驗算）；
- 65,365 與 129,021 都是影格邊界，而且都等於「≤ 上一個邊界 ＋ 64 KB 的
  最大邊界」（`docs/re/71`）。

對不起來的：
- 執行期一趟吃 38,991 個位元組，而長度表的前幾格是 78／79／78；
- 緩衝區開頭那 40 個位元組是檔案的前 40 個，後面卻接第 117 格。

兩件事指向同一個缺口：**播放的順序與餵資料的方式還沒解**，不是編碼。
下一輪從「那 40 個位元組是什麼」開始——對 `lin:175DE` 設寫入監看，
看 DOS 讀檔是怎麼把這個緩衝區填出來的（`WriteBytes` 會走 `Write8`，
監看看得到）。**不要再改解碼器**。

## 追記二：緩衝區是被**填了兩次**

對 `lin:175DE–17610` 設寫入監看（收據 `introfill`）：

| 步數 | 寫入者 | 內容 |
|---:|---|---|
| #17,897,720 | `041A:0035` | 從緩衝區位移 **0** 起，寫 `00 00 29 3F C0 80 …` ＝ **檔案位移 0** |
| #29,800,127 | `041A:0035` | 從緩衝區位移 **41** 起，寫 `00 1E 26 2E 2B 3D 06 …` ＝ **檔案位移 65,365** |

兩次都在第一趟解碼（#34,706,915）**之前**。所以緩衝區最後長這樣：

```
[0..40]   ＝ 檔案 [0..40]      （第一次填剩下來的）
[41..]    ＝ 檔案 [65,365..]   （第二次填蓋上去的）
```

而解碼器從**位移 0** 開始吃（`SI = 001E` ＝ 緩衝區位移 0，
`cs:001C = 0`）——先吃那 41 個位元組，再接上第 117 格。

所以那 41 個位元組不是殘渣，是**解碼器真的會讀到的東西**。
兩件事要一起解釋：為什麼第二次填從位移 41 開始、以及為什麼那個位置
正好是第 117 格的邊界。

填緩衝區的常式在 `041A:0035`（`OPEN.EXE` 的載入段），下一輪從那裡
反組譯——它算位移的方式就是答案。
