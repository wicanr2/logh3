# 開頭動畫在 dosgolem 上四個 plane 沒有合起來

`docs/re/72` 把解碼器解出來之後，剩一件事沒做到：拿解出來的畫格去比
執行器畫出來的畫面，**一格都對不上**。這一輪找出理由——不是解碼器，
是執行器。

## 證據：畫面上沒有色 15

收據 `intro52`（`-steps 52000000`，動畫進行中）的色號分布：

```
色 0  191,367     色 8  11,891     色 4  6,045
色 2   2,504      色 6   2,120     色 12  1,596
```

**色 15 一個像素都沒有**，而且佔多數的是 8／4／2／1 這種**只有一個
位元**的色號。

同一時期解出來的畫格不是這樣：

| 格 | 非零像素 | 最多的色號 |
|---:|---:|---|
| 120 | 9,279 | 15（3,034）、14、1 |
| 200 | 20,162 | 10、8、12 |
| 340 | 5,623 | 4、1、3 |

四個 plane 疊起來本來就會大量出現 15（四個位元都有）。畫面上一個都沒有，
表示**四個 plane 沒有疊在同一批像素上**——每個 plane 各自落在別的地方。

## 判準：這是執行器的問題，不是遊戲的

解碼是純 CPU ＋ 記憶體，畫出來才碰到 VGA。搬到 VRAM 的那一段是
`041F:0206`／`0218`／`022A`／`0241` 四個 `rep movsw`，每次之前先寫
序列器 index 2（map mask）選一個 plane（`docs/internals/10` 記過同一種
寫法）。**map mask 沒生效**的話，四趟就會各自寫到同一份位元組上、
或都寫進 plane 0——畫面上就是現在這個樣子：單一位元的色號滿天飛、
沒有 15。

畫面上看起來像「三艘船並排」也是同一件事的表徵：同一格的四個 plane
被攤到相鄰的位置去了。

`AGENTS.md`：**畫面或行為可疑時，預設懷疑對象是 dosgolem 的服務覆蓋，
不是「原版本來就這樣」。** 到目前為止每一個看似遊戲端的怪異行為，
根因都在執行器。

## 順帶：`cs:001C` 一輪只寫三次

同一輪對 `lin:0420C`（`cs:001C`）設寫入監看，45,000,000 步裡只有三次：

```
#34,706,915  0 → 38,991
#35,384,865  38,991 → 49,213
#36,682,236  49,213 → 57,395
```

三個值都**不是影格邊界**（±40 都試過）。`add cs:[001C],bx` 在反組譯裡
是一格一次，那就對不起來——除非那個迴圈一次解的不只一格，或者
執行器在這裡也有偏差。與上面那件事一起留著，等執行器修好再看。
