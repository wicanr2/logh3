# RE 14 — 資料段裡的熱區清單地圖

日期：2026-09-07
資料：`docs/internals/data/hotspot-lists.json`
產生：`tools/py.sh tools/scripts/hotspot_scan.py`
證據等級：**強證據**（掃出來的兩份與先前逐筆量過的完全一致）。

## 做法

熱區清單的位址每個畫面不同，由視窗結構傳進命中測試常式（`docs/re/09`）。
與其一個畫面一個畫面去攔，不如把整個資料段倒出來、直接掃「長得像清單」
的資料：

```
tools/go.sh run ./cmd/probe … -dump-mem '54B3:0000:65535:/src/workplace/ds54b3.bin'
```

判準是一筆 12 bytes、格子座標 < 40／< 30、寬高 1–12 格、啟用旗標 0 或 1、
**項目索引從 0 開始遞增**，而且整串以 `FF FF` 結束。

驗證：掃出來的 `DS:09D6`（主畫面，2 筆）與 `DS:26E2`（建造計劃，16 筆）
與先前逐筆量過的完全一致。

把清單與畫面對起來，這是下一步。

## 為什麼要有這張表

主畫面只有兩個熱區，往下的路只能靠既有分支上的按鈕。先前靠猜座標點，
命中率很低（會計報告是掃五個位置才掃到的，另外四個都 0 差異）。
有了這張表就不必猜——只要知道當下畫面用的是哪一份清單，
可點的位置就是確定的。

## 每一筆的 `+8` 指向一段中文

追下去發現 `+8` 的 far 指標指到 `\0` 結尾的 Big5 字串，25 份清單解出來
全部是通順的中文（戰略命令、一覽表、系統指令、出擊、陣形、占領、待命…），
沒有一份是亂碼——所以那個欄位確實是「這一項叫什麼」。

但**不能因此說它是畫在按鈕上的字**：主畫面那兩筆解出「確認」「變更」，
而畫面上對應位置是兩個沒有字的灰色小框。它比較像動作名稱或狀態列文字，
確切用途**未確認**。

完整對照表在 `docs/internals/23`。

## 光有格子座標還不夠

熱區座標是相對視窗原點的。主畫面那份的原點是格子 (10,3)（與
`screen-main-game.json` 記的一致），拿它去套「戰略命令」那一份
（`0C52`，格子 (1,0)／(7,0)／(13,0)）點三個位置，畫面 0 差異。

所以下一步不是再試座標，是找出「當下畫面用的是哪一份清單、原點是多少」。
`docs/re/09` 記的 `37A9:01F9`（命中測試）與 `341B:044A`（座標換算）是段值，
在 dosgolem 修好 EXEC 記憶體回收之後已經失效，要改用位元組簽章重新定位
（`docs/internals/00-README.md`）。

## 找到登錄常式

清單位址不在資料段裡（`-find "D6 09 B3 54"` 全記憶體沒有命中），
因為它是**程式碼裡的立即值**。改搜 `BB <位移>`（`mov bx,imm16`）就中了：

```
-find "BBD609,BBE226,BB520C,BB002A"
  BB D6 09 → 06CA3、06D4C        （主畫面那份）
  BB E2 26 → 0F951、0FBFA        （建造計劃那份）
  BB 52 0C → 053B4、05863、07012 （戰略命令那份）
  BB 00 2A → 10235、107D0        （艦隊編成那份）
```

把周邊倒出來，四處長得一模一樣：

```
1E BB <清單> 53          push ds; mov bx,清單; push bx
<推視窗指標>
9A 0F 00 A9 37           call far
```

所以 `9A 0F 00 A9 37` 就是「把清單掛到視窗上」的簽章。掃整份記憶體
找到 **25 處**，正好等於清單數——每一份清單都恰好被登錄一次。

## 為什麼還是點不到

25 處裡有 14 處能從程式碼直接讀出是哪一份清單；但**多數的視窗指標是
函式參數**（`FF 76 xx` ＝ `push [bp+xx]`），原點要執行期才知道。
靜態分析到這裡為止，下一步要在那 25 個位址上攔一次，記下當時的
視窗結構內容。對照表在 `docs/internals/23`。
