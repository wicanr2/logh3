# 270 — 防拷問答的 Enter 一直是好的；跑飛在它之後

日期：2026-09-10
執行器：`logh3-oracle`（基底 dosgolem main `c8aa69a`）對 `logh3-com-support`（`ef5be47`）
狀態：症狀與排除範圍 **confirmed**；肇因 **未定**（已縮到「main 併入 COM 支援那一刻」）

## 症狀

`logh3-oracle` 跑收據 `main1e` 的輸入序列，畫面停在防拷問答、看起來像
「數字打進去了但 Enter 沒作用」。實際上：

- **Enter 有生效。** 跑到 2.2 億道指令時調色盤 768 個位元組**全 0**——
  遊戲收下答案、把畫面淡出了。色號陣列沒變是因為淡出只動調色盤。
- 真正的問題在那之後：第 117,673,624 道指令，`1700:88C0` 的 `retf`
  取到堆疊上一個從來沒有被推進去的返回位址，跳進沒配置過的
  `7555:7500`，再 `iret` 到 `8000:0055`，之後就在全零區每次 `+2` 地爬
  （`00 00` ＝ `add [bx+si],al`，暫存器全不動）。

`typed138`（只送數字、不送 Enter）在新執行器上**畫面與調色盤都逐位元組
重現**，所以到防拷問答為止一切正常。

## 已經排除的（新舊逐項對過，全都相同）

| 對象 | 結果 |
|---|---|
| `int 21h` 呼叫序列（到讀 `STRMAP.BIT`／`.RGN` 為止） | 相同，步數差 ~300 |
| EMS 頁框內容（65,535 bytes） | 差 0 |
| EMS 頁框段位址（`E000` → `D000`） | 改回 `E000` 照樣跑飛 |
| 著色迴圈 `2376:0BE1` 前四趟的 `SI`／`DI`／`BP`／`CX` 與遮罩 | 相同 |
| 著色後的工作副本（48,000 bytes） | 差 3 |
| 畫面色號（到 #117,200,000） | 差 0 |
| `1700:88xx` 那段機器碼（線性 `1F800`–`1F8FF`） | 差 0 |
| 環境區塊的程式路徑字串（改成與舊版同一串） | 照樣跑飛 |
| `AH=4Ah` 之後移動 `freeSeg` | 拿掉之後死得更早 |
| arena 內區塊的真正 resize | 關掉之後不跑飛，但畫面仍然不對 |

## `-xscale 2` 是假的修法

新版有一支 `-xscale` 可以強制滑鼠水平倍率。設成 2 之後遊戲「畫得出畫面」
——但那是**另一條路**：遊戲收到兩倍的 X，直接進了勢力選單，**根本沒有
經過防拷問答**（收據 `cb1` 不送任何按鍵，`-xscale 2` 下卻已經在選單上）。

新舊兩版的倍率邏輯其實一樣（`640 / PixelWidth()`，mode 12h 給 1），
**收據上的座標不用改**。

## 縮到哪裡

判準：跑 `main1e` 的旗標到 2.2 億道指令，畫面與收據逐位元組相同才算通過。

- `logh3-com-support` 分支尖端（`ef5be47`）：**差 0**。
- 分支被併進 main 前的那一點（`8c8af90`）：**差 2451**——少的是
  `35d4cc3`「planar 實作 read mode 1（color compare）」，那是四個沒被
  併進 main 的 commit 之一，`logh3-oracle` 已經帶著它。
- main 併入 COM 支援的那個 merge（`52f7563`）以及它之後的每一個：
  **差 174,800、`CS:IP = 8000:C18F`**（跑飛）。

所以肇因在 main 自己那半邊，而不是分支。再往前二分卡在一個歷史形狀上：
main 的第一父線裡有那些分支 commit 的**重放版本**，而它們早於
`-dump-ega`，判準跑不起來（`git bisect` 全部 skip）。要繼續就得換一個
在那個年代也量得到的判準（例如 `-dump-vram` 或記憶體雜湊）。

## 三條方法

- **色號陣列相同不等於畫面沒變。** 平面模式的畫面是「色號 ＋ 調色盤」
  兩份狀態，淡出只動調色盤。只比色號會把「已經換狀態」讀成「輸入沒生效」，
  而且差異剛好是 0，錯得很有說服力。**判斷輸入有沒有效，兩份都要比。**
- **「畫得出東西」不能當二分判準。** 走錯路的執行也會畫出畫面。第一次用
  「調色盤還有非零位元組」當判準，夾到的是一個只是換了一條路的 commit
  （`8ff6087`，`-xscale` 預設改成自動）。**判準要釘住「同一條路的同一個
  結果」——這裡是「與收據逐位元組相同」。**
- **兩版一路對得上，就不要再往前追細節。** 指令序列、記憶體、畫面全都相同
  卻仍然分歧時，繼續加細節只會得到更多「也相同」。改成對 commit 二分，
  一次就把範圍從一億兩千萬道指令縮到一個 merge。
