## 先看當初的證據，再談推翻

`docs/re/108`「第 1–116 格從來沒被解過」與 `docs/re/116`「兩個 64 KB 緩衝區
只差 40 個位元組」都不是猜的，兩者各有一手量測：

- `docs/re/108` 的收據 `intrord`（`-regs-at 041A:0035`）量到兩次讀檔的
  目的地是 `175C:001E` 與 **`175F:0016`**，相差 40；
- `docs/re/116` 的收據 `openmem` 把那 40 個位元組與 `IBM16.350` 逐位元組
  比過（`tools/scripts/intro_bufoverlap.py`），並反組譯出 C 執行庫
  `053E:194C` 的 16 位元加法在 `farmalloc(65500)` 上溢位、把區段結尾寫成
  `0x0000`。

兩份收據都錄在 **`4732181` 之前的 dosgolem** 上。那一版的執行器在子行程結束
時不釋放它名下的 MCB，而假 MCB 標頭是寫進客體記憶體的，所以 DOS 的空間表
本身是壞的（`docs/re/270` §一：同一個 bug 把 `3705:057E` 的 `add sp,24h`
改寫成 `add sp,4Dh`）。**壞掉的空間表決定了第二塊記憶體配到哪裡**。

修好之後在同一個位置重量（收據 `introfull`，`-regs-at 041A:0035`）：

| | 舊執行器 | `2e9dd3b` |
|---|---|---|
| 緩衝區 A | `175C:001E` ＝ `175DE` | `175C:001E` ＝ `175DE` |
| 緩衝區 B | `175F:0016` ＝ `17606` | **`275D:0016` ＝ `275E6`** |
| 相差 | 40 bytes（整片重疊）| 65,544 bytes（互不相干）|

`docs/re/270` 量到的四塊 `AH=48h` 配置（`175C`／`275D`／`375E`／`44AE`）
正好對得上：plane 緩衝區也跟著從 `2760`／`34B0` 搬到 `375E`／`44AE`。

**`docs/re/116` 對遊戲本身那段算術的分析仍然成立。** 在 `#40,000,000` 倒
緩衝區 A 的堆積表頭（`-dump-mem-at 40000000:lin:175C0:64:…`）：

```
175C0: 5C 17 | 03 00 | 00 00 | 14 00 | 14 00 | FE FF | 00 00 | 5D 27
        段     旗標    區段結尾 ← 0      哨兵     FFFE            下一段
```

區段結尾**照樣被寫成 0**，第二次 `farmalloc` 照樣另開一段。差別只在
**另開的那一段落在哪裡**：空間表正常時 DOS 給的是 `275D`，一塊完整的
64 KB，不再蓋掉前一塊。所以被推翻的不是那段算術，是它的後果。

`docs/re/261` 的「500M 步裡只有 25 組解碼呼叫、間隔 71–4861 個 tick」同樣
過期：它引用的收據 `introsched` 已經在 2026-09-11 08:23 重錄過，同一組旗標
現在錄到 **1,120 次命中（280 格）**，SI 序列是 `001E → 006C → 00BB → 0109`
——差值 78、79、78，正是 `IBMFLS16.350` 的前三格長度。

## 逐格時程怎麼量的

一次跑（收據 `introfull`）同時斷在兩個地方：

- **`041A:0035`**（讀檔常式的 `int 21h` 之後，`docs/re/116`）：堆疊上
  `[bp+8]` 是目的地位移、`[bp+0A]` 是段、`[bp+0C]` 是長度。43 次讀檔。
- **`041F:024B`**（解碼器進入點）：`DS:SI` 是這一格在緩衝區裡的起點，
  `BX` 是格內的段位移，`DX` 是 plane 的目的地偏移。1,684 次命中，
  連續四次同一個 `(DS, SI)` ＝ 一格的四個 plane，共 **421 組**。

把兩邊接起來就得到檔案位移：`塊的檔案起點 ＋ (SI − 緩衝區基底位移)`。
**塊號不能用「長度累加」推**——動畫跑完載入器會回頭重讀最後幾塊，累加會
一路偏掉；分塊表（`docs/internals/data/intro-chunks.json`）那 30 個長度彼此
互異，所以用長度反查是一對一的。腳本 `tools/scripts/intro_schedule.py`。

自我檢查：**421 組的檔案位移全部落在 `IBMFLS16.350` 算出來的格邊界上**，
一組都沒有落在中間。421 組的內容是 0–348、350–373，再加上 350–373 兩遍。

## 播出來的順序

```
格 0 → 348      一格 75 刻（≈128.7 ms，約 7.8 fps），照檔案順序
  └ 格 102 前停 336 刻（≈577 ms）      ← 落在 97–102 那段全黑
  └ 格 247 前停 2,236 刻（≈3.84 秒）   ← 落在 244–251 那段全黑
格 349          從來沒有被解碼
（四個 plane 緩衝區清成 0）
格 350 → 373    一格 77 刻（≈132.2 ms）
  └ 格 350 前停 2,850 刻（≈4.89 秒）
  └ 格 351 前停 1,798 刻（≈3.09 秒，只有第一趟有）
（再清一次緩衝區）格 350 → 373，接縫停 1,240 刻（≈2.13 秒）
（再清一次緩衝區）格 350 → 373
```

- 第一趟 0 → 373 是 **697,280,000 步 ＝ 34,864 刻 ≈ 59.8 秒**；
  含尾段三趟共 817,720,000 步 ＝ 40,886 刻 ≈ **70.2 秒**。
- 畫面內容：0–348 是一艘戰艦由遠而近的鏡頭（中間兩次全黑換場），
  350–373 是標題圖「銀河英雄傳說 III／SPACE WAR SIMULATION」淡入的迴圈。
- 尾段跑完三趟之後動畫結束（最後一次解碼 `#849,965,075`），
  `#913,165,418` 開始讀 `SPTIT.350`（標題畫面）。**三趟是量到的次數，
  由什麼決定還沒查**。

### 第 349 格被跳掉，成因是分塊表那一筆對不上

第 23 塊是 `檔案[1,400,255:1,430,100]`，而 `1,430,100` 正是第 350 格的
起點——也就是這一塊裝得下 **11** 格（339–349）。但載入器資料段
`070A:0000` 的每塊格數表第 23 筆寫的是 **10**，解碼器照表遞減，數到 0 就
換手，於是**第 349 格永遠不會被解**。

`docs/internals/19` 早就記著「回算的每塊格數與表上的值只有第 23 塊不同
（回算 11、表上 10），原因未解」。這一輪補上的是它的後果：那一筆差 1
就是原版少播一格。第 349 格的壓縮長度 1,421 bytes，畫出來相對第 348 格改
**748 個像素**——播出來看得到，只是它之後緊接著就被清緩衝抹掉了。

### 進尾段之前，plane 緩衝區被清成 0

收據 `introclear2`（`-watch 38668-3866A`，那是 plane 0 在第 348 格之後
非零的兩個位元組）：

```
#602,738,014  38668: BF→77  ip=041F:02D2   ← 解碼器最後一次寫
#658,215,818  38668: 77→00  ip=0349:056B   ← 載入器清掉
#659,766,102  38668: 00→4F  ip=041F:02D2   ← 尾段第一格
#752,814,654  38668: 4F→00  ip=0349:056B   ← 第二趟前再清一次
#813,034,645  38668: 4F→00  ip=0349:056B   ← 第三趟前再清一次
```

寫 0 的是 **`0349:056B`，載入器自己**（解碼器在段 `041F`），而且每一趟
尾段之前都清一次。這是尾段能夠迴圈的前提：XOR 累加沒有反向操作，不清就
會把上一趟的殘影疊進去。

## 兩件方法

**推翻一個斷言之前，先確認它當初站在哪一份收據上。** `docs/re/108` 與
`docs/re/116` 的推理鏈一節都沒有錯，錯的是底下那份收據錄在一個會改寫
遊戲記憶體的執行器上。分辨的方法不是重讀文件，是把同一組旗標在新執行器
上重跑一次——`175F` 變成 `275D` 這一個數字就把整條鏈的結論換掉了。

**「解不出來」有時候是上一版執行器的殘影。** 這一題從 `docs/re/104`
一路到 `docs/re/261` 花了六份紀錄，每一份都在正確地解釋一個不存在的現象。
`docs/re/270` 修好執行器之後沒有人回頭重問「那些結論還成立嗎」，
而 `docs/re/276` 已經把 22 份 `intro*` 收據標成「整塊不同、要重新對準」。
**收據轉紅是在提醒結論也要重驗，不只是畫面要重錄。**
