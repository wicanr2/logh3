# RE 104 — 開頭動畫：解出來的累加影像不在記憶體裡

`docs/re/73` 的結論是「兩邊都有硬證據，中間一定還有一層沒看到」，
並留了一句「下一輪從這裡開始，不要再改解碼器」。這一輪照做，
用的是既有收據 `intro52` 的 1 MB 傾印，**沒有新開收據**。

> ⚠ 本節推出來的「間距 18,176、每個 plane 後面 16 個位元組填補」是**錯的**。
> `docs/re/108` 用 `-regs-at` 直接量到四個來源指標，間距是 `0x46F0` ＝
> **18,160**（沒有填補），而 `docs/re/72` 記的 `34B16` 本身就差了 `0x30`。
> 下面那一段的推算建立在錯的位址上；結論（累加影像不在記憶體裡）
> 用正確位址重驗過仍然成立。

## 那不是兩個緩衝區，是同一張圖的兩個 plane

`docs/re/72` 記的是「兩個解碼緩衝區 `lin:27616` 與 `lin:34B16`」。
兩者相差 `0x34B16 − 0x27616 ＝ 0xD500 ＝ 54,528`，而

```
54,528 ÷ 3 ＝ 18,176 ＝ 18,160 ＋ 16
```

18,160 正是一個 plane（80 × 227）。所以那兩個位址是**同一張四 plane
影像的第 0 與第 3 個 plane**，間距 18,176（每個 plane 後面 16 個位元組
的邊界填補）：

```
plane 0  27616      plane 1  2BD16      plane 2  30416      plane 3  34B16
```

照這個版面讀出來，四個 plane 的非零位元組數是
**3,445／3,888／4,847／5,672**（各 18,160 中）——19–31%，
比一張畫好的船艦圖稀疏得多。

## 三種假設都不對

拿 `tools/scripts/intro_decode.py` 解出來的東西去比那四個 plane：

| 假設 | 結果 |
|---|---|
| 從第 0 格連續累加到第 N 格 | 沒有一格四個 plane 全對 |
| 單獨一格的差量（不累加）| 沒有一格四個 plane 全對 |
| 隔格累加（偶數格一組、奇數格一組）| 沒有一格對 |

「最像」的都落在第 97、98 格一帶——那是場景之間的黑幕，累加整個歸零
（`docs/re/72`），所以那只是「兩邊都很多 0」，不是證據。

## 決定性的否定結果

不再猜位址，直接問「**解出來的影像到底在不在記憶體裡**」：

- 對 374 格 × 4 plane 的累加影像，各取三個位移（6000／9000／12000）
  的連續 24 個位元組當簽章，濾掉幾乎全 0 的；
- 拿 753 個簽章去掃整份 1 MB 傾印（含 `A0000` 起的 VRAM）。

**一個都沒中。**

所以：**解碼器算出來的累加影像，在第 52,000,000 步時不存在於記憶體的
任何一處**。`docs/re/73` 說的「中間還有一層」不是「緩衝區找錯了」，
是解碼器的輸出與遊戲實際持有的東西**本來就不是同一個東西**。

## 下一輪從哪裡開始

不要再拿累加影像去比記憶體，那條路這一輪已經走死。改從**指令**那邊走：

- `docs/re/73` 記著搬去 VRAM 的四趟 `rep movsw`，目的地是 `cs:[001A]`。
  **那四趟的來源 `ds:si` 指到哪還沒量**——`-regs-at` 對那條 `movsw`
  的位址下探針就能拿到，那才是真正的解碼緩衝區位址。
- 拿到位址之後再對它設寫入監看，看一格的寫入是怎麼分佈的。

順帶記著：`intro52` 的傾印裡 `A0000` 兩頁各有 2,189 與 3,346 個非零
位元組——動畫的畫面高度是 227 列，而一頁是 350 列，所以影像不是填滿整頁。
