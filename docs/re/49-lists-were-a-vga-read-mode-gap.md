# RE 49 — 清單畫不出來的原因在執行器：VGA read mode 1 沒實作

日期：2026-09-07
執行器：dosgolem-logh3 `8c8af90`（發現）→ `35d4cc3`（修好）
收據：`s3sortie`（修前）、`s3sortie2`（修後）、`s3plane`、`s3cells`、`s3jin`、`s3glyph`
狀態：**根因 confirmed，已修**。承接 `docs/re/48`。

## 一句話

原版沒有畫錯，是 dosgolem 的 VGA 讀路徑少了 read mode 1（color compare）。
遊戲拿「color don't care ＝ 0 時讀回 `0xFF`」當全開的遮罩去寫字形，
執行器回的是 plane 值，底色所在 plane 為 0 的格子遮罩整個歸零，
字一個像素都不寫。

### 字元平面的格式（`ds:D81E`，40 欄 × 20 列 × 6 位元組）

| 位移 | 意思 |
|---|---|
| `+0` | 低 5 位 ＝ 擁有這一格的視窗編號；`0x80` ＝ 髒；`0x40` ＝ 用快取字形；`0x10` ＝ 走彩色文字路徑 |
| `+1` | 另一種模式旗標（bit0 ＝ 半形字） |
| `+2/+3` | 字碼（`+2` 低位、`+3` 高位；Big5 的首位元組在 `+3`）。`0xFF??` 是內建框線圖 |
| `+4` | 屬性：高 4 位底色、低 4 位字色 |
| `+5` | 樣式旗標：`0x01` 底線、`0x02` 網點、`0x04` 加粗、`0x08` 立體上下邊 |

一格 16×20 像素，畫面 640×400 置中放進 640×480，所以第 r 列的螢幕
`y = 40 + 20r`。

### 決定性的一組數字

同一張畫面裡：

| 位置 | 屬性 `+4` | 底色 | 結果 |
|---|---|---|---|
| 標題「待命中提督資料」 | `0x97` | 色號 9（`1001b`，plane 0 ＝ 1） | 畫得出來 |
| 提督名字 | `0x87` | 色號 8（`1000b`，plane 0 ＝ 0） | 一個像素都沒有 |

樣式旗標不是原因：把名字那幾格的 `+5` 從 `0x08` `-poke` 成 `0x00`，
立體邊消失了，字還是沒出現（收據 `s3attr`）。

## 根因

畫字之前 `2376:1835` 設的是：

```
GC[5] = 0x0B   ; write mode 3 ＋ read mode 1
GC[1] = 0x0F   ; enable set/reset 全開
GC[0] = 顏色   ; set/reset
GC[3] = 0x00 ; GC[8] = 0xFF ; GC[7] = 0x00   ; color don't care 全 0
```

畫字的指令是 `and es:[di], al`（`al` ＝ 字形位元組）。在 write mode 3
裡，寫進去的位元組是**遮罩**，所以有效遮罩 ＝ `讀回值 AND 字形`。
硬體上 read mode 1 配 color don't care ＝ 0 表示「哪個 plane 都不比」，
每個像素都算相符，讀回 `0xFF`，遮罩就等於字形本身。

dosgolem 當時回的是 `gc[4]` 選的 plane，於是遮罩變成
`plane0 AND 字形`——底色色號 9 的 plane 0 是 1（讀回 `0xFF`）字就出來，
底色色號 8 的 plane 0 是 0（讀回 `0x00`）字就整個消失。

修法與語意寫在 dosgolem 的 `docs/spec/017-planar-read-mode-1.md`，
單元測試 `TestPlanarReadMode1ColorCompare`。

## 兩個踩過的坑

- **`-regs-at` 的去重會吃掉整批命中。** 它刻意跳過「`DS:SI` 只往前 ≤16」
  的連續命中（blit 迴圈的雜訊）；而 `2376:040E` 每格 si 只加 6，
  所以同一輪掃描的幾百格只留下換列的那幾筆。第一次據此得到的
  「字形常式根本沒被呼叫」是**過濾器造成的假零**，要靠 `-watch`
  單一格子的髒位元被清掉才看得出來它其實有被呼叫。
- **屬性看起來像原因就先 `-poke` 試一次。** 樣式旗標 `0x08` 和「畫不出來」
  完全相關（整張畫面只有那些格子有 `0x08`），但一 poke 就證偽了。
  相關性在只有一個樣本的時候不值錢。
