# 281 — 防拷問答少的那 32 個像素是輸入游標；原版會閃，舊收據剛好停在滅的半週期

日期：2026-09-11
執行器：`logh3-oracle` `2e9dd3b`（`6841e68` 之後只多了一個 VGM 傾印功能；
本案的每一次擷取都在 `2e9dd3b` 上，並且與 `6841e68` 錄的 `cb1` 逐位元組相同——
`screen.bin` SHA-256 `10dd957db9f5a5d3c0954176b34e9c6e1f3ba885bfde0dc4a6de756f4f88ff61`）
狀態：**confirmed**（四個輸入位數各一個資料點；閃爍有 71 個取樣點的時間軸
與畫／擦兩支常式的指令數）

## 症狀

執行器修好之後（[`270`](270-enter-works-the-divergence-is-after-it.md)），
防拷問答的收據與 remake 差 32 個像素：`(240,283)` 的一塊 16×2。

## 先把方向釘正（勘誤）

`docs/worklist.json` 的 `copyprot-16x2-block-at-240-283` 寫的是
「remake 色號 `F`、原版 `9`」——**方向相反**。`270` 的原文是
「色號新版 `F`、收據 `9`」，指的是**新執行器跑出來的原版畫面**是 `F`、
**舊收據**是 `9`。逐位元組量：

| 來源 | `(240,283)` 16×2 |
|---|---|
| `workplace/oracle-prev/cb1`（舊執行器 `2833ec9`）| 色號 `9`（＝ 視窗填色，什麼都沒有）|
| `workplace/oracle/cb1`（新執行器）| 色號 `15` |
| remake | 色號 `9` |

所以是 **remake 少畫了一樣東西**，不是多畫。（`proven`）

## 那 16×2 是輸入游標

`input_text` 的格子是 `x=240`、`pitch=16`、`y=270`，全形字 16×15 ＝ 佔 y 270–284。
那塊 16×2 正好是**某一格的最底下兩列**。哪一格？拿四個輸入位數各錄一份：

| 已輸入位數 | 收據／旗標 | 16×2 的 x | ＝ 第幾格 |
|---|---|---|---|
| 0 | `cb1` | 240–255 | 0 |
| 1 | 一次性 probe（見下）| 256–271 | 1 |
| 2 | 一次性 probe（見下）| 272–287 | 2 |
| 3 | `typed138` | 288–303 | 3 |

**游標永遠在「下一個要打的那一格」底下**，x ＝ 240 ＋ 16 × 已輸入位數。（`proven`）

一次性 probe 的旗標（跑完即刪，批次名 `cpxpress1`／`cpxpress13`）：

```
-steps 116000000 -tick 20000 -clicks 40000000:300:170,95000000:300:170 \
  -click-hold 3000000 -press 1     -press-at 105000000 -press-every 2000000
-steps 116000000 -tick 20000 -clicks 40000000:300:170,95000000:300:170 \
  -click-hold 3000000 -press 1,3   -press-at 105000000 -press-every 2000000
```

## 它會閃

`-vram-sites -vram-at 588E`（＝ y283 × 80 ＋ x240÷8）問「誰寫這個位元組」，
整趟 1.3 億道指令只有 21 次寫入。用 `-dump-at` 從 #95,000,000 到 #129,500,000
每 50 萬道倒一張畫面，那 32 個像素的亮滅是：

```
#95.0M ────────────────────────────────────────────────── #129.5M
.#########################.............############.............######
```

四個轉折都量得到：

| 事件 | 指令數 | 由誰寫 |
|---|---|---|
| 亮（畫面剛畫出來）| #95,183,578 | `2376:0DB1` |
| 亮（重畫，畫面沒變）| #101,225,243 | `2376:0DB1` |
| 滅 | #107,625,191 | `2376:107F` |
| 亮 | #114,025,214 | `2376:0DB1` |
| 滅 | 落在 (#120,400,000, #120,450,000] | — |
| 亮 | #126,825,235 | `2376:0DB1` |

同一支常式（`2376:0DB1`）相鄰兩次的間距是 **12,799,971** 與 **12,800,021**
道指令。`-tick 20000` 把 IRQ0 釘在「每 20,000 道一次」，所以那是
**640 次計時器中斷**，畫與擦各佔一半 ＝ **320 次**。（間距是整數倍的 640
而不是某個零頭，所以驅動它的是中斷次數不是指令數：`strong inference`）

本作把 PIT 分頻設成 2048（`270`），＝ 582.8 Hz，所以 640 次中斷 ≈ **1.10 秒**，
半週期 ≈ 0.55 秒——就是一般文字游標的閃法。（`strong inference`）

擦的那一支 `2376:107F` 是從 VRAM 位移 `0x9600` 抄回來的：`0x9600` ＝ 38,400，
正好是 640×480 模式可見畫面的下一個位元組，也就是**螢幕外的備份區**；
`DI` 每圈 `+0x50`（一列），跑 15 圈 ＝ 一整格 16×15。畫的那一支
`2376:0DB1` 寫同一個 `DI`，來源在資料段（`DS=54B3`）。
所以機制是「整格重畫／整格還原」，不是只塗那兩列。（`strong inference`）

## 為什麼舊收據是滅的

舊執行器的 `-tick` 會被 PIT 的重算蓋掉，實際間隔變成每 5,156 道一次
（`270`）——**計時器快了四倍**。同樣跑到第 1.3 億道指令，落在閃爍週期的
另外半邊。舊收據不是「原版沒有游標」，是**剛好停在滅的那半個週期**。
（`strong inference`；直接證據是新舊兩份收據的唯一差異就是這 32 個像素）

同一個原因的收據共六份，全部只差這 32 個像素，全部已重錄：

| 收據 | 32 像素在哪 | 用途 |
|---|---|---|
| `cb1` | 格 0 | `internal/screen`／`internal/game` 的對拍 |
| `cbAlly` | 格 0 | `internal/game/faction_test.go` |
| `typed138` | 格 3 | `internal/screen` 打字後的對拍 |
| `click5`／`click6`／`click7`／`vs1` | 格 0 | 沒有測試引用 |

`cbAlly`／`click5`／`click6`／`click7`／`vs1` 重錄後的 `screen.bin` 與 `cb1`
**同一個雜湊**（`10dd957d…`）——帝國與同盟的防拷問答畫面本來就一樣。
六份都與 `workplace/check/` 那一次獨立重跑逐位元組相同（兩次可重現）。

## remake 怎麼改

規格 `docs/internals/data/screen-copy-protection.json` 多一個 `input_caret`
（`x=240 y=283 w=16 h=2 pitch=16 ink=15`），`internal/screen.CopyProtection`
在畫完數字之後把它塗上去，位置由**已輸入的位數**決定。

**remake 目前恆亮，閃爍還沒接。** 收據都停在亮著的那半個週期，所以對拍
是綠的；但「畫面上該有一條底線」與「它每 320 次計時器中斷翻一次」是兩件事，
後者還沒有時鐘可以掛。已另立 worklist 條目 `copyprot-caret-blink`，
不要把這一份當成閃爍也做完了。

## 順帶量到、但與本案無關的兩件事

`tools/gui_check.sh`（Ebiten 顯示層走玩家路徑）十例裡有兩例紅，兩例都
**不是**這個游標：

- `load1e` 差 2,265 個像素，落在 `x[16,303] y[361,395]`——那是左下角星域
  摘要面板，2,265 正是 [`276`](276-what-the-executor-fix-changed-on-screen.md)
  形狀二的簽章數字。`internal/game` 的同一份收據是綠的，所以缺的是
  `cmd/gin3` 的腳本驅動沒有把滑鼠停留的位置餵成同一個狀態。
- `vs3` 的 274 個像素已於 2026-09-13 分成兩塊各 137 像素的 13×16 游標：
  原版在 `(400,262)`、Ebiten 腳本停在 `(300,250)`。根因是 `tools/gui_check.sh`
  漏掉收據最後一次框內、熱區外點擊；補上 `click 400 262` 後逐位元組相同。

`load1e` 與 `vs3` 都已修正並由 `tools/gui_check.sh` 十例全綠收尾；詳見該
worklist issue 的完成紀錄。

## 三條方法

- **「差 32 個像素」先問是誰多誰少，不要照抄前一份摘要的措辭。**
  worklist 把 `270` 的「新版 vs 收據」抄成「remake vs 原版」，方向整個反過來；
  照著那句話去找「remake 多畫了什麼」會一無所獲，而且不會有人報錯。
  一手證據是三份色號陣列各自的那 32 個位元組，不是任何一段散文。
- **一格 16×15 的最底下兩列，先去對輸入格的格點，不要先猜它是什麼元件。**
  `240 = input_text.x`、`283 = input_text.y + 13`、寬度 ＝ `pitch`——
  三個數字都落在既有規格的格點上，那就不是巧合。
- **要證明「它會閃」，時間軸要自己跑一趟，不能只看一張畫面。**
  `-dump-at` 可以在同一次執行裡倒幾十張，代價與跑一次一樣（這裡 1.3 億道
  指令 8 秒）。而 `-vram-at` 只回答「誰寫過這個位元組」，回答不了「什麼時候」——
  兩個一起用才把「亮著」與「一直亮著」分開。
