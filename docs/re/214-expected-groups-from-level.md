# 214 — 應有組數 `+0x0E` ＝ 提督等級查一張九段表，收據三支全中

`docs/re/213` 把 `艦隊[+0x0E]`（應有組數）列成「最關鍵、還沒讀」——
它是填編制那個迴圈的上界。找到了，而且收據上三支的數字全部對上。

## 誰設它

`2D76:0611` 在呼叫 `0FF4:11F4` 之前先叫 `297B:0066(提督編號)`
（線性 `0x29816`），那一支才是**把艦隊記錄初始化**的地方：

```
297B:0066(提督編號):
    槽 = (陣營 == 0 ? 0 : 16) + 提督[+0x09]
    艦隊 = ds:C074 + 槽 × 122
    艦隊[+0x00] = 0
    艦隊[+0x3C] = 100                       ; 完整度／士氣
    艦隊[+0x01] = 提督[+0x01]                ; 陣營
    艦隊[+0x04] = 提督編號
    艦隊[+0x05] = 提督[+0x07]                ; 副官
    艦隊[+0x06] = 提督[+0x0A]                ; 所在星域
    艦隊[+0x0E] = 297B:0209(提督[+0x06])     ; ★ 應有組數 ← 等級
    艦隊[+0x0F] = 1
    艦隊[+0x08] = 5                          ; 不動
    艦隊[+0x07] = 0FFh                       ; 沒有目的地
    艦隊[+0x48] = 4                          ; 行動：待命
    memset(艦隊 + 0x10, 0FFh, 40)            ; 編制槽先全清成 FF
    艦隊[+0x12] = 提督[+0x08] & 0Fh          ; 艦種
    艦隊[+0x13] = 20
    編制槽[0][+0..1] = 2AD2:0029(艦隊, 艦種, 0)   ; ← **旗艦那一組**
    …
```

`docs/re/213` 問的「第 0 組是誰填的」也在這裡：**旗艦那一組是
`297B:0066` 填的**，`0FF4:11F4` 才從第 1 組接手。

## 那張表

`297B:0209(等級)`（線性 `0x299B9`）是一串 `cmp` ／ `jnb`：

| 等級 | 應有組數 |
|---|---|
| < 2 | 1 |
| < 6 | 2 |
| < 16 | 3 |
| < 20 | 4 |
| < 24 | **6** |
| < 29 | 7 |
| < 34 | 8 |
| < 39 | 9 |
| 其餘 | 10 |

**5 跳過了**——4 之後直接是 6。不是打錯：`b2 04` 的下一段就是 `b2 06`。

## 收據三支全中

`turn260mem`（`docs/re/209`）：

| 艦隊槽 | 提督 | 等級 | 表算出來 | 收據的 `+0x0F` |
|---|---|---|---|---|
| 23 | 47 | 20 | **6** | 6 |
| 28 | 52 | 18 | **4** | 4 |
| 31 | 55 | 16 | **4** | 4 |

三支的 `+0x0F` 都剛好等於 `+0x0E`，代表填編制那個迴圈一路跑滿、
沒有因為艦種不足提早結束。

## remake 做了什麼

`rules.FleetSlots(level)` 就是這張表，`ai.NewFleet` 多一個 `Expected`
欄位並由 `BuildPass` 填。**`Groups` 仍然是 0**——那要等
`2AD2:0029`（產生艦艇、可能要從星域存量扣）讀出來。

所以現在建出來的艦隊是「知道自己該有幾組、但一組都沒有」。
比先前的「連該有幾組都不知道」前進一格，離「維持費算得出來」還差
`2AD2:0029` 那一層。

## 一條方法

**一個看起來像「還要再讀三層」的東西，可能只差一次 dump。**
`+0x0E` 被列成最關鍵的未讀項，實際上它的設定點就在同一條呼叫鏈的
上一支（`297B:0066`），而那一支順便把「第 0 組誰填的」也回答了。
**往上讀一層，常常比往下讀一層便宜。**
