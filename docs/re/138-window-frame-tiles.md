# 138 — 視窗外框是圖塊：`FRAME.BLK` 與 `2376:0E4A`

框那一圈格子的圖塊從哪裡來，`docs/re/137` 停在這裡。答案是原版目錄裡
一個 5,280 bytes 的檔案 **`FRAME.BLK`**：33 張 16 × 20 的四平面圖塊，
開機時整份載到 `ds:6BF4`（逐位元組相同，已驗）。四組外框各八張，
外加一張落單的。

## 從訊息框走到圖塊

```
3826:0005(種類, 色, 字串)
    3603:0006(&視窗, 色, 格x, 格y, 寬, 高, 旗標)   ; 造視窗（0x22 bytes）
    3617:000A(&視窗, 字串)                          ; 放字
    37A9:000F(&視窗, ds:8CFA＋種類×4)               ; 掛子元件（12 bytes 一筆）
    341B:0145(&視窗)                                ; 顯示
    3826:023B(&視窗)                                ; 等輸入
```

`341B:0145` 先把 `視窗[+0]` 從 1 改成 **2**——`[+0]` 是「已顯示」而不是
種類，`341B:039D` 的命中測試只認 2，所以沒顯示的視窗點不到。接著依
`視窗[+1]`（顏色）分三條路：`0xFF` → `34CB:02C4`、`0` → `34CB:00AB`、
其餘 → **`34CB:01A4`**。訊息框的顏色是 `0x97`，走第三條。

`34CB:01A4` 分兩段：`視窗[+3]` 非 0 就先 `34CB:094A` 畫外框，再把內容
格從視窗自己的緩衝區搬進畫面格表；`[+3]` 為 0 就只搬內容。

## `34CB:094A`：外框寫的是八個字碼

畫面格表在 `ds:D81E`，40 × 20 格、一格 6 bytes：

| 位移 | 內容 |
|---|---|
| `[+0]` | bit7 髒、bit6 圖塊、bit5 鎖住（設了就整格跳過）、bit4 走字模、低四位 = 擁有者槽位 |
| `[+2]` | 字碼（word） |
| `[+4]` | 顏色 |
| `[+5]` | 顏色高位 |

`34CB:094A` 對外圈每一格寫 `[+0] = 視窗[+4] | 0x90`（髒 ＋ 走字模）、
`[+4] = 視窗[+1]`、`[+5] = 0`，字碼則是

```
基底 = 0xFF00 ＋ 視窗[+3]
左上 基底＋0   上 基底＋1   右上 基底＋2
左   基底＋3               右   基底＋4
左下 基底＋5   下 基底＋6   右下 基底＋7
```

內容格由 `34CB:01A4` 從視窗緩衝區（一格 4 bytes：兩個字碼 ＋ 兩個顏色）
搬進來，空白是 `0x2020`。

## `2376:040E` → `2376:0E0D` → `2376:0E4A`

`2376:040E` 掃整張格表把髒格畫出去：畫面位移從 **`0x0C80`** 起算、
每格 ＋2、每列 ＋`0x5F0`（內層已經加掉 40 × 2）。`0x0C80` ＝ 3200 ＝
兩格列——**格座標系的原點在畫面上方 40 像素處**，與滑鼠的
`screen_y = mouse_y + 40`（`docs/re/52`）是同一個偏移。

字模那條路走 `2376:0E0D(dx ＝ 字碼, cx ＝ 顏色, di ＝ 畫面位移)`，
第一件事就是看高位元組：

```
dh == 0xFF → 2376:0E4A   外框圖塊
dh >= 0x80 → 全形（Big5）
否則        → 兩個半形
```

`2376:0E4A`：

```
si = ds:6BF4 ＋ 0xA0 × (dl − 1)      ; 一張 160 bytes
bl = cl >> 4                          ; 顏色的高四位
每一列（20 列）：
    bp = ~(平面0 | 平面1 | 平面2 | 平面3)      ; 這一列色號 0 的位元
    對四個平面：
        設 sequencer map mask
        dx = (bh 最低位 ? 0xFFFF : 0) & bp
        es:[di] = lodsw | dx
        bh >>= 1
    di += 0x50
```

**圖塊裡的色號 0 不是黑，是留給視窗底色。** 每一列先算出「四個平面
都沒有位元」的像素，再把顏色高四位（一平面一位元）填進去。所以同一組
圖塊換個顏色就是另一種框，而訊息框量到的底色 9 就是 `0x97 >> 4`。

## 四種樣式

`視窗[+3]` 不是布林值，是**樣式的第一個字碼**；圖塊索引 ＝ `[+3] − 1 ＋ n`。

| 起始碼 | 圖塊 | 收據上看到的用途 |
|---|---|---|
| 1 | 0–7 | 戰場大面板、訊息框、清單面板（`s3msg`、`s3menu`、`lstmenu1e`） |
| 9 | 8–15 | 主選單與各種小選單（`main-menu`、`s3cmd1`） |
| 17 | 16–23 | 尚未在收據上看到 |
| 25 | 24–31 | 尚未在收據上看到 |

第三、四組沒有色號 0，視窗底色透不出來。第 32 張落單。

`3603:0006` 只看 `[+3]` 是不是 0——非 0 就讓寬高各 ＋2 格，那兩格就是
外框佔的位置。這也是 `docs/re/137` 裡那條 `(內寬＋2)×16−2` 的來源。

## 驗證

收據 `s3msg`（訊息框，格 (4,7)、22 × 6、底色 9）：

| 比較範圍 | 像素 | 不同 |
|---|---|---|
| 外框那一圈 | 16,640 | **0** |
| 整個 22 × 6 格 | 42,240 | 1,806（全部落在 x 80–385、y 201–279，就是那行字） |

收據 `main-menu`（主選單，格 (17,7)、5 × 6、樣式 9、底色 9）：八張圖塊
全部逐位元組命中。`s3menu`／`s3cmd1`／`lstmenu1e` 也各自命中一整圈。

`ui.MenuFrame`（從主選單量出來的線條版）與圖塊版的關係：**線條版矩形
內的每一個像素都相同**，差別只有圖塊版多畫最外圈那一像素。五個尺寸
（5×6、4×4、4×5、10×10、22×6）差的數量都剛好等於周長
`2×寬×16 ＋ 2×高×20 − 4`。線條版看不出來，是因為主選單那一圈的圖塊
色號正好是底色 3。

## 收回的說法

`docs/re/137` 把畫的鏈條寫成 `3603:0006 → 341B:0054 → 35AA:0006 →
35AA:0068 → 35AA:00C7 → 2376:0CF0`，最後兩段是錯的：`35AA:00C7` 與
`2376:0CF0` 在整份常駐程式碼裡**一個呼叫端都沒有**（遠呼叫、段內近呼叫
與四位元組遠指標常數都掃過），而 `2376:0CF0` 的唯一呼叫端就是
`35AA:00C7`。`35AA:00C7` 讀的 `視窗[+0E]` 是一格 160 bytes 的圖塊陣列，
與 `35AA:0006` 配的「內容格數 × 4」對不上——那個矛盾本身就是它不在這條
路上的證據。真正的路是 `341B:0145 → 34CB:01A4 → 34CB:094A`（寫格表）
＋ `2376:040E → 2376:0E0D → 2376:0E4A`（畫格）。

`0x0C80` 那個結論不受影響：`2376:040E` 用的是同一個常數，而且它是活的。

## 框裡的字：位置量到了

`3617:000A(&視窗, 字串)` 走的是一支 printf（`3ACA:0079`，輸出回呼是
`3617:0099`），中間有兩張跳表（`ds:6BCC`、`ds:6BDC`）處理控制碼與顏色，
還沒讀。不過訊息框只印一行純文字，位置直接量得出來：

拿收據 `s3msg` 掃 (x 76–92) × (y 197–205) × 陰影位移 −1／0／1 ×
字色 7／15 × 陰影 3／8／0，**唯一 0 差異的組合**是

```
(80, 202)   字色 7   陰影 3   陰影往上一列   欄距 16   不加粗
```

(80, 202) ＝ 內容格 (5, 8) 的左上角 (80, 200) 再往下 2 像素。字模 16 × 15，
陰影那一趟在 y 201–215、本體在 202–216。

`screen.DrawMessageBoxText` 照做。框 ＋ 這行字合起來，整個 22 × 6 格
與收據只剩右下角那個按鈕不同。

## 還沒做的：子元件（按鈕）

`3826:0005` 在顯示之前還會 `37A9:000F(&視窗, ds:8CFA ＋ 種類 × 4)`，
那是一張 12 bytes 一筆的子元件表，`[+0]`／`[+1]` 都是 `0xFF` 就結束：

| 位移 | 內容 |
|---|---|
| `[+0]`／`[+1]` | 內容格 x／y |
| `[+2]`／`[+3]` | 格寬／格高 |
| `[+4]` | 旗標 |
| `[+5]` | 種類（0 或 1）|
| `[+8]`–`[+0B]` | 遠指標 → 字串 |

四張表（`ds:8C0A`／`8C2C`／`8C56`／`8C78`，對應種類 0–3）：

| 種類 | 筆數 | 內容 |
|---|---|---|
| 0 | 1 | 格 (17,3) 2×1，字串 `ds:8C04` |
| 1 | 2 | 格 (14,3) 2×1（`[+5]=1`）＋ 格 (17,3) 2×1 |
| **2** | 1 | 格 (17,3) 2×1，字串 `ds:8C50` |
| 3 | 2 | 格 (14,3) 2×1（`[+5]=1`）＋ 格 (17,3) 2×1 |

所以種類 1／3 是兩顆按鈕（確定／取消那種），0／2 是一顆。

`37A9:004C(視窗, 紀錄)` 直接寫進視窗的內容緩衝區
（`視窗[+0E] ＋ 紀錄[+1] × 視窗[+0B] × 4 ＋ 紀錄[+0] × 4`）：

- `紀錄[+6] == 6` → 把字串一個位元組一個位元組填進 `紀錄[+2]` 格，
  顏色取 `ds:8BE4 ＋ 紀錄[+6]`；
- 否則逐列從 `紀錄[+0] − 1` 那一格開始，`紀錄[+6] != 5` 就把內容格的
  `[+3] |= 0x10`，否則寫字碼 `0xFF16`。

種類 2 的那一筆是 `[+6] = 0`，走的是下面那條：按鈕的四格拿到

| 格 | 顏色 | 旗標 |
|---|---|---|
| `紀錄[+0] − 1` | 不動（維持視窗的 0x97）| `0x10` |
| `紀錄[+0]` … `+紀錄[+2]−1` | `ds:8BE4[紀錄[+6]]` ＝ **0x87** | `0x08` |
| `紀錄[+0] + 紀錄[+2]` | 不動 | `0x20` |

字串（`ds:8C50` ＝「確認」）就填在中間那幾格。

## 內容格的旗標 ＝ 裝飾位元

內容格的 `[+3]` 搬到畫面格表就是顏色的**高位元組**（`ch`），
`2376:10B7` 畫完底色、立體邊與字之後依它加裝飾：

| 位元 | 常式 | 效果 |
|---|---|---|
| `0x01` | `2376:1180` | 字上方一條 `0xFFFF` 的線（色 15）|
| `0x02` | `2376:116C` | `0x5555`／`0xAAAA` 交錯的網點 |
| `0x04` | `2376:1155` | 加粗（每列 OR 右移一位）|
| `0x08` | `2376:11B9` | 按鈕的上下邊 |
| `0x10` | `2376:11F1` | 按鈕左端 |
| `0x20` | `2376:121B` | 按鈕右端 |

顏色只有兩個：`2376:1270` 是 **7**、`2376:1278` 是 **3**。像素位置寫死：

```
0x08  第 0、1 列整格 16 像素 ← 7      第 18、19 列整格 ← 3
0x10  第 0–18 列的第 14、15 行 ← 7    第 19 列：第 14 行 ← 7、第 15 行 ← 3
0x20  第 1–19 列的第 0、1 行 ← 3      第 0 列：第 0 行 ← 7、第 1 行 ← 3
```

四個角就是靠最後那兩個特例像素接起來的。收據上量到的完全相同
（左端格第 19 列是 `73`、右端格第 0 列是 `73`）。

**裝飾是最後畫的**，所以按鈕上緣那兩列會蓋掉字的立體邊——照這個順序畫
與不照，差就差在 (361,261) 與 (368,261) 那兩個像素。

## 整個訊息框對完了

`DrawMessageBox` ＋ `DrawMessageBoxText` ＋ `DrawMessageBoxButtons`
與收據 `s3msg` 比整個 22 × 6 格：**42,240 個像素，0 差異**。

## 可重用的規則

- **「這個函式沒有呼叫端」是可以量的，而且要在往下讀之前量。**
  往下讀了六支都很順，卡住的地方是「同一個欄位在兩支常式裡的元素大小
  差 40 倍」。當時列了三種可能，漏掉第四種——**兩支根本不在同一條路上**。
  掃一次呼叫端只要幾秒，而它會直接把那三種可能全部作廢。
- **把整份程式碼一次倒出來，比一段一段倒便宜。** 之前每查一個段就跑一輪
  原版；改成一輪倒 217 KB（55 秒）之後，查呼叫端、切新段去反組譯都不用
  再跑。回饋迴圈越慢，越該先花力氣把它變快。
- **「素材在哪個檔案」用位元組簽章去搜，不要用檔名猜。** 拿記憶體裡那
  1,280 bytes 去掃原版目錄，一次就命中 `FRAME.BLK`，而且順帶證明它是
  整份原封不動載進去的。
