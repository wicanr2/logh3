# 262 — `ATTR.DAT` 就是戰場的圖塊遮罩（`ds:9BB4`）

`ATTR.DAT` 在 `VERIFICATION-MATRIX` 上一直標著「版面已觀察、語意未解」，
而 `docs/internals/43` 的「圖塊遮罩 `ds:9BB4`」標的來源是「倒自執行期記憶體」。
**兩者是同一張表。**

## 怎麼確認的

檔案只有 128 個位元組，值只有 `00` 與 `0F`：

```
索引 0–7      00      擋
索引 8–13     0F      通
索引 14–15    00      擋
索引 16–21    0F      通
索引 22–23    00      擋
索引 24–29    0F      通
索引 30–31    00      擋
索引 32–127   0F      通
```

拿這 128 個位元組當簽章去搜四份不同局面的 1 MB 傾印
（`monthgateA`／`t260_post`／`s3ai6`／`monthblend`），**四份都命中同一個位址
`0x5E6E4` ＝ `ds:9BB4`**，而且整份 1 MB 裡只有那一處。

程式碼那邊也對得起來——整份傾印裡引用 `0x9BB4` 這個字面值的只有兩處：

```
0x03A79  1E / BB B4 9B / 53 / 31 C0 / 50 / 9A CA 02 2E 33
         push ds; mov bx,9BB4h; push bx; push 0; call far 332E:02CA
         （這一支就緊接在主回合迴圈 0374:0343 前面，是開機那一趟）

0x15F13  55 / 89 E5 / 8A 4E 06 / 8A D9 / 30 FF / 8A 87 B4 9B / 5D / CB
         1588:0693(索引) → 回 ATTR[索引]
```

`1588:0693` 的唯一呼叫者是 `1588:0621`，也就是 `docs/internals/43` 記的通行
判定：

```
1588:0621(c, r)
    ax ＝ 1588:0672(c>>1, r>>1)     ; 地圖[(r>>1)×128 + (c>>1)]，遠指標 ds:3C1A
    ax ＝ 1588:0693(ax)             ; ← ATTR[圖塊]
    bx ＝ (r&1)×2 + (c&1)
    回 ax & ds:3C3E[bx]             ; 象限位元 [0, 2, 4, 8]
```

## 這修掉一個截斷

`docs/internals/data/battle-terrain.json` 的 `block_mask` 當初是從記憶體倒的，
**只倒了 64 筆**；`rules.BattleTerrain.Blocked` 對超出範圍的圖塊回「擋住」，
所以圖塊 64–127（實際上全是 `0x0F` ＝ 可通行）在 remake 會被當成不能走。

已量到的戰場地圖用到的最大圖塊是 **55**（`s3ai6`／`s3fight` 的
`ds:3C1A` → `0x6D3F4`，128×102 ＝ 13,056 格），所以**行為沒有差異**。
但把來源換成 `ATTR.DAT` 之後表補滿 128 筆，而且不再依賴那份一次性傾印
——照專案的保存目的，資料應該指回原版檔案。釘在
`rules.TestBlockMaskIsAttrDat`（逐位元組）。

## 一條方法

**「語意未解」的小資料檔，先拿它的內容去搜執行期記憶體。** 128 個位元組、
值只有兩種，看起來沒什麼特徵，但整份 1 MB 裡只命中一處——**罕見的是
序列不是單個值**。找到位址之後，再掃「誰引用這個位移」就直接接上既有的
反組譯（這一題只有兩處引用，其中一處就是已經解完的通行判定）。

這一輪也印證了 `rules/00` 的「下結論前先 grep 自己的 `docs/`」：機制本身
`docs/re/100` 與 `docs/internals/43` 早就寫完了，這一篇真正新的只有
「那張表的來源是 `ATTR.DAT`」與那個 64／128 的截斷。
