# 開頭動畫：對不起來的那個「第一個寫入」不是 token 寫的

`36` 解出了 `IBM16.350` 的 token 語法，但卡在「格 → 緩衝區位移」：
監看到的第一個寫入是 `27616: 00 → 20`（緩衝區位移 0、值 `0x20`），
而第 0 格的第一個 token 是「跳過 10,559 格」，於是那份紀錄把
「`add di,50` / `sub di,46EF` 那個走法至少有一處讀錯」當成最可能的解釋。

這一輪**不跑執行器**，只用檔案本身把那個推論拆掉。

## 一、語法再確認一次（純檔案）

照 `36` 的語法從檔頭解到底，每個 plane 走滿 18,160 格才停、
每格四個 plane ＋ 四個分隔位元組：

```
374 格全部對上 IBMFLS16.350 的長度，長度對不上的格數 ＝ 0
```

語法是對的，這件事與走法無關。

## 二、沒有任何一格的第一個 token 會寫格 0 的 `0x20`

不管走法是逐欄（`offset = (n mod 227) × 80 + n ÷ 227`）還是逐列
（`offset = n`），**只要走法從格 0 開始且單調前進**，
「寫到緩衝區位移 0」就等於「這一格的第一個 token 是寫入、而且涵蓋格 0」。

掃過 374 格：

- plane 0 的第一個 token 是**寫入**的只有 **14 格**；
- 那 14 格的值是 188×2、3、139、51、16、20、199、195…——**沒有 `0x20`**；
- 前八格的第一個 token 全是跳過（10559、10559、10557、10556、10556、
  10554、10554、10552）。

## 結論

`27616: 00 → 20` **不可能是 frame token 寫的**。它是別的東西寫的
（緩衝區初始化、或動畫開始前的底圖那 3,105 個非零位元組的一部分）。

所以 `36` 的推論前提不成立：**走法不一定讀錯**，對不起來的是
拿來比對的那個觀測值。

> 這與 `58` 是同一課：量到的東西與另一種量法對不起來時，
> 先確認那個觀測值**量的是不是同一件事**，再去懷疑模型。

## 下一步該做的實驗

不要再用「第一個寫入」當錨點。改成**把走法量出來**：

1. 在只差一格的兩個步數各倒一次緩衝區（`-dump-mem`）；
2. 兩份 XOR，差出來的就是那一格所有的 `(位移, 值)`；
3. 拿同一格的 token 串（值的順序是確定的）去對那串位移，
   走法就直接讀出來了，不必猜。

第 2 步之所以成立，是因為 token 的動作就是 `xor es:[di],al`——
XOR 兩份倒檔正好把那一格的寫入分離出來。
