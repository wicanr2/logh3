# 261 — 開頭動畫：解碼時序不是均勻的，而 remake 的格子對不上原版畫面

`docs/re/110` 量到「一格 73 個計時器中斷」，`docs/spec/020` 照它把 remake
的播放做成固定 125.3 ms 一格。把時序表整份量出來之後，那個模型不成立。

## `-dump-at` 也會寫色號陣列

先講一件擋了很久的事。`workplace/oracle/intro52/screen.png` 這一類動畫截圖
看起來像**雜訊**（近黑底加白點），所以「整段動畫對拍」一直沒開始。那不是
畫面壞了——是 PNG 的調色盤：動畫那一段 DAC 還沒換成 `BU16IBM.RGB`
（`docs/re/110`），`writeEGA` 拿當下的 DAC 上色，於是 16 色全部映到近黑。

`writeEGA` 除了 PNG **也會寫一份同名的 `.bin`**（色號陣列，與調色盤無關），
`-dump-at` 走的是同一支，所以一次跑就能倒出很多格的色號陣列。倒出來一量，
幾何完全正確：

| 收據 | 非零位元組 | 有內容的列 | 列數 | 前幾個色號 |
|---|---:|---|---:|---|
| `if000` | 17,563 | 61–287 | 227 | 4／8／1／12／9 |
| `if001` | 18,955 | 61–287 | 227 | 4／2／1／8／9 |
| `if003` | 32,633 | 61–287 | 227 | 8／4／2／6／12 |
| `if004` | 36,233 | 61–287 | 227 | 8／4／2／12／6 |

第 61 列正是 `screen.IntroTopRow`，227 列正是 `asset.IntroPlaneRows`，
色號有八種——**是真正的 16 色畫面**。釘在
`TestIntroPageGeometryMatchesOracle`（原本 `IntroTopRow` 是從「置中」
推出來的，現在有量到的）。

## 解碼時序：25 組，間隔從 71 到 4861 個 tick

`-regs-at 041F:024B -regs-max 1600 -steps 500000000`（批次 `introsched`），
命中四個一組（一格四個 plane）。**500M 步裡只有 25 組**，組間間隔（tick）：

```
173, 72, 73, 637, 72, 3595, 71, 73, 72, 72, 698, 73,
3432, 4513, 72, 2922, 4861, 71, 73, 73, 71, 73, 73, 674
```

七次 73、五次 72、三次 71——那是 `docs/re/110` 量到的那個節奏；但中間夾著
637、3595、698、3432、4513、2922、4861 這些長停頓。所以動畫的形狀是
**幾格快放（約 8 fps）＋ 一段長停頓**，反覆交替，不是 374 格連續播。

固定 125.3 ms 一格的模型只在快放那幾段成立。

## remake 解出來的格子與原版畫面不相交

拿 remake 的 `IntroPage`（解碼器累加 N 次之後的頁面）去比上面四份，
374 格裡**沒有一格逐位元組相同**，而且最接近的都是第 1 格：

| 收據 | 最接近的格 | 差異 | 該格非零 |
|---|---:|---:|---:|
| `if000` | 1 | 17,558 | 17,563 |
| `if001` | 1 | 18,950 | 18,955 |
| `if003` | 1 | 32,628 | 32,633 |
| `if004` | 1 | 36,228 | 36,233 |

差異幾乎等於原版那一格的非零位元組數——也就是 remake 在第 1 格時頁面
**幾乎是空的**，而原版在 `#35,500,000` 已經有一整張圖。兩邊幾乎不相交。

`asset.TestIntroDecoder` 的三個判準（逐格長度對上長度表、整檔吃光、
第 97–102 與 244–251 格的 XOR 累加整個歸零）仍然全過，所以**解碼本身
大概是對的**，對不上的是別的環節。三個候選，都還沒排除：

1. **一次解碼呼叫吃掉的不是一格。** 25 組對 374 格差了一個量級；如果
   `041F:024B` 一次把好幾格的 token 吃完，那 remake 的「一格一頁」就
   對不上原版的任何一個時點。
2. **plane 併成色號的方式。** `asset.Pixels` 把四個 plane 併成 640×227，
   位元序或 plane 順序錯了會得到「非零位元組數量差不多、位置全錯」
   ——正是量到的形狀。
3. **底圖。** `intro_decode.py` 的輸出是「不含底圖的 XOR 累加」。原版可能
   先鋪一張底圖再 XOR，remake 從全 0 開始。

## 一條方法

**看起來壞掉的截圖，先確認壞的是資料還是上色。** 動畫這一段的 PNG 像雜訊，
於是「整段對拍」被擱置了很久；而同一次傾印寫出來的 `.bin` 一直是好的
——**色號陣列與調色盤是兩件事，對拍要比的本來就是前者**。判斷點：
量非零位元組的分布（列範圍、色號種類）。真的壞掉的資料不會剛好落在
第 61–287 列、剛好用八種色號。

## 補：一組是四個 plane，第四個在另一個段

把 100 個命中按 `DX`／`ES` 排出來，每一組**都是同一個樣式**（25 組，25/25）：

```
(DX=0016, ES=2760)  (DX=4706, ES=2760)  (DX=8DF6, ES=2760)  (DX=0016, ES=34B0)
```

三個 plane 在段 `2760`、位移 `0016`／`4706`／`8DF6`（相差 `0x46F0` ＝
18,160 ＝ 一個 plane），**第四個 plane 在段 `34B0` 的位移 `0016`**。
所以「一格四個 plane」成立，但它們**不是連續的一塊**。

同時也修正上面那句「500M 步裡只有 25 組」的言下之意：那不是整段動畫，
是**開頭 25 格**。24 個間隔加起來約 22,600 個 tick，照這個密度 374 格要
一千多 M 步——`-steps 500000000` 只跑到第 25 格。

## 補：`if000` 是第 0 格，不是第 1 格

畫面是雙緩衝的（`-dump-at` 報的顯示起點在 `0` 與 `28000` 之間交替，
28,000 ＝ 640×350÷8 ＝ 一頁一個 plane）。`if000` 倒在 `#35,500,000`，
而第二組解碼在 `#34,720,076`——那一組寫的是**沒在顯示的那一頁**，
所以 `if000` 看到的是第一組（`#31,260,075`）解出來的**第 0 格**。

上面那張表「最接近的都是第 1 格」是 `IntroPage` 在第一次 `Next()`
**之後**的狀態，換算過來就是第 0 格。也就是說：**remake 的第 0 格與原版
的第 0 格幾乎不相交**，差異 17,558／原版非零 17,563。

plane 的排列順序如果只是被換了（例如第四個 plane 其實是 plane 0），
非零像素的**位置**不會變，只有色號會變——而量到的是位置也對不上。
所以剩下的候選偏向「有底圖」或「走法（欄優先）對不上」，
不是單純的 plane 順序。

## 底圖確認了，而且它在 plane 緩衝區裡不在畫面上

先把 remake 的解碼器與原版的記憶體對起來。`DX` 的三個值配 `ES=2760`
換成線性位址就是 `0x27616`／`0x2BD06`／`0x303F6`（相差 `0x46F0` ＝ 18,160
＝ 一個 plane），第四個在 `0x34B16`。在第一組解碼跑完、第二組還沒開始的
`#34,700,000` 倒這四塊：

| plane | 原版記憶體的非零位元組 | 檔案第 0 格解出來的 |
|---|---:|---:|
| 0 | **12** | **12** |
| 1 | **7** | **7** |
| 2 | 3,086 | 9 |
| 3 | 1,118 | 7 |

**plane 0 與 1 逐一相同**——所以位址是對的，而且 `asset.IntroDecoder`
與原版 `041F:024B` 解出來的東西在那兩個 plane 上一致。**解碼器沒問題。**

plane 2 與 3 差了兩、三個量級。再倒一張第一次解碼**之前**的畫面
（`#31,000,000`，批次 `introbase`）：**整張全 0**，一個非零像素都沒有。
而 `#35,500,000` 的畫面有 17,563 個非零像素，中間只跑過一組解碼、
而那一組解出來的東西只有 29 個像素。

三件事合起來只剩一種解釋：**有一張底圖，而它是直接寫進 plane 緩衝區的，
不是先畫到畫面上再 XOR**。`IBM16.350` 的 token 是疊在那張底圖上的差分，
而 remake 從全 0 開始累加——所以兩邊的第 0 格幾乎不相交。

底圖從哪來還沒查。候選是同一批檔案裡的另一份（`docs/internals/19` 記
`IBM16.350` ＋ `IBMFLS16.350` 兩個檔整檔吃光，所以底圖不在那兩個裡面），
或是 `OPEN.EXE` 自己帶的。**下一輪要追的是「誰第一次寫 `0x303F6`」**
——對那個位址設監看就會直接指出來，不必再猜。

## 修正上面的候選清單

- ~~一次解碼呼叫吃掉的不是一格~~：排除。plane 0／1 的非零位元組數與
  檔案第 0 格逐一相同，一次呼叫就是一格的一個 plane。
- ~~plane 併成色號的方式~~：排除。同上，位元組層級就對上了。
- **有底圖**：確認。而且是寫在 plane 緩衝區裡。

## 底圖不是別人寫的——是同一個模組寫的，而且時點對不上呼叫

對 plane 2 真正非零的那幾個位元組設監看（`-watch 303F7-303FA`，
批次 `introbasewho2`）：

```
#34294843  303F7: 00 → 74  ← 041F:02D2
#34382438  303F8: 00 → 41  ← 041F:02D2
#34384425  303F9: 00 → 40  ← 041F:02D2
#34386270  303FA: 00 → 02  ← 041F:02D2
```

三件事：

1. **寫入者 `041F:02D2` 就在解碼模組裡**（解碼進入點是 `041F:024B`，
   差 0x87 個位元組）。所以那些內容不是別的程式碼載進來的底圖，
   是**同一支解碼程式寫的**。
2. **在那之前是 0。** 監看從 0 開始跑，`#34,294,843` 那一筆是
   `00 → 74`——所以 plane 2 在第一次解碼之前確實是空的。
   （第一次試的範圍 `303F6-303F9` 命中 0 次，因為 `0x303F6` 那一格
   本來就是 0；要挑**真的非零**的位址設監看。）
3. **時點與呼叫對不上。** `DX=8DF6`（＝ plane 2 的位移）那一次呼叫在
   `#31,406,517`，而寫入發生在 `#34,294,843`——差了 2.9×10⁶ 步，
   中間還沒有別的 `041F:024B` 命中（下一次是 `#34,619,960`）。

所以「remake 少了一張底圖」這個說法要再收一次：**plane 0／1 與 plane 2／3
的差別不在有沒有底圖，而在原版對後兩個 plane 多寫了東西，而且寫的時點
不在 `041F:024B` 那一次呼叫裡。**

下一輪的作法照 `docs/re/255` 那一套：**在監看命中的那一步倒一份堆疊**
（`-dump-mem-at '<步數>:lin:<SS:SP>:…'`），把回傳位址讀出來就知道
`041F:02D2` 那一刻是誰在跑。`-regs-at` 這一題沒用——已經知道它不是
從 `041F:024B` 進去的。
