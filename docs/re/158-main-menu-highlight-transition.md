# 158 — 主選單的反白轉場沒有殘留

`docs/internals/07` 記著一條 `confirmed`：

> 反白從 A 列搬到 B 列時，被還原的 A 列不是乾淨的重畫——會留下與靜態
> 畫面不同的像素（實測 74 個）。

`VERIFICATION-MATRIX` 的第 3 列（主選單互動）因此掛著「還缺切換過程」，
`TestMainMenuMatchesOracle` 也把 `curfill`（游標壓在視窗下緣外框上）
排除在外，理由是那一帶會被殘留污染。

**在執行器 `ef5be47` 上重現不出來。** 十四份收據，一個像素都沒差。

## 怎麼比的

反白的命中判定用游標熱點（`滑鼠y + 41`）落在哪一格（`200 + 20r` 起、
高 20），所以第 r 列對應的滑鼠 y 是 `159 + 20r … 178 + 20r`。

**同一個終點、兩種到達方式**：

| 到達方式 | 做法 |
|---|---|
| 選單畫出來**之前**就定位 | `-click-x 300 -click-y <y> -click-at 15000000`（那一下同時跳過開頭動畫與定位滑鼠），之後不再動 |
| 畫完**之後**才搬過去 | `-click-x 320 -click-y 200 -click-at 15000000`（先落在第 2 列），再 `-mouse-x 300 -mouse-y <y> -mouse-at 30000000` |

```
r0pre（畫之前定位，第 0 列）  vs  r0（第 2 列 → 第 0 列）   逐位元組相同
r3pre（畫之前定位，第 3 列）  vs  r3（第 2 列 → 第 3 列）   逐位元組相同
```

**每一組列與列之間的搬動**也都試過（`-click-y` 決定起點、`-mouse-y`
決定終點，都在 60,000,000 步時拍）：

```
0→1 = 乾淨的第 1 列    0→3 = 乾淨的第 3 列
1→3 = 乾淨的第 3 列    2→0 = 乾淨的第 0 列
3→0 = 乾淨的第 0 列    0→2 = 乾淨的第 2 列
```

**搬動的時機也試過**：把 `-mouse-at` 推到 59,000,000／59,800,000／
59,950,000（離拍照只剩 50,000 步），三份都與乾淨的第 2 列相同。
所以不是「殘留很快就被蓋掉」——是根本沒有殘留。

## 舊收據在新執行器上仍然成立

`r0`／`r1`／`r2`／`r3`／`cur300`／`curfill` 六份是 `2833ec9` 時做的。
用同一組旗標在 `ef5be47` 重跑，六份的 `screen.bin` SHA-256 **全部相同**
——所以這不是「收據換版本失效」，是原本那個結論本身重現不出來。

## 結果

- `curfill`（滑鼠 (310,241)，游標壓在視窗下緣外框上、不反白）進了
  `TestMainMenuMatchesOracle`，**逐位元組相同**。主選單的六個狀態
  （四列反白 ＋ 選單外 ＋ 壓在外框上）現在全部對拍過。
- `docs/internals/07` 那一節改寫成現況。
