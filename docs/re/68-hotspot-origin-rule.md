# 熱區的位置換算：視窗左上角 ＋ (格子 ＋ 1) × (16,20)

`docs/internals/23` 解出熱區清單的版面（12 bytes 一筆，`+0…+3` 是格子
座標與大小），但「格子換算成畫面座標的原點」一直是靠某一個畫面反推的，
而且反推出來的規則自相矛盾：對命令列成立的那條，套到別的視窗會差兩格。

這一輪拿**兩個視窗、六顆按鈕、其中兩個是反例**把它定下來。

## 規則（confirmed）

```
熱區像素 = 視窗左上角 + (格子 + 1) × (16, 20)
熱區大小 =            （格）× (16, 20)
```

畫出來的框**左右各比熱區多 2 像素**，上下對齊。所以框裡最外那兩行
點不到——這不是誤差，是原版的版面。

|---|---|---|---|
| 經歷 | (17,11) 2×1 | (384,320) 32×20 | (382,320) 36×20 |
| 中止 | (20,11) 2×1 | (432,320) 32×20 | (430,320) 36×20 |
| 出擊 | (23,11) 2×1 | (480,320) 32×20 | (478,320) 36×20 |

## 兩個反例（confirmed）

同一組輸入序列，最後一次點擊改成落在**框內、熱區外**：

| 收據 | 點的位置 | 落在 | 結果 |
|---|---|---|---|
| `fnum` | (368,350) | 艦隊編號熱區內 | 開出艦隊編號清單 |
| `fnum2` | (400,350) | 框內、熱區外 1 像素 | `screen.bin` 與 `fleet1e` **雜湊相同** |
| `fadj` | (432,350) | 副官熱區內 | 開出變更／卸任 |
| `fadj2` | (448,350) | 框內、熱區外 1 像素 | `screen.bin` 與 `fleet1e` **雜湊相同** |

一個像素的差別換到兩個完全不同的結果——這比六個正例更能定住邊界。

## 兩個獨立的佐證

開出來的兩份清單，**反白條的矩形正好等於熱區**：艦隊編號那份是
x336–399（＝ 4 格），副官那份是 x416–447（＝ 2 格）。反白條是遊戲
自己畫的，與熱區清單是兩條獨立的路徑，量出來卻是同一個矩形。

「確認」那顆的按鈕文字起繪點量出來是 x=464，也正好是熱區的左緣。

## 順帶更正：`10BC` 不是船艦訂造報告那一份

`docs/internals/23` 原本用「在訂造報告上點 (448,310) 會開出建造計劃」
反推 `10BC` 屬於訂造報告，同一節還記著另外兩筆換算出來的位置點下去
「什麼都沒發生」，並假設是「處理常式在這個局面不做事」。

按上面的規則，`10BC` 三筆落在**艦隊編成**的視窗上，而且三筆各自對應
畫面上真的有的按鈕（副官／艦隊編號／確認），兩筆點下去開得出東西。
所以那個「不做事」的假設不必要——是清單認錯了畫面。

`2A00`（戰艦…／決定／陣形／中止）同理不屬於艦隊編成，屬於再下一層的
**艦隊組成**（`docs/re/67`）：那張畫面右下角就是陣形／中止／決定三顆。
