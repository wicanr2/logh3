# 開頭動畫：那 65 KB 是照**影格邊界**切的

`docs/re/36` 把 token 語法解出來了（374 格逐格對上長度表、整檔吃光），
卡在「執行期讀的位置與『檔案 ＝ 374 段首尾相接』不在同一個座標系」，
並且把下一步寫成「從那 65 KB 是怎麼讀進來的開始追」。

這一輪就是追那一件事，而且不必反組譯讀檔常式——**拿記憶體去對檔案**
就看得出來。

## 做法

跑到動畫進行中（收據 `intro40`，`-steps 40000000`，畫面上是船艦剪影），
把整個 1 MB 倒下來，然後在 dump 裡每 512 bytes 取一段 32 bytes 回頭去
`IBM16.350` 裡搜。

127 段全部命中，而且 **`dump 位移 − 檔案位移` 是同一個常數 30385**
——那一整塊就是壓縮資料的緩衝區，一對一映射到檔案的一段。

逐位元組收緊之後：

```
dump 0x17606–0x26EAE  ＝  檔案 0x00FF55–0x01F7FD
起點 ＝ 檔案位移 65365，長度 63656
```

## 結論（confirmed）

**65365 正好是第 117 格的邊界**（374 個長度累加出來的邊界表裡有它），
而且 `65365 + 63656 = 129021` **也是邊界**。

再對一次規則：

| | 值 |
|---|---|
| ≤ 65536 的最大影格邊界 | **65365** |
| ≤ 65365 + 65536 的最大影格邊界 | **129021** |

兩個都對上。所以讀檔是這樣切的：

> 每次填一個 64 KB 的緩衝區，**塞得下幾個完整影格就塞幾個**，
> 剩下的留給下一次。分界一律落在影格邊界上。

`cs:[001C]`（「目前吃到哪」）因此是**這一塊裡的位移**，不是檔案位移
——`docs/re/36` 拿它去對檔案的絕對位置，當然對不上。

## 這解掉了什麼

`docs/re/36` 的「格 → 位移」死路有兩個症狀，這條規則解掉第一個：
執行期的 `cs:[001C]` 與檔案位移之間差一個「這一塊的起點」。

第二個症狀（第一個 token 應該是「跳過 10,559 格」、但監看到的第一個
寫入是 `0x20` 寫進第 0 格）還在。不過那個數字量自執行器
`8c8af90`，而現在是 `2833ec9`——**收據綁執行器版本**，那個觀測要重做才
算數。
