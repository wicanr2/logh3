# 115 — `OPEN.EXE` 的讀檔常式與那個 +40

`docs/re/108` 量到開頭動畫的兩次讀檔差 40 個位元組，因此遊戲看到的
資料流是 `檔案[0:40] ＋ 檔案[65365:]`，第 1–116 格從來沒被解過。
這一輪去找**為什麼是 40**。

## 先把段對到位址

`OPEN.EXE` 的段值直接就是線性位址除以 16 ——**載入段是 0**。
錨點：`mov cx,2378h` 在線性 `0x4417`，後面接 `F3 A5`（`rep movsw`），
而那條 `rep movsw` 就是 `docs/re/108` 記的 `041F:022A`：

```
0x441A − 0x022A = 0x41F0 = 0x041F × 16   →  載入段 0
```

倒一份執行期記憶體就能直接用 `seg × 16 + off` 讀碼
（收據 `openmem`，只跑 3,000 萬步 ≈ 13 秒）。

## 讀檔常式（`041A:0023`，線性 `0x41C3`）

```
push bp / mov bp,sp
push ds
lds  dx,[bp+8]        ; 緩衝區 far ptr
mov  cx,[bp+0Ch]      ; 長度
mov  bx,[bp+6]        ; 檔案代號
mov  ah,3Fh
int  21h              ; ← 041A:0035，`docs/re/108` 的觀測點
pop  ds / leave / retf
```

就是 `read(handle, buf, len)` 的薄包裝，**+40 不是它做的，是呼叫端
傳進來的**。兩次傳的是：

| 次 | 傳進來的 far ptr | 線性 | 長度 |
|---|---|---|---|
| 1 | `175C:001E` | `0x175DE` | 65,365 |
| 2 | `175F:0016` | `0x17606` | 63,656 |

段 ＋3、位移 −8，淨 ＋40。

## 段 `041F` 開頭那張指標表

```
cs:000A  0020
cs:000C  0080
cs:000E  001E:175C   ← 讀取緩衝區的 far ptr
cs:0012  0016:2760   ← plane 0 的緩衝區（`docs/re/108`）
cs:0016  0016:34B0
cs:001A  6D60        ← VRAM 的第二頁
cs:001C  0000        ← 這一格在緩衝區裡的位移（`docs/re/73` 的那個值）
```

## 呼叫端沒找到

在整份 1 MB 的傾印裡搜**所有**會解到 `0x41C3` 的 far call
（`9A` ＋ 任何 seg:off）與 near call（`E8`），**一個都沒有**；
搜寫 `cs:000E` 的指令也沒有。所以那支常式是**透過指標呼叫的**
（`call far [mem]`），符合 GLUE 打包後的樣子。

**所以「+40 從哪裡來」還是沒解。** 下一步要嘛在讀檔的 `int 21h` 上
掛 `-regs-at` 把回返位址（堆疊上的 CS:IP）讀出來，要嘛對 `cs:000E`
下寫入監看。兩條都可行，這一輪沒做。

## 這件事對 remake 的影響

沒有影響到目前的實作：remake 照**檔案順序**播 374 格
（`docs/spec/020`）。原版那個行為會讓 374 格裡的 116 格永遠看不到，
是不是要照抄是**忠實度取捨**，等使用者裁決。
